# 5. 容灾与监控

## 杀 leader 实测

`docker stop` leader(zk-2/132):

- 剩余两节点**秒级完成选举**,zk-3/133 成为新 leader(`srvr` 的 Mode 即时翻转);
- 切换窗口内写入会失败(ZAB 需要新 leader 就位),**读(如果客户端连的是 follower)也存在短暂不可用**——ZK 客户端库自带重连重试,应用侧重点是会话超时设置(session timeout 建议 ≥ 2×tickTime×syncLimit);
- 132 回归后自动以 follower 身份重新加入,**数据由快照+事务日志自动追平**(zxid 对齐,巡检 Z10 的语义)。

运维要点:**杀 leader 是 ZK 最值得定期演练的故障**(无损害、可预期);三节点环境不要同时重启两台——剩余 1 台不构成多数派,整个 ensemble 拒绝服务。

## 监控:mntr 四字命令(实测输出)

```bash
echo mntr | timeout 3 bash -c 'exec 3<>/dev/tcp/127.0.0.1/2181; cat >&3; timeout 2 cat <&3'
# zk_version              3.9.5-293c895a8d966a3ecb92872be4a1daf87d725da2, ...
# zk_peer_state           following - broadcast        ← leader 是 leading - broadcast
# zk_avg_latency          134.0                        ← Z03:>50ms P1
# zk_outstanding_requests 0                            ← Z04:>10 持续 P1
# zk_znode_count          5                            ← Z06 趋势
# zk_followers            2(仅 leader 上有意义)
```

接 Prometheus 走 zookeeper exporter(mntr 转 metrics);命令面(巡检 Z01~Z10)与指标面共用这些字段,阈值真源在巡检文档。

## 排障字典(实测)

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| ruok/mntr 返回空 | 四字命令白名单没放行 | zoo.cfg 的 4lw.commands.whitelist(第 3 篇) |
| ensemble 组不起来,日志只有超时 | ZOO_MY_ID 与 server.N 不匹配 | 逐台核对 myid |
| 全体 Mode 都是 follower/looking | 多数派失联(两台同时挂/网络分区) | 恢复节点;别同时重启两台 |
| `Node does not exist: <子路径>`(create 时) | 父节点不存在,报错文案误导 | 先建父(第 4 篇实测坑) |
| dataDir 涨满盘 | autopurge 默认关 | 基线开启(第 3 篇) |
| 客户端频繁重连 | session timeout 过小/网络抖动/GC 停顿 | 调大客户端 timeout;查 ZK 主机 GC 日志 |
