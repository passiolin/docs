# LVM 缓存迁移与实测(10.10.10.44)

> - **环境**:PVE 9.2.2(kernel 7.0.2-6-pve,lvm2 2.03.31),Xeon E5-2698B v3,251G 内存,2026-10-16 迁移并实测。
> - **本次变更**:4T HGST 从 ZFS(tank)迁为 LVM;960G SK hynix NVMe 全量转作该卷的 dm-cache **writeback** 缓存(880G cachepool、64K chunk、smq 策略);ZFS 在本机退役。
> - **历史文档**:[1.存储配置](1.存储配置.md)、[2.存储性能实测](2.存储性能实测.md) 记录 ZFS 时期(2026-10-10~10-16)的方案与数字,可作本次迁移前基线;local-lvm(NVMe 原生)部分不受本次变更影响。

## 一、决策背景与终态

ZFS 时期实测出的两个事实促成这次迁移:

1. **VM 的 O_DIRECT 直读吃不到任何缓存**(`dd iflag=direct` 实测 47MiB/s),而 VM 盘在 `cache=none` 下全部走直读路径;
2. **L2ARC 766G 对 VM 读零贡献**(命中率 ~1%,整场压测 `l2_read_bytes` 无变化),ARC 常驻仅 4.3G/64G,基本不驱逐、L2ARC 收不到料。

dm-cache 的特点正好覆盖这两条:块层缓存,对 O_DIRECT 一视同仁;writeback 让**异步写也吃 NVMe**(ZFS 的 SLOG 只加速同步写)。代价事先列明并接受(本机为测试机、数据可重建):失去 ZFS 快照与压缩、串行 fsync 变慢(见 3.4)、掉盘/断电 = 缓存后数据从备份重建。终态:

```
hdd VG(4T HGST + 960G NVMe 各一个 PV,共 4.51T)
├─ hdd/data   3.64T linear LV → ext4(-m 1,noatime)→ /mnt/hdd
│              PVE dir 存储 hddvm;所有 VM 盘 = /mnt/hdd/images/<id>/vm-<id>-disk-0.raw
└─ hdd/cpool  880G @ NVMe(64K chunk / smq / writeback)透明挂在 data 上
```

建栈命令(重建参照):

```bash
HDD=/dev/disk/by-id/ata-HGST_HUS724040ALA640_PN1338P4H0LDLB    # 4T
NVME=/dev/disk/by-id/nvme-HFS960GD0MEE-5410A_EI6CQ0678101A1F3U  # 960G

# 1) 4T:单大 LV + ext4,先占满机械盘(保证后面 cachepool 只能落 NVMe)
pvcreate $HDD; vgcreate hdd $HDD
lvcreate -l 100%FREE -n data hdd $HDD
mkfs.ext4 -m 1 -L hdddata /dev/hdd/data
mkdir -p /mnt/hdd/{images,dump,template/iso,snippets}
mount /dev/hdd/data /mnt/hdd     # fstab:/dev/hdd/data /mnt/hdd ext4 defaults,noatime 0 2

# 2) NVMe 并入同 VG 做缓存池(同 VG 是硬要求)
sgdisk --zap-all $NVME; sgdisk -n 1:1MiB:0 -t 1:8E00 $NVME; partprobe $NVME
pvcreate ${NVME}-part1; vgextend hdd ${NVME}-part1
lvcreate -y --type cache-pool -L 880G --poolmetadatasize 4G --chunksize 64K -n cpool hdd ${NVME}-part1
lvs -a -o name,devices hdd                         # ★ cdata/cmeta 必须都落在 nvme 上
lvconvert -y --type cache --cachepool hdd/cpool --cachemode writeback --cachepolicy smq hdd/data
```

## 二、迁移记录(六阶段,约 3.5 小时,VM 零停机)

| 阶段 | 时间 | 动作 | 关键点 |
| --- | --- | --- | --- |
| 1 拆加速件 | 17:33 | `zpool remove` SLOG、L2ARC | 数分钟;窗口内 fsync 走盘上 ZIL(慢一档);可原样挂回 |
| 2 NVMe 重分区 | 17:35 | 单分区 → flash VG/薄池(95%FREE + 4G 元数据) | 作数据中转仓库,PVE 定义 flashvm |
| 3 迁入 NVMe | 17:36–18:53 | 4 台 VM 盘在线 `qm move-disk` → flashvm | 437G;102 的 750G 约 1h20m |
| 4 4T 转 LVM | 18:59–19:03 | `zpool destroy` → pv/vg/lv → ext4 → 挂载 → `pvesm add dir hddvm` | 不可逆点;前置=副本验证(在线三台持续运行 + 101 首/末 256M 抽检与启动验证) |
| 5 回迁 | 19:06–20:29 | `qm move-disk` 逐台 → hddvm,恢复 ISO/模板与 150 的 cloudinit | 写入端为裸机械盘,750G 约 1h20m |
| 6 缓存上线 | 20:35–20:55 | 拆 flash → NVMe 并入 hdd VG → 建 cpool → 挂 writeback → 冒烟 | 附加在挂载中的卷上在线完成 |

迁移踩坑:

1. **运行中的 VM 持有"已从 conf 删除"的旧 cloudinit 镜像句柄** → `zpool destroy` 报 `pool or dataset is busy`;重启该 VM(本次为 150)释放句柄后销毁成功。换盘类操作前先查挂载点持有进程(`fuser -vm` 或扫 /proc);
2. **conf 的 `[PENDING]` 段与 `unused0` 死引用**要在删除旧存储定义前清理:103 的 [PENDING] scsi0 残指 tankvm,不清理则下次启动失败;`qm set -delete unused0` 因卷文件已不存在会拒绝,直接编辑 conf 删除该行;
3. **`cache_pool_max_chunks` 默认 100 万**:880G × 64K = 1440 万块超限,lvm2 会把缓存池静默降成 1M 粒度、并让显式 `--chunksize 64K` 报错。改 `/etc/lvm/lvm.conf` 的 `allocation {}` 段加一行 `cache_pool_max_chunks = 20000000`(本机备份 `lvm.conf.bak-20261016`);LVM 会提示"高于推荐值",属预期。1M 粒度对随机写不利(部分块写要按整块回读);
4. origin(占满整盘的 LV)不支持 discard 透传,dm-cache 自动 `no_discard_passdown`;整盘场景无实际影响。

### 3.2 测试环境:VM104(fio-hot)

新建,克隆自 fio-test(本机唯一带 cloud-init 的现成 fio 环境;克隆期间源 VM 停了约 5 分钟):Debian 13 + fio 3.39,4C/4G,`sda` 20G(系统)+ `sdb` 60G(测试盘,均落 hddvm),IP 10.10.12.160,root 免密。

```bash
qm clone 150 104 --full --storage hddvm --format raw --name fio-hot
qm set 104 --cores 4 --memory 4096 --onboot 0 \
  --net0 virtio,bridge=vmbr1 --ipconfig0 ip=10.10.12.160/24,gw=10.10.12.1
echo "ssh-rsa <公钥>" > /root/fio-vm.pub        # qm set --sshkeys 收的是文件路径,不是内容
qm set 104 --sshkeys /root/fio-vm.pub
qm set 104 --scsi1 hddvm:60,format=raw,aio=threads,cache=none,discard=on,iothread=1,ssd=1
qm cloudinit update 104        # instance-id 随之变化;重启后 cloud-init 重跑并注入公钥
# 来宾内:mkfs.ext4 -m 1 /dev/sdb && mount /dev/sdb /mnt/fio
```

不用了:`qm destroy 104`;`/mnt/fio` 里 f1/f2 留着可复测。

### 3.3 热数据五件套(VM104 内,ext4 on hddvm)

预热:f1(8G)/f2(2G)先顺序写满,f1 再全量直读一遍,保证 64K 块全部进缓存;所有测试 `--direct=1 --invalidate=0`——fio 默认 `invalidate=1` 会先清文件页缓存,不清则永远测不到缓存层(承接第二篇踩坑表)。

```bash
cd /mnt/fio
fio --name=seqR --filename=f1 --bs=1M --rw=read --ioengine=libaio --iodepth=32 --direct=1 \
    --runtime=20 --time_based --invalidate=0 --group_reporting | grep -E "^ +read:"
fio --name=seqW --filename=f1 --size=8G --bs=1M --rw=write --ioengine=libaio --iodepth=32 --direct=1 \
    --runtime=20 --time_based --invalidate=0 --group_reporting | grep -E "^ +write:"
fio --name=rw4k --filename=f2 --size=2G --bs=4k --rw=randwrite --ioengine=libaio --iodepth=32 --direct=1 \
    --runtime=20 --time_based --invalidate=0 --group_reporting | grep -E "^ +write:"
fio --name=fw4k --filename=f2 --bs=4k --rw=randwrite --ioengine=libaio --iodepth=1 --direct=1 --fsync=1 \
    --runtime=20 --time_based --invalidate=0 --group_reporting | grep -E "^ +write:|sync \("
fio --name=rr4k --filename=f2 --bs=4k --rw=randread --ioengine=libaio --iodepth=32 --direct=1 \
    --runtime=20 --time_based --invalidate=0 --group_reporting | grep -E "^ +read:"
```

| --- | --- | --- |
| 顺序读 1M QD32 | **935MiB/s** | 冷读 104–110MiB/s |
| 顺序写 1M QD32 | **711MiB/s** | 97–134MiB/s |

### 3.4 fsync 短板(本架构的关键约束)

- 现象:单笔 4K+fsync 仅约 116 IOPS、单笔延迟约 9ms;
- 归因链:来宾内 8.6ms ≈ **主机侧绕过 QEMU 直测 12.2ms**,慢在存储层;该 NVMe 报 `vwc=0` 且无 FUA,dm-cache 对 flush 走保守路径(确认前先把本轮脏块写回机械盘),9–12ms 即磁头随机写延迟;LVM/dm-cache 无此项开关;
- 影响:**DB 类串行 fsync 负载维持落 local-lvm**(见 [2.存储性能实测](2.存储性能实测.md) 第四节);批量提交(如 32 笔/次)可摊到约 1.9k IOPS;
- 理论替代:dm-writecache(fsync 快、写日志式)无读缓存,不适合本机画像。

## 四、运维行为与回退键

- **脏块不自动清理**:dm-cache 把脏块攒到缓存压力才回写(本机空闲后台写约 6MB/s,dirty 持续缓慢增长)。`dmesg` 的 cleaner 排空消息在本内核不支持(试过报 EINVAL)。巡检看 `cache_dirty_blocks`,长期贴近 1440 万(≈880G)说明工作集超缓存,写路径将退化为回写速度(~110–180MiB/s);
- **冷数据仍是磁头速度**:冷顺序读 100–140MiB/s;冷 4K 随机写约 123 IOPS(部分块写按 64K 回读,固有行为)。热才快,这是本架构的定义;
- **回退键**:`lvconvert -y --splitcache hdd/data`(摘缓存、保留池)/ `--uncache`(连池一起删);两者都先把脏块写回,loop 沙盘实测摘前摘后数据 sha256 一致;
- **语义**:writeback 下缓存盘是脏块的唯一副本,断电/掉盘 = 恢复备份(测试机已接受);正常重启不丢(脏位图在盘上);
- 巡检工具:`/root/hdd-cache-status.sh`(缓存模式/命中/脏块/空间一屏);
- VM 盘参数维持 `aio=threads,cache=none,discard=on,iothread=1,ssd=1`;ext4 层上 io_uring 亦可用,待 A/B(需各自重启一次)。
