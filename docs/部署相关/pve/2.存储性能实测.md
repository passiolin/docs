# 存储性能实测(tank + local-lvm)

> - **环境**:PVE 9.2.2(kernel 7.0.2-6-pve,OpenZFS 2.4.2-pve1),Xeon E5-2698B v3(32 线程),251G 内存,2026-10-15/16 实测。
> - **被测存储**:tank = HGST HUS724040ALA640 4TB(7200 转 CMR 单盘)+ 海力士 HFS960GD0MEE 960G NVMe(SLOG 128G + L2ARC ~766G);local-lvm = WDC SN530 512G NVMe 上的 LVM-thin。
> - **被测虚机**:VM 114(remote,Ubuntu,kernel 7.0.0-38-generic),200G 盘先后挂在 tank 与 local-lvm 上各测一轮;测试期间同机还有 5-6 台 VM 在跑,共存负载对数字的影响见第五节。
> - **工具**:fio 3.39/3.41,libaio 引擎,每项 10-20s time_based;结论均为主机侧与虚机内双侧对照后的数字。

## 一、测试方法与命令

五件套 fio,每项对应一条真实路径(考察点见表)。完整命令如下,虚机内 root 执行,目录任意、预留测试文件空间即可:

```bash
apt-get install -y fio        # 未装时
mkdir -p /test && cd /test

# 顺序写 1M QD32(持续写吞吐)
fio --name=seqW --filename=f1 --size=8G --bs=1M --rw=write --ioengine=libaio \
    --iodepth=32 --direct=1 --runtime=20 --time_based --group_reporting | grep -E "^ +write:"

# 顺序读 1M QD32(刚写完即读 = 热读口径)
fio --name=seqR --filename=f1 --bs=1M --rw=read --ioengine=libaio \
    --iodepth=32 --direct=1 --runtime=20 --time_based --group_reporting | grep -E "^ +read:"

# 4K 随机写 QD32
fio --name=rw4k --filename=f2 --size=2G --bs=4k --rw=randwrite --ioengine=libaio \
    --iodepth=32 --direct=1 --runtime=20 --time_based --group_reporting | grep -E "^ +write:"

# 4K 随机写 QD1 + fsync(持久化确认延迟,重点看输出里 sync (usec) 的中位数)
fio --name=fw4k --filename=f2 --bs=4k --rw=randwrite --ioengine=libaio \
    --iodepth=1 --direct=1 --fsync=1 --runtime=20 --time_based --group_reporting \
    | grep -E "^ +write:|sync \("

# 4K 随机读 QD32
fio --name=rr4k --filename=f2 --bs=4k --rw=randread --ioengine=libaio \
    --iodepth=32 --direct=1 --runtime=20 --time_based --group_reporting | grep -E "^ +read:"

rm -f f1 f2
```

结果只取 fio 输出的三类行:`read:` / `write:`(IOPS 与 BW)和 `sync (usec)`(fsync 延迟分布,中位数是 SLOG/存储层的真实确认延迟)。两条执行纪律:`--ioengine=libaio` 必写(默认 psync 会把 iodepth 静默砍成 1,见第五节踩坑表);`--direct=1` 的口径见本节末第 4 条(direct=disabled 的池上它被忽略,等价 buffered;未 disabled 的 ZFS 池上会走慢路径)。

| 项 | 命令要素 | 考察点 |
| --- | --- | --- |
| 顺序写 1M QD32 | `--bs=1M --rw=write --ioengine=libaio --iodepth=32 --direct=1` | 持续写吞吐 |
| 顺序读 1M QD32 | 同上 `--rw=read` | 读吞吐(冷/热分开报) |
| 4K 随机写 QD32 | `--bs=4k --rw=randwrite` | 随机写吞吐 |
| 4K 随机写 QD1 + `--fsync=1` | 逐笔持久化 | 同步确认延迟(SLOG 的主场) |
| 4K 随机读 QD32 | `--rw=randread` | 随机读(冷/热分开报) |

四个必须交代的口径,数字离开它们没有意义:

1. **冷与热分开报**。读路径有三层缓存:guest 页缓存 → 主机 ARC(64G)→ L2ARC(766G)。同一块盘,2G 热文件在 ARC 里测出 102k IOPS,全冷撞磁头只有 100-250 IOPS——都不是假数据,是不同层的真实速度;
2. **确认速度 ≠ 持续落盘速度**。fio 报的 BW 是"收到确认的速率",sync=disabled + 25G dirty 蓄水时确认速度(313MB/s)远高于磁头落盘速度(~130MB/s),长跑会回落;
3. **共存负载记账**。同机 VM 的读写与压测抢磁头,安静时刻与繁忙时刻同参数差 2-5 倍(178 vs 76 的顺序写就是同一参数的两个时刻);
4. **direct 语义**。fio 的 `--direct=1` 与 VM 盘的 `cache=none` 都产生 O_DIRECT;OpenZFS 2.3+ 引入 `direct` 数据集属性后,O_DIRECT 的处理路径随属性变化(见第三节),这是本轮最大的一个坑。

## 二、调优时间线

| 步骤 | 变更 | 动机 | 实测效果 |
| --- | --- | --- | --- |
| 1 | 发现 `zfs_arc_max=16G` 为旧手写配置,上调 64G | 一级读缓存过瘦 | 读管线进料恢复 |
| 2 | `l2arc_write_max` 8MB/s → 128/256MB/s,`l2arc_noprefetch=0` | 默认暖机速度形同关闭 | L2ARC 分钟级进料 |
| 3 | 发现 `atime=on`(默认),改 `atime=off` + `relatime=on` | 读附带元数据写 | 读密集负载去放大器 |
| 4 | 发现 `direct=standard`(默认)下 O_DIRECT 回退路径拖垮写(1M 顺序写 4-50MB/s,buffered 路径 313MB/s),改 `direct=disabled` | O_DIRECT 全部走慢车道 | **单笔最大修复**,详见第三节 |
| 5 | `sync=always` → `standard` → `disabled` 三轮 A/B | 验证确认时机对吞吐的影响 | 持续写零差异(守恒律),最终取 disabled(确认最快) |
| 6 | `dirty_data_max` 60G + `txg_timeout` 15s 实验 | 想扩大突发蓄水 | **反向优化**,写崩到 2-5MB/s,回滚默认 25G/5s |
| 7 | vdev 队列 `async_read/write_max_active` 3/10 → 16/16 | 高延迟设备社区值 | 幅度有限,保留 |
| 8 | VM 盘 `cache=none` 保持,补 `discard=on,ssd=1`,guest 开 `fstrim.timer` | thin 池空间回收 + SSD 语义 | 空间纪律,非性能项 |
| 9 | qemu 引擎默认 io_uring → **`aio=threads`**(tankvm 全部 VM 盘) | io_uring 对 ZFS 数据集文件的直写退化 | VM102 guest 直写 5.4 → 95MB/s;VM150 同条件 988MB/s |
| 10 | VM 盘格式 **qcow2 → raw**(`qm move-disk --format raw --delete` 在线转换) | 隔离实验:同 VM 同池同参数,raw 988 vs qcow2 146MB/s | qcow2 元数据序列化罚消失;102(425G)转换后待复测 |

第六行值得记一笔:dirty 上限调到 60G 时,60G 已超过 ARC 有效水位(实测仅 4-64G 浮动),脏数据挤压导致新写阻塞,叠加 `txg_timeout=15` 把确认周期拉长,写入崩到个位数 MB/s。回滚默认后恢复。"参数不是越大越好"在这两个旋钮上有实测背书。

## 三、结果一:guest 在 tank 上(HDD + 缓存)

tank/vm 终态参数:zstd / recordsize=64K / **sync=disabled** / **direct=disabled** / atime=off / logbias=latency。

| 场景 | sync=always(初版) | sync=disabled + buffered(终态) |
| --- | --- | --- |
| 顺序写 1M QD32(主机侧) | 49.5MB/s(direct=1 拖累)/ 178MB/s 长跑持续 | **278MB/s(确认速度)/ ~130MB/s 磁头持续** |
| 顺序写 1M QD32(虚机内) | 24-42MB/s | **278MB/s** |
| 4K 随机写 QD32(虚机内) | ~450 IOPS | **2,328 IOPS** |
| 4K fsync QD1(主机侧,安静时刻) | 5628 IOPS / 178µs | 561-1588(受共存负载浮动) |
| 顺序读 1M QD32(热,ARC/L2ARC 命中) | 603MB/s-1.2GB/s | 同左 |
| 4K 随机读(热,2G 全驻 ARC) | **102k IOPS** | 同左 |
| 4K 随机读(冷,磁头) | 100-250 IOPS | 同左 |
| 4K 随机读(冷 × 写风暴拥塞,最坏记录) | **6 IOPS** | 同左 |

两条守恒律贯穿全部数字:**持续写吞吐 = 磁头落盘速度**(sync 属性只改确认时机,同刻 A/B 零差异);**读速度 = 数据所在层的速度**(ARC/L2ARC 热读是 NVMe 级,冷读是磁头级,写风暴时冷读陪葬到个位数)。

## 四、结果二:guest 迁 local-lvm 后(NVMe 本体)

VM 114 移到 local-lvm(LVM-thin on SN530),盘设置 `cache=none, discard=on, ssd=1, iothread=1`,重启后虚机内实测:

| 场景 | 数字 | 对照 tank 终态 |
| --- | --- | --- |
| 顺序写 1M QD32 | 792 → 977MB/s(两轮,第二轮缓存热) | ~9.9 倍 |
| 顺序读 1M QD32 | 2247MB/s(含 guest 缓存加成,稳态约 1-1.5GB/s) | ~1.9 倍 |
| 4K 随机写 QD32 | 44.6k → 88.1k IOPS | **~38 倍** |
| 4K 随机写 QD1 + fsync | ~1000 IOPS,sync 延迟中位 ~850µs | fsync 延迟 ~3 倍改善,吞吐口径不同不可直接比 |
| 4K 随机读 QD32(direct 路径) | 6202 IOPS(冷直读) | 磁头冷读的 ~20 倍 |

结论与方案期预判一致:数据物理上在 NVMe,才有"NVMe 满速";缓存只能兑现延迟与热读,不能给持续吞吐。

## 五、踩坑清单

**VM 102(425G,qcow2→raw 在线转换)终测**(2026-10-16,转换后干净环境):

| 场景 | qcow2 时代 | raw 终态 | 备注 |
| --- | --- | --- | --- |
| 顺序写 1M QD32 | 95-105MB/s | **312MB/s** | qcow2 元数据罚消除,3 倍;长跑回落磁头持续段 |
| 顺序读 1M QD32(8G>ARC) | 87-94MB/s | 102MB/s | 冷读磁头物理,不变;热读见下 |
| 4K 随机写 QD32 | — | **2,147 IOPS** | RAM 确认;前置 6G 落盘未排空时被拖到 54,测试须等 dirty 排空 |
| 4K 随机读 QD32(热) | — | **331k IOPS / 1.3GB/s** | 2G 全驻 ARC |
| 4K 写+fsync QD1 | — | 105 IOPS,sync 均值 1.1ms(长尾 133ms) | guest 串行提交路径固有水位;主机侧同负载 561,local-lvm 约 1000;DB 型负载建议落 local-lvm |

| 坑 | 现象 | 处置 |
| --- | --- | --- |
| fio 默认 ioengine=psync | 不写 `--ioengine=libaio` 时 iodepth 被静默砍成 1(输出有警告行),QD32 测试实为 QD1 | 压测必写 libaio;看输出 `IO depths: 1=100%` 即中招 |
| O_DIRECT 回退慢路径 | `direct=standard`(默认)下,cache=none 的 VM 盘与 `--direct=1` 压测全走慢车道(1M 顺序写 4-50MB/s) | `zfs set direct=disabled tank/vm`;或改用 buffered 口径测 |
| guest 内 `--direct=1` 压测 | sync=disabled 之下仍穿透缓存直击磁头,叠加落盘争抢后崩到 2-6MB/s | 测"日常体验"去掉 direct;测下限再单独测 |
| atime 默认 on | 读附带元数据写,读密集负载被放大 | `zfs set atime=off relatime=on` |
| dirty 上限超过 ARC 有效水位 | 60G dirty(>实测 ARC 4-64G)阻塞新写,崩到个位数 MB/s | 回滚默认(10% 内存);dirty/txg 实验证明"调大"反向 |
| 压测时机 | 同参数安静/繁忙时刻差 2-5 倍(178 vs 76) | 对比测试必须同时间窗背靠背 |
| qcow2 稀疏 | fio size=8G 实写可能远小于 8G(未分配簇跳过),百分比虚高 | 以目标池 `zfs list used` 增量为准 |
| qemu io_uring × ZFS 文件 | PVE 默认引擎对 ZFS 数据集上的盘文件直写退化,guest 直写掉到个位数 MB/s | 盘选项加 `aio=threads`;LVM 块存储不受影响(114 在 local-lvm 同引擎满速) |
| qcow2 在 HDD 支撑的池上 | 簇分配/元数据路径把持续写压到 raw 的约 1/7(同 VM 同池隔离实测 146 vs 988MB/s);425G 老文件叠加 CoW 碎片更差(VM102 仅 95MB/s) | VM 盘用 raw;存量 `qm move-disk <VMID> scsi0 tankvm --format raw --delete` 在线转换 |
