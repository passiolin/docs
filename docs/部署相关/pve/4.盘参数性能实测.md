# 盘参数性能实测(hddvm + dm-cache)

> - **环境**:PVE 9.2.2(kernel 7.0.2-6-pve,lvm2 2.03.31),Xeon E5-2698B v3(32 线程),251G 内存,2026-10-17 实测。
> - **被测存储**:hddvm = 4T HGST LVM(ext4)+ 960G SK hynix NVMe 上的 dm-cache **writeback**(880G cachepool、64K chunk、smq 策略);栈本身见 [3.LVM缓存迁移与实测](3.LVM缓存迁移与实测.md)。
> - **被测虚机**:6 台同源 Debian 13 + fio 3.39(4C/4G),`150` 为基线,`105–109` 各改一个 PVE 盘参数;全部位于 hddvm,IP `10.10.12.150–155`。
> - **工具**:fio 3.39,libaio 引擎;主测每项 20s time_based,复测 10s;全部 `--direct=1 --invalidate=0`。沿用的五件套口径与"冷热分层"方法见 [2.存储性能实测](2.存储性能实测.md)。

## 一、测试设计

**单变量矩阵。** 基线 = `aio=threads, cache=none, raw, virtio-scsi-single, iothread=1, discard=on, ssd=1`(与 3 篇 3.3 的 VM104 同参数)。五台变体各只改一项:aio 引擎、QEMU 盘缓存模式(两档)、盘格式、总线。

**为什么逐台背靠背。** 先跑完全部 6 台的主测,再对随机三项(4K fsync / 4K 随机写 / 4K 随机读)做第二轮背靠背复测——dm-cache 的 fsync 与随机写对缓存积压状态敏感(见 3 篇 3.4),只有两轮一致的差异才算配置效应。

**文件协议。** 与 2 篇一致:f1=8G、f2=2G 建在各自系统盘(20G,ext4),先顺序写满 f1/f2、f1 再全量直读一遍(保证 64K 块全部进缓存),然后跑五件套。所有 fio 都加 `--invalidate=0`——默认的 `invalidate=1` 会先清文件页缓存,永远测不到缓存层。

## 二、测试环境与复现命令

**底座(VM 150)。** 用本地云镜像新装,无外部依赖:

```bash
qm create 150 --name fio-base --memory 2048 --cores 2 --ostype l26 --scsihw virtio-scsi-single \
  --net0 virtio,bridge=vmbr1 --agent 1 --serial0 socket --vga serial0 --onboot 0 --numa 0
qm importdisk 150 /var/lib/vz/template/iso/debian-13-generic.qcow2 hddvm --format raw
qm set 150 --scsi0 hddvm:150/vm-150-disk-0.raw,aio=threads,cache=none,discard=on,iothread=1,ssd=1
qm resize 150 scsi0 20G
qm set 150 --ide2 hddvm:cloudinit --ciuser root --sshkeys /root/fio-vm.pub --ciupgrade 0 \
  --ipconfig0 ip=10.10.12.150/24,gw=10.10.12.1 --nameserver 10.10.12.1 --boot order=scsi0
# 来宾内:apt-get install -y fio
```

**变体。** 停底座后克隆(克隆要求源 VM 停机),改 IP 与磁盘行,`qm cloudinit update` 刷新 seed,再启动:

```bash
qm stop 150; qm set 150 --cores 4 --memory 4096
qm clone 150 105 --full --storage hddvm --format raw   --name fio-iouring
qm clone 150 106 --full --storage hddvm --format raw   --name fio-wcache
qm clone 150 107 --full --storage hddvm --format raw   --name fio-unsafe
qm clone 150 108 --full --storage hddvm --format qcow2 --name fio-qcow2
qm clone 150 109 --full --storage hddvm --format raw   --name fio-vblk
qm start 150
# 每台:改 ipconfig0;改磁盘行(见下表);qm cloudinit update <id>
```

## 三、结果

### 3.1 主测(顺序 20s / 随机 20s)

| VM | 变更 | 顺序读(MiB/s) | 顺序写(MiB/s) | 4K 随机写 | 4K fsync(IOPS / avg) | 4K 随机读 |
| --- | --- | --- | --- | --- | --- | --- |
| 150 | 基线 | 865 | 696 | 55.2k | 1103 / 885µs | 82.6k |
| 105 | aio=io_uring | **1045(+21%)** | 698(持平) | **61.0k(+10%)** | **3072 / 305µs(≈3×)** | 70.6k(−15%) |
| 106 | cache=writeback | **1559(+80%)** | **1544(+122%)** | 46.5k(−16%) | 572 / 1724µs | 83.3k(持平) |
| 107 | cache=unsafe | **1655(+91%)** | **1801(+159%)** | 41.6k(−25%) | **5479 / 163µs(假确认)** | 82.3k(持平) |
| 108 | qcow2 | 693(−20%) | 648(−7%) | 51.3k(−7%) | 1199 / 811µs | 81.4k(持平) |
| 109 | virtio-blk | 863(持平) | 687(持平) | **57.7k(+5%)** | 907 / 1082µs | **86.1k(+4%)** |

fsync 行的长尾:各配置 max 40–460ms,avg 0.16–1.7ms——单笔确认对缓存积压状态敏感,见 4.5。

### 3.2 第二轮复测(背靠背,各项 10s)

| VM | fsync(IOPS / avg) | 4K 随机写 | 4K 随机读 |
| --- | --- | --- | --- |
| 150 | 770 / 1276µs | 54.6k | 82.6k |
| 105 | **3112 / 301µs** | **60.4k** | 69.5k |
| 106 | 1359 / 712µs | 49.1k | 86.1k |
| 107 | **6370 / 138µs** | 48.0k | 84.2k |
| 108 | 1032 / 947µs | 52.0k | 79.0k |
| 109 | 1431 / 679µs | 57.9k | 83.4k |

两轮对照:**io_uring(顺序外三项)与 unsafe 的差异两轮一致**;其余项波动 ≤±10%,按配置效应解读。

### 3.3 预热速率(参考)

| VM | f1 顺序写(MiB/s) | f1 全量读 | f2 写 |
| --- | --- | --- | --- |
| 150 / 105 / 109 | 674 / 707 / 693 | 687 / 705 / 1510 | 684 / 690 / 657 |
| 106 / 107 | 1374 / 1454 | 1537 / 1707 | 1239 / 1441 |
| 108 | 630 | 813 | 627 |

writeback/unsafe 的预热读写在 1.3–1.7GB/s 量级——宿主页缓存直接兑现;cache=none 组的预热速率则与"首次触碰 + 后台回写"混合口径一致。

## 四、逐项分析

### 4.1 aio=io_uring:收益全面,代价一处

顺序读 +21%(865→1045)、4K 随机写 +10%(55.2k→61.0k)、串行 fsync ≈3–4×(885–1276µs→301–305µs);两轮一致。唯一代价是 **4K 随机读 −15%**(82.6k→70.6k,两轮同样一致)。净判断:顺序、写、确认三面全赢,随机读的损失发生在 7–8 万 IOPS 的高位,按"顺序与 fsync 是日常痛点"的负载画像取 io_uring。机制不展开(提交/完成路径的开销差异是主要嫌疑),数据可复现即可用。

ZFS 时代"io_uring 对数据集文件退化"的结论不适用于本栈:那是 ZFS 文件层的路径问题,ext4 上 io_uring 行为正常。

### 4.2 cache 模式:writeback/unsafe 的翻倍不是缓存层

106/107 的顺序读写在 1.5–1.8GB/s,是 **宿主页缓存**在兑现(多出来的一层易失缓存),不是 dm-cache 层变快:①长跑仍受 dm-cache→机械盘回写(~110–180MiB/s)约束;②4K 随机写反而比基线低 16–25%(页缓存合并/回写路径的开销);③unsafe 把 guest flush 一并吞掉——其 163µs / 5479 IOPS 的 fsync 是假确认,断电丢整个未落盘窗口。默认保持 `cache=none`;只有"数据可弃 + 要突发顺序吞吐"才上 writeback。

### 4.3 qcow2:ZFS 时代的 1/7 罚已消失

顺序读 −20%、顺序写 −7%、4K 随机写 −7%、随机读持平、fsync 持平。对比 2 篇在 ZFS 池上隔离实测的 raw 988 vs qcow2 146MiB/s(约 1/7),本栈的代价已收窄到个位数~20%。结论:需要 PVE 原生快照/回滚时直接上 qcow2(落地记录见 [3.LVM缓存迁移与实测](3.LVM缓存迁移与实测.md) 第五节),追吞吐用 raw。

### 4.4 virtio-blk:边际收益

4K 随机写 +5%、随机读 +4%,顺序与 fsync 持平。不值得为它放弃 virtio-scsi-single 的生态与多盘管理,维持现状。

### 4.5 基线互证与 fsync 的状态敏感性

同一参数(threads/none/raw/scsi-single)与 3 篇 3.3 的 VM104 相比:顺序写 696 vs 711、4K 随机写 55.2k vs 54.4k、随机读 82.6k vs 77.8k,互证成立;顺序读 865 vs 935 略低(不同 VM 镜像与共存负载)。唯一大差异是 fsync:VM104 当时 116 IOPS / 8.6ms,本组 770–1103 / 0.9–1.3ms——同配置跨会话差近 10 倍,指向**脏块积压状态**,而非配置。因此:fsync 的绝对值不可跨时段比较,配置差异必须在同窗口背靠背里看(本表的两轮设计)。

## 五、结论与推荐参数集

**默认参数集(hddvm,新盘/新 VM):**

```bash
qm set <VMID> --scsi0 hddvm:<VMID>/<卷>,aio=io_uring,cache=none,discard=on,iothread=1,ssd=1
```

| 需求 | 选择 | 代价 |
| --- | --- | --- |
| 默认(吞吐 + 确认速度) | `aio=io_uring, cache=none, raw` | 4K 随机读 −15%(相对 threads) |
| 要 PVE 原生快照/回滚 | 盘格式 **qcow2**(其余同上) | 顺序 −7~−20%、随机 −5% |
| 数据可弃、要突发顺序吞吐 | `cache=writeback`(flush 语义仍透传) | 页缓存一层易失 + 随机写 −16%;`unsafe` 仅限纯可弃数据 |
| 追求 4K 随机极限 | `virtio-blk` | 收益 +4~5%,放弃 scsi-single 生态,不值得默认 |
| 4K 随机读敏感、可放弃 fsync 提速 | 回退 `aio=threads` | 顺序读 −17%、fsync 慢 3–4× |

存量 VM 的 io_uring 切换在各自重启窗口执行。

## 六、口径与踩坑

| 坑 | 现象 | 处置 |
| --- | --- | --- |
| fio 默认 `invalidate=1` | 每个 job 启动先清文件页缓存,复读永远不命中缓存层 | 全部加 `--invalidate=0`,测试文件必须先预热 |
| fsync 行跨时段不可比 | 同配置不同会话 116 vs 770–1103 IOPS;avg 0.16–12ms 都能出现 | 配置对比必须同窗口背靠背;绝对值当作区间看(受脏块积压支配) |
| cache=writeback/unsafe 的数字口径 | 顺序读写的翻倍来自宿主页缓存,不是存储层 | 与 cache=none 组不可按"存储速度"横比;报告时注明层 |
| 克隆 cloud-init VM 后不刷新 seed | 新 IP/公钥不生效,克隆还带着源 VM 的 IP | 改完配置执行 `qm cloudinit update <id>`,重启后 cloud-init 重跑(instance-id 变化) |
| `qm set --sshkeys` | 传公钥内容报 `can't open 'ssh-rsa …'` | 传**文件路径**(`--sshkeys /root/fio-vm.pub`) |
| virtio-blk 带 `ssd=1` | 启动报 `ssd: property is not defined in schema` | virtio-blk 不支持 ssd 属性,去掉;换总线后 `boot: order` 同步改 |
| 主测 ≠ 复测的随机写波动 | 单轮数字受时段负载影响 ≤±10% | 关键结论只取两轮一致项;其余按噪声处理 |
| 并行跑多台 | 同池共存负载会互相抢缓存/磁头 | 6 台顺序执行,单台运行测试套件 |

测试组留存:VM 150(fio-base)与 105–109 在 hddvm 保留(IP `10.10.12.150–155`,root 免密),可随时复测;不用了 `qm destroy`。
