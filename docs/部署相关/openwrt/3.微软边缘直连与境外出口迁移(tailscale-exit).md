# 微软边缘直连与境外出口迁移(tailscale-exit)

2026-10-29 晚高峰,家里的 `ping bing.com` 出现 3~4 秒 RTT 加 66% 丢包。排查下来是两个不相干的问题叠在一起:分流清单没覆盖微软的全球边缘网段,导致 bing 流量被兜进隧道;而隧道本身(当时的 OpenVPN TCP)晚高峰被运营商 QoS 掐到秒级。这一篇记录网关侧的处理:bing 直连修复、境外出口整体迁移到 hk-1 的 tailscale exit node、OpenVPN 拆除,以及排查过程中挖出的 **pbr 与 tailscale0 网关纳管冲突**这个总根因。tailnet 侧的接入与打洞分析在[家用路由器接入 headscale 与 exit 出口迁移](../tailscale/3.家用路由器接入headscale与exit出口迁移.md)。

## 一、bing 秒级延迟的定位

### 1.1 四层证据

| 目标 | RTT | 丢包 | 路径 |
| --- | --- | --- | --- |
| 网关 `192.168.0.1` | 1.3ms | 0% | WiFi |
| `223.5.5.5` | 10ms | 0% | chnroute 直连 |
| `202.89.233.100`(cn.bing.com,世纪互联) | 42ms | 0% | 直连,**在** chnroute 里 |
| `150.171.27.10`(bing.com,微软全球边缘) | **3000~5800ms** | **0~70%** | 隧道,**不在** chnroute |
| `223.254.128.189`(`ping -I pppoe-wan` 绕开策略) | 24ms | 0% | 直连,CN2(`59.43.x`) |

关键推理有三条。其一,所有境外目标同量级地慢(8.8.8.8、1.1.1.1 与 bing 一个量级),说明瓶颈在隧道,不在某家服务。其二,绕开策略路由直连 ping 办公室端点、VPS、微软边缘全部干净,国际链路当晚根本不堵。其三,`ping` 输出里的 `pipe 5~15`(同时刻 5~15 个包滞留链路)是队列堆积特征,配合 TTL 恒定 39,排除路由环路。

### 1.2 根因:两个问题叠加

1. `bing.com` 解析到微软**全球**边缘(`150.171.27.10`/`150.171.28.10`),只有 `cn.bing.com` 才落在世纪互联的国内 CDN(`202.89.233.100`,恰好被 chnroute 覆盖)。微软全球边缘不在国内清单里,按"国内直连、其余走隧道"的判定必然进隧道。
2. 隧道自身病了:OpenVPN over TCP 8443 的长连接晚高峰被动态 QoS,每次重连后短暂正常、几分钟内塌到秒级,`ovpn-watchdog` 每 5 分钟重启兜底。TCP-over-TCP 一旦外层丢包,双层重传叠加,雪崩到秒级。

## 二、微软边缘直连

### 2.1 修复结构

把 `150.171.0.0/16` 加进 pbr 的直连用户集合,并让 bing 相关域名解析出的任何 IP 动态跟进:

```sh
# /etc/pbr.d/15-extra-direct.sh (新增,pbr 官方钩子目录)
#!/bin/sh
EXTRA_FILE="/etc/pbr-china/extra-direct.txt"
SET_NAME="pbr_wan_4_dst_ip_user"
[ -s "$EXTRA_FILE" ] || exit 0
while read -r cidr; do
	case "$cidr" in ''|\#*) continue ;; esac
	nft add element inet "${nftTable:-fw4}" "$SET_NAME" "{ $cidr }" 2>/dev/null \
		|| logger -t pbr-extra-direct "failed to add $cidr"
done < "$EXTRA_FILE"
```

```sh
# /etc/pbr-china/extra-direct.txt — 手动维护的额外直连网段
150.171.0.0/16
```

`/etc/dnsmasq.conf` 追加三条,域名解析结果动态进同一集合,防微软换边缘网段:

```
nftset=/bing.com/4#inet#fw4#pbr_wan_4_dst_ip_user
nftset=/cn.bing.com/4#inet#fw4#pbr_wan_4_dst_ip_user
nftset=/www.bing.com/4#inet#fw4#pbr_wan_4_dst_ip_user
```

效果:`ping 150.171.27.10` 3000ms → **54ms**,`https://bing.com` 从 TLS 握手超时恢复到 0.38s 正常打开,国内直连无回归。

### 2.2 踩坑

1. **Kwrt 的 pbr init 对多元素 `dest_addr` 有 shift bug**:`dest_addr` 给多个元素时报 `shift: 3: shift count out of range`,元素静默不进集合。走 `/etc/pbr.d/` 钩子绕开。
2. **pbr reload 会重建 user 集合**:手动 `nft add element` 加的网段活不过下一次 reload(OpenVPN 每次重连都触发 reload)。必须放进 `/etc/pbr.d/` 钩子。
3. **Kwrt 的 dnsmasq init 不生成 uci 的 `list nftset` 选项**(uci 里存了,生成的 conf 里没有),dnsmasq 2.91 二进制本身支持 nftset,写进 `conf-file=/etc/dnsmasq.conf` 才生效。
4. 鉴别"国际堵"还是"隧道堵"最快的办法:路由器上 `ping -I pppoe-wan <目标>` 绕开策略直接测。

## 三、境外出口切换 tailscale exit

### 3.1 为什么可以切

hk-1(tailnet 里的 VPS 节点,`100.64.0.2`)与家用网关之间是 WireGuard UDP 直连,物理路径 24ms;而 OpenVPN 是 TCP,晚高峰被掐到秒级且 TLS 握手都完不成。出口协议从"被 QoS 针对的长寿 TCP"换成"自托管控制面调度的 UDP WireGuard",是质变。

### 3.2 部署

```sh
# hk-1 上(VPS docker 容器 ts-hk)
docker exec ts-hk tailscale set --advertise-exit-node
docker exec headscale headscale nodes approve-routes -i 7 -r "0.0.0.0/0,::/0"

# 家用网关上
tailscale set --exit-node=100.64.0.2 --exit-node-allow-lan-access=true
uci set tailscale.settings.exit_node='100.64.0.2'; uci commit tailscale
```

### 3.3 规则全景

| 优先级 | 规则 | 作用 |
| --- | --- | --- |
| 5200 | `fwmark 0x80000 → pbr_wan` | tailscale 自身传输(disco/STUN)强制直连,防 STUN 污染 |
| 5265 | `fwmark 0x10000 → pbr_wan` | chnroute 已标记的国内流量抢在 exit 兜底之前直连,**保住国内外分流** |
| 5270 | `lookup 52` | tailscale 的表:对端 /32、已接受子网、`default dev tailscale0`(exit) |
| 29997/29999/30000 | pbr 的 fwmark 规则 | 旧 OpenVPN 时代的直连/隧道标记,保留兼容 |
| 32766 | `lookup main` | 兜底(def1 `/1` 路由已随 OpenVPN 拆除消失) |

国内走 5265 直连、境外走 5270 进 exit、mesh 目标按 table 52 的最长前缀匹配,三条路径互不干扰。

### 3.4 实测

| 路径 | 实测 |
| --- | --- |
| 境外 `google.com`(经 hk-1 exit) | 200 OK,0.58s(凌晨)/0.99s(晚高峰),出口 IP = VPS 荃湾 |
| 国内 `223.5.5.5` | 6.9ms,无回归 |
| bing 直连 | 0.51s |

晚高峰跨境 UDP 也有 QoS(观测过 ~170ms + 少量丢包),凌晨明显干净。回滚一行:`tailscale set --exit-node=` 清空即可回到旧架构(但旧架构的隧道本身是病的,没有回滚的价值)。

## 四、pbr 与 tailscale0 的网关纳管冲突(总根因)

当晚路由表反复"时好时坏"的总根源,日志链完整:

1. netifd 里存在绑定 `tailscale0` 的接口时,pbr 自动检测会把它纳管为 gateway(日志:`pbr started with gateways: wan/... tszif/tailscale0/...`);
2. 此后每次 pbr reload(OpenVPN 每次重连都触发)都会清理它认为属于自己的规则,与 tailscaled 的 netlink 协调器互相打架;
3. tailscaled 日志出现 `monitor: ip rule deleted`,随后 **table 52 反复被清空或只重装一半**;
4. table 52 一空,未标记流量全部落回 main 的兜底路由——当兜底还是 OpenVPN 的 `/1` 时,国内外流量一起掉进病隧道。

修复:**不建 netifd 接口**,fw4 zone 直接绑定设备:

```sh
uci set firewall.tsz=zone
uci add_list firewall.tsz.device='tailscale0'   # 无 network 的纯 device zone,fw4 支持
```

此后 pbr 网关列表只剩 `wan`,冲突源消除,table 52 一次到位。

## 五、OpenVPN 拆除与双层自愈

### 5.1 拆除清单

10-31 上午电信强制重拨 PPPoE(CGNAT 换址 `100.80.218.206` → `100.73.59.91`)把 OpenVPN 残留的问题彻底暴露:tun0 每轮重连都触发 tailscaled `major rebind`,重装 table 52 时半途而废。确认 exit node 稳定后拆除:

```sh
/etc/init.d/openvpn stop; /etc/init.d/openvpn disable
opkg remove openvpn-openssl openvpn
sed -i '\|/root/ovpn-watchdog.sh|d' /etc/crontabs/root   # ovpn-watchdog 一并退役
uci -q delete network.openvpn
```

### 5.2 双层自愈

| 层 | 载体 | 触发 | 覆盖 |
| --- | --- | --- | --- |
| 事件层 | `/etc/pbr.d/20-tailscale-direct.sh` | pbr reload(接口/防火墙事件) | 5200 传输直连、5265 国内直连、table 52 丢失时重启 tailscale |
| 定时层 | `/root/ts-route-watchdog.sh`,cron `*/2` | 每 2 分钟 | 覆盖 PPPoE 重拨这类**没有 pbr 事件**的抖动 |

定时层是必须的:PPPoE 重拨引发 tailscaled rebind 时未必伴随 pbr reload,纯事件钩子会输给竞速。修复动作统一为重启 tailscale 服务(toggle accept-routes 只能恢复子网路由,**对端路由必须整服务重启才回来**)。

### 5.3 重拨场景实测

10-31 上午重拨后,定时层在下一个周期内完成修复,最终验收:mesh 办公室主机 9ms、PVE 节点 7.9ms(均直连 0 丢包),国内 6.9ms,google 经 exit 0.58s,出口 IP = VPS。

## 六、遗留

- VPS 开 BBR(`net.ipv4.tcp_congestion_control=bbr` + `fq`),exit node 与 derper 的 TCP 链路都受益;
- 打洞依赖家里电信 CGNAT 的映射新鲜窗口,偶尔退化回 DERP(分析见[家用路由器接入 headscale 与 exit 出口迁移](../tailscale/3.家用路由器接入headscale与exit出口迁移.md)),要永久稳定可在办公网路由器加 `UDP 41641 → 10.10.10.106:41641` 映射。
