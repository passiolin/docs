# 内核参数与百万连接

单机长连接(接入层、推送网关、TCP 代理)要往上堆并发时,内核默认值会接连挡路。本文把这些参数一次理清:哪些要改、哪些新内核已经不用改、每条为什么。实测环境:PVE VM 105(`linux-test`),Ubuntu 26.04 LTS,内核 7.0.0-38-generic,4C/4G(可用 3.3Gi)/40G;出厂默认值在升级前的 7.0.0-27 上采集,调优值在 27/38 两个内核上都验证过并经重启复验。十万级连接为本文实测;百万级只有笔者的生产口径(Nginx 单机 100 万,见文末),未在 4G 测试机复测,推算处单独标出。

## 一、出厂默认值(26.04 实测基线)

网上老文章的"默认值"大多停在内核 4.x 时代,先看这台机器的真实现状:

| 参数 | 出厂值(实测) | 说明 |
| --- | --- | --- |
| fs.file-max | 9223372036854775807 | 等效无限,新内核不用再抬 |
| fs.nr_open | 2147483584 | 老内核是 1048576,如今百万单进程不再撞它 |
| net.core.somaxconn | 4096 | accept 队列上限 |
| net.core.netdev_max_backlog | 1000 | 突发流量下丢包高发点 |
| net.ipv4.tcp_max_syn_backlog | 256 | 半连接队列,出厂偏小 |
| net.core.rmem_max / wmem_max | 4194304 | 老文章说的 208KB 早已翻篇 |
| net.ipv4.tcp_rmem | 4096 131072 26436704 | 单连接读缓冲 下限/默认/上限 |
| net.ipv4.tcp_wmem | 4096 16384 4194304 | 写缓冲同上 |
| net.ipv4.tcp_mem | 38724 51634 77448 | 全局 TCP 缓冲水位,**单位是页**(×4KB) |
| net.ipv4.tcp_max_tw_buckets | 16384 | TIME_WAIT 上限,按 4G 内存算的 |
| net.ipv4.tcp_max_orphans | 16384 | 同上 |
| net.ipv4.tcp_tw_reuse | 2 | 新内核出厂仅 loopback 生效 |
| net.ipv4.tcp_fin_timeout | 60 | |

| net.ipv4.tcp_syncookies | 1 | 已开 |

| 登录会话 ulimit -n | soft 1024 / hard 524288 | |
| net.netfilter.nf_conntrack_max | 65536(模块加载后) | 随内存缩放,见第五节 |

## 二、参数怎么组织与生效

统一写 `/etc/sysctl.d/99-xxx.conf`,`sysctl --system` 生效,重启复验过全部保持。每行后面注释出厂值,半年后就知道自己改了什么、偏离多远。`tcp_mem` 单位是页,`rmem/wmem` 单位是字节,混着写很容易差 4096 倍。

## 三、文件描述符:三层限制,缺一层撞一层

1. **系统总量 fs.file-max**:出厂已是 `9223372036854775807`,不用动。老脚本第一行就是抬它,属于无效功。
2. **单进程硬上限 fs.nr_open**:出厂 2147483584。实测天花板行为——`bash -c 'ulimit -Hn 2147483000'` 成功;`ulimit -Hn 3000000000` 报 `cannot modify limit: Operation not permitted`,**root 也一样被拒**,想超过它得先抬 nr_open。如今这个数比百万大四个数量级,实际场景撞不到。
3. **进程实际限制**,分两种入口:
   - 登录会话:`/etc/security/limits.conf` 加 `* soft/hard nofile 65535`,重新登录生效(实测 65535;sshd 的 PAM 链带 `pam_limits.so`)。坑:自带文件的注释示例里就有 "nofile" 字样,拿它做"是否已配置"的 grep 判断会误判。
   - systemd 服务:单元里 `LimitNOFILE=1048576`(实测生效)。坑:`systemd-run --scope -p LimitNOFILE=...` 报 `Unknown assignment`——scope 类单元不支持该属性,验证要走 service(`systemd-run -p LimitNOFILE=1048576 sh -c 'ulimit -Hn'`)。容器是第四层,启动时单独 `--ulimit nofile=...`,主机配置救不了它(笔者测试机没装 Docker,此条未复测,TODO)。

## 四、调优配置全文(实测生效)

```ini
# /etc/sysctl.d/99-tcp-scale.conf —— 场景:单机长连接。注释里的"出厂"为 26.04 实测值。

# accept 队列
net.core.somaxconn = 65535               # 出厂 4096
net.ipv4.tcp_max_syn_backlog = 65535     # 出厂 256
net.core.netdev_max_backlog = 250000     # 出厂 1000

# socket 缓冲:对百万连接,上限收紧是兜底——出厂 tcp_rmem 上限 25M,
# 单连接吃满是内部破坏,16M 封顶把最坏情况的总量框住
net.core.rmem_max = 16777216             # 出厂 4194304
net.core.wmem_max = 16777216             # 出厂 4194304
net.ipv4.tcp_rmem = 4096 131072 16777216 # 出厂 4096 131072 26436704
net.ipv4.tcp_wmem = 4096 65536 16777216  # 出厂 4096 16384 4194304

# TIME_WAIT / 孤儿连接(出厂 16384 是按 4G 内存给的,百万场景必抬)
net.ipv4.tcp_max_tw_buckets = 1048576
net.ipv4.tcp_max_orphans = 1048576
net.ipv4.tcp_tw_reuse = 1                # 出厂 2(仅 loopback)
net.ipv4.tcp_fin_timeout = 15            # 出厂 60

# 空闲长连接探测(出厂 7200/75/9:对端死两小时才发现)
net.ipv4.tcp_keepalive_time = 600
net.ipv4.tcp_keepalive_intvl = 30
net.ipv4.tcp_keepalive_probes = 5

# BBR(出厂 cubic)
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr

# 小内存机器(出厂 60)
vm.swappiness = 10

# conntrack:NAT/iptables 机器必看,见第五节
net.netfilter.nf_conntrack_max = 262144  # 出厂 65536(4G 机)
```

BBR 补充实测:`sysctl -n net.ipv4.tcp_available_congestion_control` 出厂只有 `reno cubic`;`modprobe tcp_bbr` 后多出 bbr;直接写上面的配置、`sysctl --system`,`tcp_bbr` 和 `sch_fq` 模块**自动加载**(lsmod 可见),26.04 连 `/etc/modules-load.d` 都不用配。

## 五、conntrack:一次真实截胡

机器上只要有 iptables/nftables 规则(NAT、防火墙、fail2ban 都算),每条连接进 conntrack 表。模块默认不加载,一旦加载,出厂上限按内存给——4G 机实测 65536。

十万连接测试第一轮(第七节),连接数停在 6.5 万,`alloc 130381 ≈ 2×65191` 这个整数关系暴露了元凶,dmesg 里成串:

```text
nf_conntrack: table full, dropping packet
```

抬到 262144 复跑,20 万 socket 全部 ESTABLISHED,事故闭环。代价:每条目约 300 字节,26 万条目约 78MB,可忽略;hash 桶出厂与上限同数(65536),要压低负载因子可以在 `/etc/modprobe.d/` 里 `options nf_conntrack hashsize=65536`(桶数=上限/4,此条笔者未复测,TODO)。观测:`conntrack -C` 看当前条目,`dmesg | grep -i conntrack` 看有没有在丢。

这台机不需要连接跟踪的话,`iptables -t raw` 里对相应端口打 NOTRACK 可以整条绕过——但笔者在 7.0.0-38 上实测**环回流量的 NOTRACK 没生效**:raw 表规则优先级正确(priority raw)、计数器在涨,连接仍进表。复现:

```bash
conntrack -C                                  # 基线
iptables -t raw -A OUTPUT -p tcp --dport 9999 -j NOTRACK
iptables -t raw -A PREROUTING -p tcp --dport 9999 -j NOTRACK
# 向本机 9999 端口发起若干连接后
conntrack -L | grep 9999                      # 条目照常出现
```

原因待查,在定性之前,生产上以"抬 max"为主、NOTRACK 为辅,改完用 `conntrack -C` 前后对比复核。

## 六、端口与 TIME_WAIT:受 65535 限制的是客户端角色

服务端一个监听端口就能挂百万连接——连接由五元组(源 IP、源端口、目的 IP、目的端口、协议)区分,监听端口不占本地端口。受端口数卡死的是**客户端角色**:本机主动外连时,出厂 `ip_local_port_range = 32768-60999` 只有 28232 个源端口,对同一个 `目的IP:端口` 最多挂 2.8 万条;扩到 `1024 65535` 也才 6.4 万,再往上要给本机加辅助 IP 或加客户端。压测百万连接最常犯的错就是单客户端打满端口后误判服务端不行了。

TIME_WAIT 堆在**主动关闭的一侧**。代理机两头都主动关,两头都堆:客户端方向靠 `ip_local_port_range`+`tcp_tw_reuse=1`(出厂 2 只对 loopback 生效,要显式改 1,依赖 timestamp,新内核默认开);服务端方向 TIME_WAIT 不占端口,占的是 `tcp_max_tw_buckets` 的额度(出厂 16384,百万场景抬到百万级,见第四节)。`tcp_fin_timeout` 管 FIN_WAIT_2,60 秒改 15 秒,减的是半关连接的驻留。

## 七、十万连接实测(本文环境)

方法:Python asyncio,服务端 4 个监听端口(18801-18804)各收 2.5 万,客户端分 4 路建连后全部挂住不发数据;两端进程各以 `LimitNOFILE=1048576` 的 systemd service 启动。服务端开 4 个端口的原因:客户端角色对单个 `IP:端口` 只有 2.8 万个源端口(第六节),一个端口收不下 10 万。

10 万连接全存活时的读数:

| 指标 | 实测值 | 读法 |
| --- | --- | --- |
| sockstat | inuse 200008 / alloc 200009 | 客户端 10 万 + 服务端端 10 万,`ss -s` estab 200001 |
| 内存增量 | +1708 MB | 应用侧 1052MB(asyncio 两进程)+ 内核侧约 656MB |
| 内核侧每连接 | 约 3.3KB | socket 控制块(slab),与经典的 3-4KB 一致 |
| sockstat 的 mem | 256 页 = 1MB | **只统计收发缓冲**;空闲连接缓冲近零,大头在控制块 |
| ListenOverflows / ListenDrops | 0 / 0 | somaxconn 65535 + backlog 全程没丢 |
| conntrack | 10 万条目,零丢包 | 65536 出厂上限在第一轮 6.5 万处截胡,抬 max 后闭环(第五节) |

两个读数上的坑:`/proc/net/sockstat` 的行首是大写 `TCP:`,grep 小写会静默落空;`mem` 字段只算缓冲,估内存占用要用"总量增量减应用 RSS"反推内核侧,或者直接看 slabtop。

结论:十万量级上,fd 和内存都不是墙(4G 内存机都绰绰有余),出厂值里真正动手的是 conntrack;再往上翻倍,先涨的还是应用侧内存——asyncio 每连接 5KB 的对象开销比内核的 3.3KB 还大,Netty/Go 各有自己的系数,内存账要按"内核 3-4KB + 应用侧 N KB"两笔一起算。

## 八、百万连接:推算与未竟事项

从十万外推百万(TODO:以下带 ★ 的均为推算或生产口径,未在本文环境复测):

- **内存 ★**:内核侧 3.3KB/连接 × 100 万 ≈ 3.5GB,8G 内存起步;应用侧缓冲自管,按需分配(先 4KB 起步按需扩),每连接预分配 64KB 就是 64GB 直接出局。
- **四元组**:服务端一个监听端口足够,不用开一堆端口。
- **软中断 ★**:包处理集中在单核时 `mpstat -P ALL 1` 的 `%soft` 会先打满,这是参数全调对之后第一堵墙。多队列网卡做 IRQ 亲和、虚拟机单队列开 RPS、`ethtool -G` 加大 ring buffer——本文虚机未做此项实测。
- **应用架构**:epoll/io_uring 事件模型是唯一路线,一连接一线程在一万连接时已经死透;`SO_REUSEPORT` 起多 worker 分摊 accept。框架自带缓冲的默认值(Netty 的 pooled allocator 等)逐个核对。
- **生产口径**:笔者生产 Nginx 单机 100 万级长连接,参数与本文同一套思路;4G 测试机不复现百万,只验证到十万。
- 再往上是 C10M:DPDK/XDP 内核旁路,那就是另一套技术栈了,本文不展开。

## 九、观测点

```bash
grep "^TCP:" /proc/net/sockstat   # inuse/alloc/tw 与 mem(页,只算缓冲)
ss -s                              # 各状态分布汇总
nstat -az | grep -E "ListenOverflows|ListenDrops"   # accept 队列丢包
conntrack -C                       # conntrack 条目数,对照 nf_conntrack_max
dmesg | grep -i conntrack          # "table full" = 正在丢新连接
mpstat -P ALL 1                    # %soft 单核打满 = 软中断瓶颈
slabtop -o | grep -iE "tcp|sock"   # 内核侧控制块的真实开销
```

压测时盯住这几个,出问题能定位到层: drops 在 Listen* 查 accept 队列,丢在 dmesg 查 conntrack/orphans,内存看 sockstat 加 slabtop,吞吐上不去先看 %soft。

## 十、过时参数黑名单

网上流传的"高并发优化脚本"按下不动:

| 条目 | 现状 |
| --- | --- |
| net.ipv4.tcp_tw_recycle | 内核 4.12 已删除(NAT 环境下导致连接异常,删得好) |
| net.ipv4.netfilter.ip_conntrack_max | 2.6 时代旧名,现在是 net.netfilter.nf_conntrack_max |
| /proc/sys/net/ipv4/route/* 缓存参数 | 路由缓存 3.6 就没了,全组无效 |
| "file-max/nr_open 必改" | 新内核出厂已等效无限(见第一节),改了是无效功 |
| tcp_tw_recycle 配套的 tcp_timestamps 关闭 | timestamp 是 tw_reuse 的依赖,关了 reuse 一起废 |
