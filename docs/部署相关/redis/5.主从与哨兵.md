# 5. 主从与哨兵

> **实测状态**:✅ 已实测 —— Redis 8.0.6,一主两从 + 三哨兵(redis-1/2/3),2026-09-30。复制建立、哨兵互相发现、**故障切换 18 秒**、旧主回归自动降级全流程验证。

## 拓扑

```
redis-1 10.10.12.118  master(6379)  + sentinel(26379)
redis-2 10.10.12.119  replica(6379) + sentinel(26379)
redis-3 10.10.12.127  replica(6379) + sentinel(26379)
```

单主两从、哨兵三节点(quorum=2)。写走主,读可分散到从(应用侧注意复制是异步的)。

## 部署

**从库**(gen 注入 replicaof,其余继承 common):

```bash
./gen-node-conf.sh 10.10.12.119 replica /root/redisconf 10.10.12.118
cp /root/redisconf/redis.conf /data/redis/conf/
docker run -d --name redis --restart=always --stop-timeout=180 --net=host \
  --health-cmd="redis-cli ping | grep -q PONG" -e REDISCLI_AUTH=Redis@2026 \
  -v /data/redis/data:/data -v /data/redis/conf:/conf \
  redis:8.0 redis-server /conf/redis.conf

# 验证(刚起时 master_link_status 可能短暂 down=正在同步,以主库视角为准):
redis-cli INFO replication | grep -E "^role|^master_link_status"
# role:slave / master_link_status:up
# 主库视角:
redis-cli INFO replication | grep -E "^connected_slaves|^slave[01]"
# connected_slaves:2
# slave0:ip=10.10.12.119,port=6379,state=online,offset=45,lag=1
# slave1:ip=10.10.12.127,port=6379,state=online,offset=45,lag=1
```

**哨兵**(每台一个,独立容器、独立配置目录——哨兵运行时会改写自己的配置文件,必须挂**目录**而非单文件):

```bash
./gen-node-conf.sh 10.10.12.118 sentinel /root/redisconf 10.10.12.118
mkdir -p /data/redis/sentinel-conf /data/redis/sentinel-data
cp /root/redisconf/sentinel.conf /data/redis/sentinel-conf/
docker run -d --name redis-sentinel --restart=always --net=host \
  -v /data/redis/sentinel-conf:/conf -v /data/redis/sentinel-data:/data \
  redis:8.0 redis-sentinel /conf/sentinel.conf --sentinel
```

**部署验收的第一项:哨兵互相发现**(`num-other-sentinels` 必须 =2):

```bash
redis-cli -p 26379 SENTINEL master mymaster | sed -n '/num-slaves/{n;p};/num-other-sentinels/{n;p}'
# 2   2
```

**实测教训(本次实验真实踩到)**:`sentinel announce-ip` 配错(例:只写了 `10.10.12.`)时,哨兵能监视主从、`SENTINEL master` 看起来正常,但 **num-other-sentinels=0**——三个哨兵互相看不见,quorum 永远凑不齐,**主挂了也不会切换**。这一项不验收,整套哨兵形同虚设。

## 故障切换实测

`docker stop` 主库(优雅停机),实测时间线:

```
00:58:13 发起停止
01:05 版重测(修正 announce-ip 后):停主 → 18 秒后 SENTINEL get-master-addr 返回新主 10.10.12.127
        且新主 INFO replication 已是 role:master
```

18 秒的构成:down-after-milliseconds(基线 5s)主观下线 → 多哨兵协商客观下线(quorum=2)→ 选举执行者 → 提升从库。硬故障(kill -9/断电)同样流程,只是下线判定同样从 5s 起算。

```bash
# 应用侧拿当前主地址(客户端重连逻辑就靠它):
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
# 1) "10.10.12.127"
# 2) "6379"
```

**旧主回归自动降级**(实测):主库重启后被哨兵配置为新主的从库:

```
role:slave
master_host:10.10.12.127
GET failover:test → ok   ← 切换期间写在新主上的数据已同步回来
```

## 应用接入

- 连接串给哨兵地址列表,客户端库支持 sentinel 模式自动寻主(Java: Jedis/Lettuce sentinel 模式;Go: go-redis ParseSentinelURL);
- 重试语义:切换窗口(本实测约 18s)内写入失败,应用要重连+重试;
- 从库读:注意异步复制的延迟窗口,强一致读走主。

## 已知坑(实测)

| 坑 | 现象 | 解 |
| --- | --- | --- |
| announce-ip 错误 | num-other-sentinels=0,永不切换 | 部署验收必查(见上);--net=host 下 announce-ip=本机真实 IP |
| 哨兵配置挂单文件 | 运行时改写配置导致挂载失效 | 挂目录(conf + data 分开) |
| 从库刚起查 master_link_status | 短暂 down(同步中)属正常 | 以主库 connected_slaves state=online 为准 |
| 切换后旧主重启 | 若旧主配置仍是 standalone | 哨兵会下发 replicaof 改写;确认哨兵在线再回归 |
