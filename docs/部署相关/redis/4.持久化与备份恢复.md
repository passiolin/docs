# 4. 持久化与备份恢复

> **实测状态**:✅ 已实测 —— Redis 8.0.6。RDB、AOF 多部分结构、kill -9 崩溃恢复全链路验证,输出摘自实测。

## 基线策略

RDB + AOF 双开(第 2 篇 common.conf):AOF everysec 保丢失窗口 ≤1 秒,RDB 保"整文件快速重启/异地备份"。纯缓存场景可关 AOF(巡检 R07 按业务约定豁免),当存储用则必须双开。

## 文件层实测:数据目录长什么样

```bash
# BGSAVE 后:
redis-cli BGSAVE
redis-cli INFO persistence | grep rdb_last_bgsave_status    # rdb_last_bgsave_status:ok
ls -la /data/redis/data/
# dump.rdb                              ← RDB 快照

# 7.0+ 的 AOF 是"目录"而不是单文件(实测):
ls -la /data/redis/data/appendonlydir/
# appendonly.aof.1.base.rdb     ← 基础文件(混合持久化:RDB 格式开头)
# appendonly.aof.1.incr.aof    ← 增量命令流
# appendonly.aof.manifest      ← 清单(记录 base/incr 序列)
```

**备份与迁移的注意**:拷 AOF 必须连 `manifest` 一起拷整个 `appendonlydir/`;只拷一个 .aof 文件在新版会因缺 manifest 拒载。

## 崩溃恢复实测(kill -9)

```bash
redis-cli SET hello:redis v1
redis-cli SET big:key "<5000 字节值>"
docker exec redis sh -c "kill -9 1"        # 模拟进程暴毙
# restart=always 自动拉起
docker exec -e REDISCLI_AUTH=Redis@2026 redis redis-cli GET hello:redis   # v1
docker exec -e REDISCLI_AUTH=Redis@2026 redis redis-cli GET big:key | wc -c   # 5001
```

**结论:everysec 下 kill -9 数据完好**(最多丢最后 1 秒窗口内的写入)。

## 备份操作

```bash
# 快照备份(BGSAVE 期间服务不中断):
redis-cli BGSAVE && ls -la /data/redis/data/dump.rdb
cp /data/redis/data/dump.rdb /data/backup/dump-$(date +%F).rdb

# AOF 整目录备份:
tar czf /data/backup/aofdir-$(date +%F).tgz -C /data/redis/data appendonlydir
```

## 恢复操作与演练纪律

- **RDB 恢复**:停实例 → 放 dump.rdb 到 dir(删掉旧 appendonlydir,否则优先 AOF)→ 起实例;
- **AOF 恢复**:停实例 → 整个 appendonlydir 换成备份版 → 起实例;
- 演练:在实验机上按上面两条各走一遍,验证 key 数与抽样值;**改备份策略的验收标准是恢复演练通过**,不是"备份脚本跑成功"(同 MySQL 第 4 篇纪律)。

## 已知坑

1. 恢复时 RDB 与 AOF 并存,**AOF 优先加载**——想用 RDB 恢复必须移走 appendonlydir;
2. `SAVE`(前台快照)会阻塞所有请求,运维只用 `BGSAVE`;
3. fork 内存:BGSAVE/AOF 重写靠 fork COW,宿主要留内存余量(maxmemory 之外),否则巡检 R07 的 bgsave 失败(fork 失败)是第一嫌疑;Linux `vm.overcommit_memory=1` 是常规前置(联动 inspect-server)。
