# 5. 容灾实测

> **实测状态**:✅ 已实测 —— ES 8.19.14 三节点,杀节点全流程(yellow → 检索可用 → 回归 green),2026-10-01。

## 杀节点实测时间线

`docker stop` es-3(136,持有 1 个主分片 + 2 个副本):

**停后 15 秒**:

```
"status":"yellow"          ← 副本/主分片重新分配中或未分配
"number_of_nodes":2
curl _count → "count":9    ← 检索完全可用!
```

解读:
- 数据**零丢失**(es-3 上的主分片 2 在别处有副本,副本即刻顶上成为新主);
- yellow ≠ 故障:**yellow = 副本没凑齐但数据完整可服务**;**red = 有主分片彻底不在**(巡检 ES01 的 P0 线);
- 写入在 yellow 期间也正常(新副本异步补齐后回 green)。

**es-3 回归(约 2~3 分钟 JVM 启动)**:

```
"status":"green" / "number_of_nodes":3
```

副本自动回补,分片分布重新均衡——全程无人工干预,这是 ES 与前几章组件最大的体验差异:**自愈是默认行为**。

## 什么情况会 red

- 挂掉的节点持有某分片的**全部副本**(单节点索引/副本数不足以分散);
- 磁盘超 watermark 触发分配保护;
- 处置顺序(巡检 ES01):`GET _cluster/allocation/explain` 先定位原因,**不要急着重启节点**。

## 节点维护的标准姿势

```bash
# 摘除节点前先排干分片(比直接 stop 更平滑):
PUT _cluster/settings {"transient":{"cluster.routing.allocation.exclude._ip":"10.10.12.136"}}
# 等 relocating_shards 归零再维护;维护完清掉设置,分片自动回流
```
