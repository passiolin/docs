# 5. 快照备份

> **实测状态**:✅ 已实测 —— ES 8.19.14,fs 仓库注册 + 全量快照 SUCCESS(2026-10-01)。恢复命令给出但**恢复演练未在本环境执行**(列入待办,演练纪律同 MySQL 第 4 篇)。

## 前置:path.repo 白名单(实测必踩)

yml 不设 `path.repo` 时注册 fs 仓库直接报错——快照目录必须显式白名单:

```yaml
path.repo: ["/usr/share/elasticsearch/snapshots"]   # 容器内路径,挂宿主
```

基线模板已内置(第 3 篇);漏配的表现是 `repository_exception ... path not in repo whitelist`。

## 注册仓库 + 快照(实测)

```bash
# 宿主目录挂载到 /usr/share/elasticsearch/snapshots(见第 2 篇 docker run)
curl -s -X PUT "localhost:9200/_snapshot/lab-repo" -H 'Content-Type: application/json' \
  -d '{"type":"fs","settings":{"location":"/usr/share/elasticsearch/snapshots/lab-repo"}}'

# 全量快照(等完成):
curl -s -X PUT "localhost:9200/_snapshot/lab-repo/snap-1?wait_for_completion=true" \
  | grep -oE '"state":"[A-Z]+"'
# 实测输出:"state":"SUCCESS"
```

- 快照是**集群级一致性**的(进行中写入按 segment 快照点处理);
- 生产改 S3/OSS 仓库(type:s3 + 我们的对象存储体系),命令结构相同;
- 定时:`PUT _slm/policy/...` 快照生命周期策略(每日 + 保留 N 份,与 ILM 联动),巡检 ES11 的"近 7 天无 SUCCESS 快照 P1"靠它兜底。

## 恢复(命令路径,演练待办)

```bash
# 查看快照内容:
curl -s "localhost:9200/_snapshot/lab-repo/snap-1?pretty"
# 恢复(可换索引名,避免覆盖在线索引):
curl -s -X POST "localhost:9200/_snapshot/lab-repo/snap-1/_restore" \
  -H 'Content-Type: application/json' \
  -d '{"indices":"device-events","rename_pattern":"(.+)","rename_replacement":"restored-$1"}'
```

**验收纪律**:备份策略的验收 = 恢复演练通过(数据条数对账 + 抽样值核对),不是"快照 SUCCESS"。改仓库/策略后必演练。

## 已知坑

| 坑 | 现象 | 解 |
| --- | --- | --- |
| path.repo 未配 | repository_exception 白名单报错 | yml 配置 + 滚动重启(第 3 篇) |
| 快照目录属主 | 注册成功但写入失败 | chown 1000:1000 |
| 恢复到原索引名 | 与在线索引冲突 | rename_replacement 换名恢复 |
