# 3. 参数基线与配置模板

> **实测状态**:✅ 已实测 —— ES 8.19.14,模板 [conf/elasticsearch.yml](conf/elasticsearch.yml) + [conf/jvm.options](conf/jvm.options) 已在三节点集群实际应用(discovery/bootstrap/分片行为全部生效)。

## 按"值由谁拍板"分组

| 组 | 拍板人 | 参数(默认 → 基线) |
| --- | --- | --- |
| 一、集群身份 | 定一次 | cluster.name、node.name(gen 注入) |
| 二、发现 | 拓扑 | discovery.seed_hosts(3 台)、**cluster.initial_master_nodes(仅首次组网读!)** |
| 三、网络 | 部署 | network.host、9200/9300 |
| 四、路径 | 部署 | path.data/logs、path.repo(快照白名单) |
| 五、安全 | 合规 | xpack.security.enabled(8.x 默认 true → 内网基线 false) |
| 六、资源 | 机器内存 | ES_JAVA_OPTS 堆(8G 机器 → 2g;**≤31GB 原则,给 50% 左右**) |

**三个易错点**:

1. **cluster.initial_master_nodes 是"一次性火种"**:只在集群第一次组网时被读;生产规范是**组网完成后从配置里删掉它**(留着的风险:整集群重启时有分脑历史的节点可能各自再引导)。本文模板为实验便利保留了三个名字,生产部署按此条执行;
2. **path.repo 不设则快照注册直接报错**(`unknown setting` / repository Path 未在白名单)——第 5 篇备份的前提,基线直接带上;
3. 堆的大小**不是越大越好**:压缩指针在 >31GB 失效,且要给 OS 文件缓存留量(ES 的倒排索引极吃 page cache)。8G 机器 2g 堆是均衡值。

## 参数的生效方式

yml 改动 = 滚动重启(一次一台,`_cluster/health` 回 green 再下一台);少数参数支持 `PUT _cluster/settings` 动态(如分片分配开关)——**动态改动要回抄模板**,否则下次重启回退,和 MySQL/Redis 的漂移纪律一致(巡检 ES09/版本一致性的检查背景)。

## 应用与验证

```bash
./gen-node-yml.sh es-1 /root/    # 共享 yml + node.name 注入
# 重启后核对:
curl -s localhost:9200/_cat/nodes?h=name,master  # 角色与点名正确
```
