# 2. 参数基线与配置模板

> **实测状态**:✅ 已实测 —— Kafka 4.3.1,模板 [conf/kafka-common.env](conf/kafka-common.env) 已在集群实际应用(env 全部生效:topic 的 min.insync.replicas=1、segment.bytes 等出现在 topic 配置里)。

## 按"值由谁拍板"分组(env 键)

| 组 | 拍板人 | 参数(默认 → 基线) |
| --- | --- | --- |
| 一、角色与仲裁 | 架构 | PROCESS_ROLES=broker,controller、CONTROLLER_QUORUM_VOTERS(3 台)、LISTENERS 双端口 |
| 二、副本语义 | 可用性/一致性权衡 | NUM_PARTITIONS(1→3)、DEFAULT_REPLICATION_FACTOR(1→2)、MIN_INSYNC_REPLICAS(1 保持)、内部 topic 副本=2 |
| 三、保留策略 | 磁盘 | LOG_RETENTION_HOURS(168→24,按业务)、LOG_SEGMENT_BYTES(1G 保持) |
| 四、行为基线 | 定一次 | AUTO_CREATE_TOPICS_ENABLE(true→**false**)、GROUP_INITIAL_REBALANCE_DELAY_MS(3000→0) |
| 五、JVM | 机器内存 | KAFKA_HEAP_OPTS(1G 默认→按机器显式设,4G 机器 1G) |
| 六、数据目录 | 部署 | LOG_DIRS=/var/lib/kafka/data(挂宿主) |

**两个必须反直觉设置的**:

1. **auto.create.topics.enable=false**(默认 true):topic 是 schema 资产,手滑打错名字自动建出幽灵 topic 是脏数据之源;显式创建 + 命名规范(巡检 K12 漂移项的源头治理);
2. **副本三元组要自洽**:RF=2 + min.insync.replicas=1 = 3 节点环境的基线(容忍 1 台挂仍可读写);生产要更强一致性可 min ISR=2,代价是挂 1 台就不可写。**min.insync.replicas > RF 是配置事故**(永不满足),巡检 K12 直接 P2。

## 参数的生效方式

- env 在**容器创建**时烙进 server.properties——改 env 必须**重建容器**(docker rm + run),restart 不重读;
- 运行时改单 topic 配置走 `kafka-configs.sh --alter`(如 retention),这类改动是巡检 K12 的"漂移"检查对象。

## 应用与验证

```bash
# 建 topic 后从 topic 配置回看 env 是否落地(实测):
timeout 60 docker exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server $B --describe --topic device-events
# Topic: device-events  PartitionCount: 3  ReplicationFactor: 2
#   Configs: min.insync.replicas=1,segment.bytes=1073741824
```
