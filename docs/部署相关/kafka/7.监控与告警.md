# 7. 监控与告警

## 分工:巡检(命令面)与监控(指标面)用同一套 K 编号

| 巡检项 | 命令面 | 指标面(实测指标名) | 阈值(同源巡检) |
| --- | --- | --- | --- |
| K01 broker 存活 | broker-api-versions | `kafka_brokers` | < 预期台数 P0 |
| K02 消费 lag | consumer-groups describe | `kafka_consumergroup_lag{...}` / `kafka_consumergroup_lag_sum` | >100 万 P1;持续增 P0 |
| K03 消费组活跃 | groups describe | `kafka_consumergroup_members` | 关键组无成员 P1 |
| K08 消息速率 | — | `rate(kafka_topic_partition_current_offset[5m])` | 突降 0 P1 |
| K10 分区分布 | topics describe | `count by (leader) (...)`(leader 分布) | 失衡 P2 |

实测指标样例:

```
kafka_brokers 2
kafka_consumergroup_lag{consumergroup="lab-group",partition="0",topic="device-events"} 1
kafka_consumergroup_lag_sum{consumergroup="lab-group",topic="device-events"} 1
kafka_topic_partition_current_offset{partition="0",topic="__consumer_offsets"} 4
```

(样例里 lag=1 正是杀 broker 期间生产、消费组未跟上的那条——指标面如实反映故障窗口,与命令面对账一致。)

## exporter 部署(实测)

```bash
docker run -d --name kafka-exporter --restart=always --net=host \
  danielqsj/kafka-exporter:v1.8.0 --kafka.server=10.10.12.128:9092
# 注意:v1.8 是命令行参数(--kafka.server),不是 KAFKA_URI 环境变量(实测踩坑)
# 验证:curl -s localhost:9308/metrics | grep -c '^kafka_'  → 385
```

- 一台 exporter 指向任一 broker 即可看到全集群(元数据自发现);多集群则按集群各部署一组;
- broker 端 JVM/请求延迟类指标(K09)exporter 不覆盖,需要 JMX exporter 挂 broker——**已实测(2026-10-09)**,见下节。

## JMX exporter 挂 broker(K09 实测,2026-10-09)

prometheus `jmx_exporter` javaagent 直挂 broker JVM(agent 下载走 **Maven Central**:`io/prometheus/jmx/jmx_prometheus_javaagent/1.0.1`,GitHub release 直链实测 404):

```bash
# ① 容器重建时追加两个挂载与一个 env(jar + 配置放挂载目录):
-e KAFKA_JVM_PERFORMANCE_OPTS="-server -XX:+UseG1GC -XX:MaxGCPauseMillis=20 \
  -XX:InitiatingHeapOccupancyPercent=35 -XX:+ExplicitGCInvokesConcurrent \
  -XX:+ExitOnOutOfMemoryError -Djava.awt.headless=true \
  -javaagent:/opt/jmx/jmx_agent.jar=7072:/opt/jmx/kafka-jmx.yml" \
-v /data/kafka-jmx:/opt/jmx
# ② yml 用 lowercaseOutputName + 正则 rules(mBean → 指标名),抓取 :7072/metrics
```

实测指标名(v1.0.1,K09 对齐):

| 巡检项 | 实测指标名 | 说明 |
| --- | --- | --- |
| 请求队列堆积 | `kafka_network_requestchannel_requestqueuesize` | gauge,持续 >0 需关注 |
| 请求总延迟 | `kafka_network_requestmetrics_totaltimems_count{request="Produce/Fetch/..."}` | counter,**rate() 即 QPS** |
| 请求延迟分位 | `kafka_network_requestmetrics_(local|total|response)timems_99thpercentile{request=...}` | 实测 Fetch follower 99th = 24ms |
| 处理线程空闲 | `kafka_server_kafkarequesthandlerpool_requesthandleravgidlepercent` | **Meter 语义,raw Value 异常大(1e10 级),需差分/rate 处理,别直接告警** |
| broker 吞吐 | `kafka_server_brokertopicmetrics_(messages|bytes|replicationbytes)inpersec` | 重启初期 EWMA 为 0,等一会儿再判 |

实测踩坑(两个都真实发生):

1. **javaagent 会传染容器内所有 CLI**:`KAFKA_JVM_PERFORMANCE_OPTS` 是 kafka-run-class 级别的,CLI(consumer-perf-test 等)启动时也想绑 7072 → 端口冲突 → **agent 主动 exit 整个 CLI JVM**(`Prometheus JMX Exporter exiting`)。解:容器内跑 CLI 一律 `docker exec -e KAFKA_JVM_PERFORMANCE_OPTS="-server" kafka ...` 覆盖;
2. yml 追加规则后**重抓即生效**(无需重启 broker;`jmx_config_reload_*` 计数不动但新指标已出现)。

## 告警规则示例(与巡检阈值对齐)

```yaml
groups:
- name: kafka
  rules:
  - alert: KafkaBrokersLost                  # K01 / P0
    expr: kafka_brokers < 3
    for: 1m
  - alert: KafkaConsumerLagHigh              # K02 / P1
    expr: kafka_consumergroup_lag_sum > 1000000
    for: 10m
  - alert: KafkaConsumerLagGrowing           # K02 / P0
    expr: deriv(kafka_consumergroup_lag_sum[1h]) > 0
    for: 1h
```
