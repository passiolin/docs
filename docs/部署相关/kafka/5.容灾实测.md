# 5. 容灾实测

> **实测状态**:✅ 已实测 —— Kafka 4.3.1(2 broker 在线形态),2026-10-01。杀 broker 全流程:Leader 迁移、ISR 收缩、单副本可写、回归自动补齐。**分区重分配已实测**(2026-10-09,三节点形态)。

## 杀 broker 实测时间线

`docker stop` kafka-1(128,持有 2 个分区的 Leader):

**停后 12 秒**,从幸存 broker(129)视角:

```
Partition: 0  Leader: 2  Replicas: 1,2  Isr: 2     ← Leader 已迁移,ISR 从 [1,2] 收缩为 [2]
Partition: 1  Leader: 2  Replicas: 2,1  Isr: 2     ← (原本 Leader 就在 2)
Partition: 2  Leader: 2  Replicas: 1,2  Isr: 2
```

**期间继续生产**:成功(RF=2 但 min.insync.replicas=1,单副本仍满足写入条件)——3 节点基线(RF=2/minISR=1)在单 broker 故障时**读写双可用**;若基线是 minISR=2,此刻写入会报 NotEnoughReplicas,这是可用性/一致性的显式取舍点。

**128 回归**:副本自动追平(ISR 回到 [1,2]),Leader 是否回迁由 broker 设置决定(默认不抢)。

## KRaft 仲裁容灾

controller 仲裁 3 选 2:杀 1 台,元数据多数派仍在,集群自治;**同时挂 2 台 = 元数据不可用,全集群停摆**——三节点的容错边界就是 1 台。巡检 K06(quorum describe --status 的 LeaderId/CurrentVoters)是这一层的健康口径。

## 分区重分配实录(2026-10-09,三节点)

背景:device-events(3 分区 RF=2)此前副本全在 [1,2]、**三个 Leader 全在 broker 1**;kafka-3 并入后做一轮再均衡。

```bash
# ① 生成提案( topics.json 列出要搬的 topic):
kafka-reassign-partitions.sh --bootstrap-server $BS \
  --topics-to-move-json-file /tmp/topics.json --broker-list 1,2,3 --generate
# ② 执行(plan.json = 上一步 "Proposed" 那行 JSON):
kafka-reassign-partitions.sh --bootstrap-server $BS --reassignment-json-file /tmp/plan.json --execute
# ③ 验证:
kafka-reassign-partitions.sh --bootstrap-server $BS --reassignment-json-file /tmp/plan.json --verify
```

实测结果:`Successfully started partition reassignments for device-events-0,1,2` → **verify 立即全部 completed**(小数据量;大数据量会经历 in-progress 阶段并自动挂节流阈值),最终 describe:副本摊到三台(0:[1,2] / 1:[2,3] / 2:[3,1]),**Leader 1/2/3 各一**;清理由工具自动完成(Clearing broker-level throttles)。

**实测坑:`--generate` 的提案带随机成分**——同一状态连续生成两次,提案不同(本次实测两次分别为 [3,1]/[1,2]/[2,3] 与 [1,2]/[2,3]/[3,1])。生成后**以实际保存的 plan.json 为准**,别脑补"上一次生成的方案";execute 会同时打印当前分配供回滚,回滚就用那份 JSON。

**下线节点姿势**(K10 延伸):先把该节点的分区 reassign 到其他节点(--generate 时 broker-list 排除它),verify 完成后再停 broker。
