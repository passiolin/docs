# 什么是 ServiceLB

ServiceLB(klipper-lb)是 k3s 内置的 LoadBalancer 实现:`type: LoadBalancer` 的 Service 无需安装任何组件,EXTERNAL-IP 直接落地。它和 local-path、traefik 并列为第 1 篇盘点出的开箱即用三件套;RKE2 v1.35 已移除它,要 LoadBalancer 必须自装 MetalLB——有无这一件,直接影响两发行版的选型结论(见 [第 4 篇](4.与RKE2对比.md))。

## 一、控制面:内置 controller 落地址

LoadBalancer 型 Service 需要有人回答"对外 IP 从哪来":云上由 cloud controller 对接 EC2/ALB,自建裸机/虚机集群没有这层,Service 会一直 Pending(RKE2 集群实测如此,见 [kubernetes/8](../kubernetes/8.日常运维与排障.md) 排障表)。ServiceLB 的 controller 内置在 k3s server 进程里,监听所有 LoadBalancer Service 并回填 `status.loadBalancer.ingress`,零安装。关闭参数 `--disable=servicelb`(所有 server 都要带),关闭后存量 LB Service 回到 Pending 无人认领——这是换 MetalLB 前的第一步。

回填的不是池内地址,是 svclb Pod 已就绪节点的自身 IP(节点配了 external IP 用 external,否则 internal,上游文档口径)。所以 `kubectl get svc` 的 EXTERNAL-IP 常是一串节点地址,入口即"任意节点 IP:端口"。

## 二、数据面:一个 Service 一个 svclb DaemonSet

建一个 LoadBalancer Service,kube-system 里随之出现一个 `svclb-<service名>-<随机后缀>` DaemonSet(第 1 篇盘点的"随 LB Service 按需出 svclb Pod"),删 Service 则 DaemonSet 一并回收。svclb Pod 是 privileged 容器(要在宿主机写 iptables),按 Service 声明的端口占住 hostPort,容器里只做一跳:把该端口的流量 DNAT 到 Service 的 ClusterIP——负载均衡本身仍由 kube-proxy 完成。

```text
客户端 → 节点IP:80 → svclb(iptables DNAT)→ ClusterIP:80 → kube-proxy → Pod
```

对照 NodePort 即知定位:链路同样是"节点端口 → Service → Pod",NodePort 用 30000-32767 的随机高端口,ServiceLB 把入口换成 Service 自己声明的 80/443。代价是每个节点都要占住这个端口。

观测:

```bash
kubectl -n kube-system get ds | grep svclb-      # 每个 LoadBalancer Service 一个(svclb-<名>-<后缀>)
kubectl -n kube-system get ds <上面查到的名字> -o yaml | grep -B2 -A2 hostPort
kubectl get svc <name> -o jsonpath='{.status.loadBalancer.ingress}'
```

## 三、限制与根因

| 限制 | 根因 | 出路 |
| --- | --- | --- |
| 同端口全集群只能有一个 LB Service(实测:第二个 80 端口 LB Service 的 svclb Pod 在 144-146 无节点可落,EXTERNAL-IP 永远 Pending) | DaemonSet 要求每个节点占住该 hostPort;traefik 默认起 LoadBalancer Service,svclb-traefik 占死所有节点的 80/443 | 错开端口,或换 MetalLB |
| 入口就是节点 IP,节点宕机打到该 IP 的流量即断 | 无地址池、无 VIP、无 leader,EXTERNAL-IP 是节点真 IP | 要固定 IP/漂移则换 MetalLB(其 L2 VIP 有 leader 选举) |
| 只做四层 | 它只是把端口引进集群的一跳 | 七层归 ingress(traefik/ingress-nginx) |

LB 流量进来之后的 SNAT/conntrack 话题(externalTrafficPolicy、单源 64K、conntrack 表)是 kube-proxy 一侧的事,与前置的 LB 实现无关,已按 10 万连接压测展开,见 [plugins/metallb](../kubernetes/plugins/metallb/README.md)。

## 四、什么时候换 MetalLB

ServiceLB 够用的场景:实验与边缘集群、对外服务少、接受"节点 IP 即入口"、端口能与 traefik 错开。出现以下任一情况,就到了换 MetalLB 的时候(第 4 篇的实测判断:对外服务一多,内置优势被稀释):

- 要固定对外 IP(Grafana 固定 10.10.12.241 那类用法,RKE2 集群由 MetalLB 池分配)
- 80/443 已被 traefik 占死,还想多开对外入口
- 要节点宕机后的地址漂移
- 连接规模大到 L2 单 leader 成瓶颈(压测篇结论:多 LB IP 分散 leader,或上 BGP)

操作路径:所有 server 带 `--disable=servicelb` → helm 安装 MetalLB → 建 IPAddressPool + L2Advertisement,完整流程与 10 万连接压测见 [plugins/metallb](../kubernetes/plugins/metallb/README.md)。

上游还支持用 `svccontroller.k3s.cattle.io/enablelb=true` 节点标签把 svclb Pod 收敛到指定节点(可配合 `lbpool` 标签分池),本系列未验证,待实测。
