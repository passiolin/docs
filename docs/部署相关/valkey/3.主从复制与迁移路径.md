# 3. 主从复制与迁移路径

> **实测状态**:✅ 已实测 —— Valkey 自身复制、Valkey↔Redis 跨软件复制,2026-09-30。迁移路线结论全部有实测依据。

## Valkey 自身主从复制(与 Redis 无差异)

```bash
# 从库配置追加:
replicaof <主库IP> 6379
masterauth Valkey@2026

# 实测(6380 从 6379):
valkey-cli -p 6380 INFO replication | grep -E "^role|^master_link_status"
# role:slave / master_link_status:up
valkey-cli -p 6380 GET valkey:self-test    # native(同步到位)
```

哨兵、Cluster 的机制与 Redis 完全一致,部署直接照 [../redis/5.主从与哨兵.md](../redis/5.主从与哨兵.md) 与 [../redis/6.Cluster集群.md](../redis/6.Cluster集群.md)(把 redis-server/redis-cli 换名即可)。

## 跨软件复制实测(Redis 8 → Valkey:**不通**)

让 valkey 作为 redis 8.0 主库的从库(迁移最经典的"主从切换法"):

```
replicaof 10.10.12.118 6379
masterauth Redis@2026
```

实测 valkey 侧日志:

```
Primary replied to PING, replication can continue...          ← 握手成功
(Non critical) Primary does not understand REPLCONF VERSION    ← 小方言,无害
PRIMARY <-> REPLICA sync: Loading DB in memory
Failed trying to load the PRIMARY synchronization DB from disk ← 全量同步载荷装载失败
PRIMARY <-> REPLICA sync: Discarding the half-loaded data      ← 反复重试,master_link_status 永远 down
```

**根因与第 2 篇 RDB 互导失败同源**:全量同步传输的就是主库的 RDB 流,Redis 8 的 RDB v12 valkey 装不了。所以**协议兼容 ≠ 复制兼容**,跨软件复制被文件格式挡死。

## 迁移路线决策表(实测结论)

| 场景 | 路线 | 可行性 |
| --- | --- | --- |
| Redis ≤7.4 → Valkey | 复制法(valkey replicaof redis)→ 追平后切主 | 物理通道可用(RDB ≤v11;未在本环境实测 redis 7,依据是格式边界,迁移前重测) |
| Redis ≤7.4 → Valkey | 快照法(BGSAVE → 拷 dump.rdb → 起库) | 同上 |
| **Redis 8.x → Valkey** | 复制法/快照法 | **❌ 实测不通(RDB v12)** |
| Redis 8.x → Valkey | 逻辑迁移:redis-shake 等同步工具 / SCAN+DUMP-RESTORE 逐键搬运 / 双写切换 | ✅ 协议层全兼容(第 2 篇矩阵),按 key 量评估停写窗口 |

逻辑迁移注意:

- `DUMP/RESTORE` 的单键序列化跨版本容忍度好于 RDB 整库,但含新类型/新编码的 key 在目标端可能拒收,**先用抽样 key 验证**再全量;
- 迁移窗口用 `INFO replication` 的 master_link_status 与 `DBSIZE` 双指标确认追平,再切流量;
- 回切方案先写好(逻辑迁移是双向协议兼容的,回切成本可控——这是相比物理迁移唯一的安慰)。
