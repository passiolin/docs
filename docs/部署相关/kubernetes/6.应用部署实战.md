# 应用部署实战

把一个带状态的业务从零跑通:Deployment(探针+资源限额)→ PVC(local-path)→ Service → Ingress,全程在恢复后的三节点集群实测(2026-10-10/11)。示例以 nginx 充当业务镜像,换成任何 web 服务步骤一致;示例文件可直接 apply。

## 1. 存储先行:装 local-path

RKE2 v1.35 无预置 StorageClass(见第 5 篇),有状态应用上线前先装 provisioner。实测 v0.0.37:

```bash
curl -sfL -o /tmp/lp.yaml \
  https://raw.githubusercontent.com/rancher/local-path-provisioner/master/deploy/local-path-storage.yaml
kubectl apply -f /tmp/lp.yaml
kubectl patch storageclass local-path \
  -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
kubectl get pod -n local-path-storage   # 等 Running,镜像经 mirror 约 1-2 分钟
```

PVC 动态供给实测:PVC 从 Pending(WaitForFirstConsumer)到 Pod 调度后 Bound,卷落在调度节点的 `/var/lib/rancher/rke2/...`(local-path 配置的 helperPod 挂载路径),`kubectl get pvc` 出现 VOLUME 即成功。

## 2. 完整示例:Deployment + PVC + Service + Ingress

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-test
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web-demo
  template:
    metadata:
      labels:
        app: web-demo
    spec:
      containers:
      - name: nginx
        image: docker.io/library/nginx:alpine
        ports:
        - containerPort: 80
        resources:
          requests: {cpu: 50m, memory: 64Mi}
          limits: {cpu: 250m, memory: 128Mi}
        readinessProbe:
          httpGet: {path: /, port: 80}
          initialDelaySeconds: 3
          periodSeconds: 5
        volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: pvc-test
---
apiVersion: v1
kind: Service
metadata:
  name: web-demo
spec:
  selector:
    app: web-demo
  ports:
  - port: 80
    targetPort: 80
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-demo
spec:
  ingressClassName: nginx
  rules:
  - host: demo.k8s.lab
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-demo
            port:
              number: 80
EOF

# 写入页面并验证
kubectl exec deploy/web-demo -- \
  sh -c 'echo hi-from-$HOSTNAME > /usr/share/nginx/html/index.html'
curl -s -H "Host: demo.k8s.lab" http://10.10.12.141/
# 实测输出:hi-from-web-demo-79c5c8f755-5xq72
```

## 3. 入口怎么进来的(实测形态)

rke2-ingress-nginx 是 **DaemonSet + hostPort 80/443**,跑在每台节点上——没有任何 LoadBalancer/NodePort Service,流量从任意节点 IP 的 80 端口进来,由 Host 头路由到后端 Service。实测三个节点 IP 访问同一 Host 头,全部命中:

```bash
for n in 141 142 143; do curl -s -H "Host: demo.k8s.lab" http://10.10.12.$n/; done
```

配套含义:DNS 把 `*.k8s.lab` 解析到任一(或轮询全部)节点 IP 即完成接入;要做高可用入口,把节点 IP 换成 VIP(10.10.12.140)解析,或上 MetalLB 提供 LoadBalancer(见 plugins/metallb,待建)。测试阶段没有 DNS 时,`curl -H "Host: demo.k8s.lab"` 就是等价物。

## 4. local-path 的 RWO 语义(实测)

`replicas: 2` 且同挂一个 RWO PVC 时,两个副本全部调度到卷所在节点(实测都在 k8s-server-03);`scale` 到 3 依然同节点,不会因 RWO 拒绝调度——RWO 限制的是"一个节点",不是"一个 Pod"。推论:**local-path 适合单副本有状态应用;多副本共享数据请换 NFS(RWX)或应用层自带复制**,卷钉死单节点意味着该节点挂掉服务即中断。

## 5. 探针与空卷的坑(实测)

示例里 readinessProbe 指向 `/`,而 `/usr/share/nginx/html` 被 PVC 空卷覆盖——nginx 对不存在的 index 返回 **403**,探针持续失败,Pod 永远 `0/1 Running`,ingress 回 503。实测解法即示例第 2 步:部署后立刻写入 index.html;生产做法是应用启动时自产首页,或探针改用专门的 `/healthz` 路径。判断口诀:`0/1 Running` = 容器活着但探针不过,先看探针路径返回码,不是重启大法。

## 6. 日常操作速查

```bash
kubectl scale deploy web-demo --replicas=3      # 扩缩容(实测 RWO 同节点语义,见第 4 节)
kubectl set image deploy/web-demo nginx=nginx:1.27 && kubectl rollout status deploy/web-demo
kubectl rollout undo deploy/web-demo            # 回滚
kubectl logs deploy/web-demo -f --tail=50
kubectl delete ingress/web-demo svc/web-demo deploy/web-demo pvc/pvc-test
```
