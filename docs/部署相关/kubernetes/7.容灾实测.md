# 容灾实测

备份的价值在恢复。本篇记录 2026-10-10/11 一次完整的"真事故→快照全量恢复→对端重新加入"演练:calico IPPool 在节点加入时被连带删除、IPAM 瘫痪,最终用事故前的 etcd 快照把集群整体拉回。所有命令与输出均为实测。

## 1. 备份体系

RKE2 内置 etcd 快照,默认每小时整点执行、保留 5 份,落盘在 `/var/lib/rancher/rke2/server/db/snapshots/`;config.yaml 可改节奏(`etcd-snapshot-schedule-cron` / `etcd-snapshot-retention`)。手动留底:

```bash
rke2 etcd-snapshot save --name pre-upgrade
# 实测输出:Snapshot pre-upgrade-k8s-server-01-1791645676 saved.(单份约 17M)
```

两条纪律:**升级/变更前手动留一份**;快照目录与集群同机同盘,不算容灾,定期拷走(推 S3 的 `etcd-s3-*` 配置待实测)。

## 2. 事故实录:IPPool 消失,新 Pod 全部无法联网

**现象**:新 Pod 卡 `FailedCreatePodSandBox`,calico 报 `cannot find a qualified ippool`;`kubectl get ippools` 为空;老 Pod 凭旧 IP 继续跑,`calico-system` 里 Installation 对象带 deletionTimestamp 卡死,operator 日志反复 `Installation is terminating, skipping IP pool reconciliation`。

**根因链**:第 2 台起的 server 的 config.yaml 没写 `cni`,rke2 的本地包引导按默认部署 **rke2-canal** chart,与首台的 **rke2-calico** chart 形成两套 CNI 互删——canal 的安装/卸载循环连带删掉了 calico 的 Installation(CRD),operator 因"正在终止"拒绝重建 IPPool,IPAM 就此瘫痪。第一次事故发生在加入节点的时刻,快照恢复后又复发一次,直到三台配置对齐并清掉 canal chart 才根除。

**预防(写进流程)**:每台 server 的 config.yaml 都要写全 `cni` 与两个 CIDR,和首台严格一致;加入节点后 `kubectl get helmchart -n kube-system` 确认只有 `rke2-calico`、没有 `rke2-canal`。agent 不部署 CNI chart,不受此影响。

## 3. 全量恢复实录(cluster-reset)

适用:etcd 数据损坏、误删核心资源、CNI 体系瘫死且原地修不动。原则是把整个 etcd 卷回事故前快照,对端节点清数据重加入。

```bash
# 0. 留底当前状态(后悔药)
rke2 etcd-snapshot save --name pre-restore

# 1. 三台全部完整停止(只 systemctl stop 是"假停",见第 2 篇第 6 节)
systemctl stop rke2-server && /usr/local/bin/rke2-killall.sh

# 2. 在持有快照的节点(141)执行恢复,注意服务处于停止状态,直接跑二进制
rke2 server --cluster-reset \
  --cluster-reset-restore-path=/var/lib/rancher/rke2/server/db/snapshots/manual-test-k8s-server-01-1791641977
# 实测关键输出:
#   Cluster reset: backing up certificates directory to .../tls-<时间戳>
#   Managed etcd cluster membership has been reset ... Backup and delete
#   ${datadir}/server/db on each peer etcd server and rejoin the nodes

# 3. 先起恢复节点
systemctl start rke2-server          # 实测 8 秒后 Ready

# 4. 对端节点:按提示备份并删除 etcd 数据,再启动
mv /var/lib/rancher/rke2/server/db /var/lib/rancher/rke2/server/db.bak-$(date +%H%M)
systemctl start rke2-server
```

实测结果:141 恢复后 `default-ipv4-ippool` 随快照回来(事故前状态),142 清 db 后 8 分钟重新 Ready,etcd 三成员重新聚齐,新 Pod 正常拿到 Pod IP——IPAM 完全复活。

## 4. 恢复路上的两个坑(实测)

**残留 VIP 双占导致对端无法加入**:143 在事故前持有 VIP,killall 是 SIGKILL、kube-vip 没机会释放,地址残留在 ens18 上;141 起来后 kube-vip 又把 VIP 挂到自己身上——两台同持一个 IP,ARP 飘忽,143 bootstrap 时 `dial tcp 10.10.12.140:9345: connect: connection refused`。处置:残留节点上 `ip addr del 10.10.12.140/32 dev ens18`,并 `crictl stop` 它的 kube-vip 容器强制重新选主,bootstrap 立即通过。

**helm 卡死链的清理次序**:两套 CNI 互删会把 `helm-install/helm-delete` Job、HelmChart 对象、helm release secret 全部拖入僵死(典型报错:`release name check failed: cannot reuse a name that is still in use`、`Job/tigera-operator/tigera-operator-uninstall not ready. status: Failed`)。实测有效的次序:

```bash
kubectl delete secret -n kube-system sh.helm.release.v1.rke2-calico.v1   # 释放 release 名
kubectl delete deploy -n tigera-operator tigera-operator                 # 清旧 operator
kubectl patch helmchart rke2-canal -n kube-system --type=merge \
  -p '{"metadata":{"finalizers":[]}}'                                    # 解开卡终止的 chart
kubectl delete job -n kube-system helm-install-rke2-calico               # 清僵死安装 Job
systemctl restart rke2-server                                            # 包管理器重新装配
```

重装后全套校验:`kubectl get ippools`(Pool 在)、`kubectl get pods -n calico-system`(controller/3×node/typha 全 Running)、跑一个 busybox 拿 Pod IP、业务 ingress 可访问。

## 5. 故障分级与处置入口

| 级别 | 场景 | 处置 |
| --- | --- | --- |
| 单 Pod/负载 | 崩溃、探针失败 | 见第 6 篇第 5 节,别动集群 |
| 单节点故障 | 完整停机 → VIP 漂移(第 2 篇第 6 节),恢复后自动归队 | 无需人工干预 |
| CNI/IPAM 瘫痪 | 新 Pod 全部沙箱失败 | 先排 canal 冲突(第 2 节),原地修不动再进第 3 节全量恢复 |
| etcd 损坏/误删核心资源 | apiserver 起不来、资源大面积丢失 | 直接第 3 节 cluster-reset |
