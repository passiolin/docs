# 安装部署-集群

三台 server 加一个 VIP,etcd 3 副本、API Server 双活。本篇实测于 k8s-server-01/02/03(10.10.12.141/142/143)+ VIP 10.10.12.140(kube-vip v1.2.4),RKE2 v1.35.6+rke2r1,2026-10-10;路径是"先按第 1 篇装好单节点,再集群化",每一步都在这条升级路径上验证过。RKE2 的 server 节点默认不设污点、可跑业务 Pod,实验室规模不需要单独的 agent;要隔离时在 config.yaml 打开 `node-taint` 注释。

## 1. 拓扑

| 节点 | IP | 角色 |
| --- | --- | --- |
| k8s-server-01/02/03 | 10.10.12.141-143 | server(etcd + 控制面 + 业务) |
| 集群 VIP | 10.10.12.140 | kube-vip 承载,API Server 入口 |

VIP 选 DHCP 池外的地址并在路由器上静态绑定。agent(worker)的加入见第 6 节。

## 2. 单节点集群化:补 VIP 并轮换证书

单节点的 apiserver 证书里只有本机 IP;VIP 要进来必须先进 tls-san 再轮换证书,否则经 VIP 访问 API 报证书错误。

```bash
# /etc/rancher/rke2/config.yaml 的 tls-san 补一行
#   - 10.10.12.140
systemctl stop rke2-server
rke2 certificate rotate        # 实测输出:Successfully backed up certificates to .../tls-<时间戳>
systemctl start rke2-server

# 验证新证书含 VIP
openssl x509 -in /var/lib/rancher/rke2/server/tls/serving-kube-apiserver.crt -noout -text \
  | grep -A1 "Subject Alternative" | tail -1
# 实测 SAN:IP:10.10.12.141, IP:10.10.12.140, IP:127.0.0.1, ...
```

手工删除 server/tls/ 下的证书文件是危险操作,轮换一律走 `rke2 certificate rotate`。

## 3. kube-vip(三台 server 各一份)

kube-vip v1.x 的 release 不再附带二进制,manifest 直接用官方容器镜像生成。镜像经 mirror 先拉到本机 containerd,生成后把 image 字段改回 ghcr.io 原名(正式拉取走 registries.yaml 的 mirror):

```bash
CTR="/var/lib/rancher/rke2/bin/ctr --address /run/k3s/containerd/containerd.sock"
$CTR images pull ghcr.m.daocloud.io/kube-vip/kube-vip:v1.2.4
$CTR run --rm --net-host ghcr.m.daocloud.io/kube-vip/kube-vip:v1.2.4 kv \
  /kube-vip manifest pod --interface ens18 --vip 10.10.12.140 \
  --controlplane --arp --leaderElection > /tmp/kubevip-raw.yaml
sed 's|ghcr.m.daocloud.io/kube-vip/kube-vip|ghcr.io/kube-vip/kube-vip|' \
  /tmp/kubevip-raw.yaml > /var/lib/rancher/rke2/agent/pod-manifests/kube-vip.yaml
```

生成结果按 RKE2 修正两处,最终版见 [conf/kubevip.yaml](conf/kubevip.yaml):

1. v1.2.4 生成的清单挂载 kubeadm 路径 `/etc/kubernetes/admin.conf`,RKE2 改为 hostPath `/etc/rancher/rke2/rke2.yaml`;
2. v1.x 用 `vip_address` 时必须补 `vip_subnet: "32"`,否则 CrashLoop(实测报错 `vip_subnet must be set`)。

**存放位置是关键坑**:`agent/pod-manifests/` 才是 kubelet 静态 Pod 目录(与 etcd.yaml、kube-apiserver.yaml 同列)。放去 `server/manifests/` 会被 rke2 的 deploy controller 当成 API 对象创建,结果是一个被调度到单节点的普通 Pod——节点一挂就没了,HA 无效(实测踩过)。

改完清单后 pod 若在 CrashLoopBackOff,退避会拖住重启,force delete 立即生效:

```bash
kubectl delete pod -n kube-system kube-vip-k8s-server-01 --force --grace-period=0
```

验证(实测):三台各出现一个 `kube-vip-k8s-server-0N` 静态 Pod,leader 日志出现 `Successfully acquired lease` 与 `layer 2 broadcaster starting`,VIP 挂到 ens18:

```bash
kubectl get pods -n kube-system -o wide | grep kube-vip
ip -4 addr show ens18 | grep 10.10.12.140    # leader 节点上
ping -c1 10.10.12.140
```

## 4. 后续两台 server 加入

前置(系统参数、chrony)与第 1 篇相同;registries.yaml 每台必配。**config.yaml 必须写全 `cni` 与两个 CIDR,和首台严格一致**——实测教训:只写 server/token/tls-san 的极简配置会让 rke2 的本地包引导按默认部署 rke2-canal,与首台的 rke2-calico 两套 CNI 互删,直接把 IPPool 删瘫(全过程见第 7 篇第 2 节):

```yaml
# /etc/rancher/rke2/config.yaml
server: https://10.10.12.140:9345   # 经 VIP 注册;VIP 未起前可先写首台 IP
token: <TOKEN>
cni: calico
cluster-cidr: 10.42.0.0/16
service-cidr: 10.43.0.0/16
tls-san:
  - 10.10.12.140
  - 10.10.12.142                    # 本机 IP
```

安装与首台同一条命令(同版本),`systemctl enable --now rke2-server`。实测两台先后加入,Ready 各需 3-10 分钟(镜像拉取为主)。加入完成后核对 `kubectl get helmchart -n kube-system` 只有 rke2-calico、没有 rke2-canal。

## 5. 集群与 etcd 验证

```bash
kubectl get nodes    # 3 台 Ready,ROLES=control-plane,etcd
```

RKE2 v1.35 的 bin 目录不再带 etcdctl,etcd 镜像是 distroless(连 sh 都没有),健康检查直接 exec 二进制,证书已按同路径挂进 pod:

```bash
kubectl exec -n kube-system etcd-k8s-server-01 -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/var/lib/rancher/rke2/server/tls/etcd/server-ca.crt \
  --cert=/var/lib/rancher/rke2/server/tls/etcd/server-client.crt \
  --key=/var/lib/rancher/rke2/server/tls/etcd/server-client.key \
  member list -w table
# 实测:3 成员 started,PEER ADDRS 各自 10.10.12.14x:2380
```

经 VIP 的 API 通路:`curl -sk https://10.10.12.140:6443/readyz` 返回 401 即通(401 是认证层在应答,说明 TLS 与转发正常;readyz 本身需要认证)。

## 6. VIP 漂移实测(容灾前置)

完整停一台 server 的正确姿势是两条命令——只 `systemctl stop` 时 systemd 在 90 秒超时后放弃,containerd 的 shim 与宿主机网络的容器(API server、kube-vip)全部存活,unit 显示 inactive 但节点根本没停(实测踩过):

```bash
systemctl stop rke2-server
/usr/local/bin/rke2-killall.sh
```

实测(2026-10-10):141 完整停止后 20 秒内 VIP 漂到 03,经 VIP 的 API 全程可访问;141 重新 `systemctl start` 后 45 秒内回到 Ready,kube-vip 转为备选。非优雅停机(SIGKILL)时旧节点上可能残留 VIP 地址,新 leader 的免费 ARP 会把流量接管过来,残留等节点恢复后自清。

## 7. agent(worker)加入

```yaml
# /etc/rancher/rke2/config.yaml,见 conf/config-agent.yaml
server: https://10.10.12.140:9345
token: <TOKEN>
tls-san:
  - 10.10.12.140
node-label:
  - "node-type=worker"
```

安装命令换成 `INSTALL_RKE2_TYPE=agent`,服务名 `rke2-agent`。agent 不需要 server/manifests、etcd 等目录;registries.yaml 与系统前置照做,漏配 mirror 是 agent 拉不到镜像的头号原因(待实测,当前三节点无 agent)。

## 8. 集群化踩坑实录

| 现象 | 结论(2026-10-10 实测) |
| --- | --- |
| 经 VIP 访问 API 证书报错 | tls-san 没补 VIP 或没轮换证书;补后 `rke2 certificate rotate` |
| kube-vip CrashLoop: vip_subnet must be set | v1.x 用 vip_address 必须配 vip_subnet,见 conf/kubevip.yaml |
| kube-vip 挂载 admin.conf 不存在 | 生成器写的是 kubeadm 路径,RKE2 改挂 rke2.yaml |
| kube-vip 变成被调度的普通 Pod | 清单放错目录;静态 Pod 在 agent/pod-manifests/ |
| 改了静态 Pod 清单不生效 | CrashLoopBackOff 退避拖住重启,force delete pod |
| systemctl stop 后节点"假活" | shim 与容器存活,完整停止要加 rke2-killall.sh |
| host 上没有 etcdctl | v1.35 已移除,exec 进 etcd pod 直接调 etcdctl(无 sh,不能加 sh -c) |
| 新 Pod 全部沙箱失败: cannot find a qualified ippool | 加入节点没写 cni,canal 与 calico chart 互删把 IPPool 删了;见第 7 篇 |
| helm 报 release name still in use | 旧 release secret 未清;按第 7 篇第 4 节次序清理 |
