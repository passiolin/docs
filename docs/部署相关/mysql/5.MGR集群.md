# 5. MGR 集群(三台 docker 组网)

## 拓扑

```
mysql-1 10.10.12.115  PRIMARY   ─┐
mysql-2 10.10.12.116  SECONDARY  ├─ 组通信端口 33061(xcom 层),业务端口 3306
mysql-3 10.10.12.117  SECONDARY  ─┘
```

三台机器上的 docker daemon 互相无需感知——**集群是 MySQL 自己组的,docker 只是每台机器上的进程管理器**。配置分三层(见 [conf/](conf/)):

```bash
# 每台生成节点配置 = common + role-mgr + 节点差异(3 个参数)
./gen-node-conf.sh 10.10.12.115 115 /root/mgrconf && cp /root/mgrconf/my.cnf /data/mysql/conf/my.cnf
```

节点差异只有 `server_id` / `report_host` / `group_replication_local_address` 三项,由脚本注入。

## 关键前置:loose- 前缀不是习惯,是必需

role-mgr.cnf 里所有 `group_replication_*` 变量必须写 `loose-group_replication_*`。实测原因:**全新数据目录初始化(`mysqld --initialize`)时插件尚未注册,裸写插件变量直接中止初始化**:

```
[ERROR] [MY-000067] [Server] unknown variable 'group_replication_group_name=...'
[ERROR] [MY-010119] [Server] Aborting
```

(存量数据正常启动不走 initialize 路径,所以同样的配置"有时能起"——这个差异极其隐蔽。)

## 第一个节点:存量单机演进为引导节点

容器从 `-p 3306:3306` 切到 `--net=host`(MGR 的组通信和成员互访不再适合端口映射),数据原地保留:

```bash
docker rm -f mysql
cp /root/mgrconf/my.cnf /data/mysql/conf/my.cnf
docker run -d --name mysql --restart=always --stop-timeout=300 \
  --ulimit nofile=1000000 --net=host \
  --health-cmd="mysqladmin ping -h127.0.0.1 -uroot -p\"\$MYSQL_ROOT_PASSWORD\" --silent" \
  --health-interval=15s --health-timeout=5s --health-retries=10 \
  -v /data/mysql/data:/var/lib/mysql -v /data/mysql/conf:/etc/mysql/conf.d \
  -e TZ=Asia/Shanghai mysql:8.4
```

复制恢复账号 + 引导组:

```sql
-- 注意:8.4 权限关键字仍是 REPLICATION SLAVE(改名只改了语句,没改权限;
-- 实测 GRANT REPLICATION REPLICA 报 1064 语法错)
CREATE USER rpl_user@'%' IDENTIFIED BY 'Rpl@2026';
GRANT REPLICATION SLAVE, BACKUP_ADMIN ON *.* TO rpl_user@'%';   -- BACKUP_ADMIN 供 clone 供数
CHANGE REPLICATION SOURCE TO SOURCE_USER='rpl_user', SOURCE_PASSWORD='Rpl@2026'
  FOR CHANNEL 'group_replication_recovery';

-- 引导三行,只在建组第一次执行;bootstrap 严禁写进 my.cnf(双引导=脑裂)
SET GLOBAL group_replication_bootstrap_group=ON;
START GROUP_REPLICATION;
SET GLOBAL group_replication_bootstrap_group=OFF;
```

## 新节点加入:docker 环境的"三步成熟路径"

空节点直接 `START GROUP_REPLICATION` 会被拒,docker 环境要按下面顺序走:

```sql
-- ① 清掉 docker 首次初始化自带的本地 GTID(entrypoint 建 root 账号产生 5 条本地事务,
--    组内没有 → 报 "more executed transactions than those present in the group" 被拒)
RESET BINARY LOGS AND GTIDS;

-- ② 装 clone 插件(空节点与组内数据差距大,binlog 增量追不上时 MGR 自动改走克隆;
--    不装则报 "clone plugin is not present or active")
INSTALL PLUGIN clone SONAME 'mysql_clone.so';

START GROUP_REPLICATION;   -- ③ 触发克隆
```

克隆会把 donor 的完整数据目录拷过来,然后**必须重启 mysqld 完成切换**——docker 官方镜像里 mysqld 是 PID 1(无 supervisor),clone 的自动重启必然失败,实测报错:

```
[ERROR] [MY-013462] Clone shutting down server as RESTART failed.
[ERROR] [MY-013465] ... Error message: Restart server failed (mysqld is not managed by supervisor process)
```

这是预期内的,处置就两步:

```bash
docker restart mysql      # 数据其实已克隆落盘,重启即完成切换
docker exec mysql mysql -uroot -p'...' -e "START GROUP_REPLICATION;"   # 再入组,此时 GTID 已对齐
```

入组成功后 `replication_group_members` 三台全 ONLINE。

> 若在 super_read_only 状态下执行 INSTALL PLUGIN 会报 ERROR 1290——先 `docker restart` 清状态再操作。

## 验证清单(实测输出)

```sql
SELECT member_host, member_state, member_role FROM performance_schema.replication_group_members;
-- 10.10.12.115  ONLINE  PRIMARY
-- 10.10.12.116  ONLINE  SECONDARY
-- 10.10.12.117  ONLINE  SECONDARY

-- 从库只读由 MGR 自动维护:
SELECT @@read_only, @@super_read_only;         -- 1  1(SECONDARY 上)
-- 从库写入被拒:ERROR 1290 ... --super-read-only
```

写复制:主库 `INSERT` 后秒级出现在两台从库(实测 3 秒内)。

## 故障切换实测

`docker stop` 主节点 115(优雅停止,组内有序退组),实测时间线(从 117 日志):

```
14:34:13.973  Primary server with address 10.10.12.115 left the group. Electing new Primary.
14:34:13.983  A new primary with address 10.10.12.117 was elected.
              The new primary will execute all previous group transactions before allowing writes.
```

**选主耗时 10 毫秒**(优雅退组场景;硬故障(kill -9/断电)要等故障检测超时,典型多等数秒)。切换后:新主可写并正常复制;旧主回来后:

```bash
docker start mysql
# start_on_boot=OFF 的基线策略下,手动入组(变 SECONDARY):
docker exec mysql mysql -uroot -p'...' -e "START GROUP_REPLICATION;"
```

`group_replication_consistency=BEFORE_ON_PRIMARY_FAILOVER`(role-mgr.cnf 已设)保证新主接管前先补齐本地事务,客户端不会在切换瞬间读到旧数据。

## 整组冷启动 Runbook

三台全停后重启,`start_on_boot=OFF` 意味着没人会自动入组。顺序:

1. 任选一台(建议原 PRIMARY 或数据最新者)执行"引导三行"(bootstrap ON → START → OFF);
2. 其余两台各执行 `START GROUP_REPLICATION;`(不要 bootstrap);
3. 三台 ONLINE 后再放业务流量。

若把 `group_replication_start_on_boot` 改为 ON,单节点重启可自动回归,但**整组冷启依然需要人工引导第一台**——这项纪律不随参数消失。

## 已知坑汇总

| 坑 | 现象 | 解 |
| --- | --- | --- |
| 插件变量没加 loose- | 全新初始化 `unknown variable` 后 Aborting | role-mgr.cnf 全部 loose- 前缀 |
| 权限关键字想当然写 REPLICA | `GRANT REPLICATION REPLICA` 报 1064 | 8.4 仍写 `REPLICATION SLAVE` |
| docker 首启自带本地 GTID | 入组报"more executed transactions"(外层显示 ERROR 3092) | 入组前 `RESET BINARY LOGS AND GTIDS` |
| 没装 clone 插件 | "clone plugin is not present or active" | 各节点 INSTALL PLUGIN;donor 授权 BACKUP_ADMIN |
| mysqld 是 PID 1 | clone "Restart server failed (not managed by supervisor)" | 预期内:`docker restart` 后再 START |
| super_read_only 下动插件 | INSTALL PLUGIN 报 ERROR 1290 | 先 docker restart 清状态 |
| 首启初始化窗口发 SQL | Lost connection / runc ns 错误 | 等 healthy 且日志出现 2 次 ready 再操作 |
