# 8. 日常运维与排障

> **实测状态**:✅ 已实测 —— MySQL 8.4.11(docker 三节点 MGR + Router + exporter 环境),2026-09-30。慢日志样例、排障字典中的每条报错均来自本次实验环境实录。pt-query-digest / gh-ost 等外部工具流程标注"未实测"。

## 日常操作速查

```bash
docker logs -f mysql                        # error log(stderr)
docker exec mysql mysql -uroot -p'...'      # 进 SQL
docker exec mysql mysql -uroot -p'...' -e "SHOW REPLICA STATUS\G"   # 复制状态(MGR 成员视角用 M06 查询)
docker exec mysql du -sh /var/lib/mysql     # 数据目录粗估(精确用 M09 带 stats_expiry=0)
```

## 慢查询治理(M04)

基线已开慢日志(第 2 篇:long_query_time=1)。**文件位置实测**:`@@slow_query_log_file = /var/lib/mysql/<主机名>-slow.log`——注意 `--net=host` 模式下容器**继承宿主机名**(实测生成 `mysql-1-slow.log`,不是容器 ID),所以日志名天然可定位到机器。

实测样例(值得知道:管理命令也会被记录):

```
# Time: 2026-09-30T15:08:01.700056Z
# User@Host: root[root] @ localhost []  Id:  1778
# Query_time: 2.546909  Lock_time: 0.000000 Rows_sent: 0  Rows_examined: 0
SET timestamp=1790780682;
START GROUP_REPLICATION;          ← 连组复制启动都超 1s 被记
```

治理路径:先用 `long_query_time=1` 收集基线,再逐步收紧到 0.5;聚类分析用 pt-query-digest(**未实测**,工具文档:https://docs.percona.com/percona-toolkit/pt-query-digest.html );改造前先 `EXPLAIN`,无索引大表禁止直接变更。

## 大表 DDL(原则,工具未实测)

生产大表加列/改类型的选项:MySQL 8.0+ 的 `ALGORITHM=INSTANT`(加列秒级,优先试)、`INPLACE`(不锁写但耗资源)、`COPY`(锁表,禁止);不满足 INSTANT/INPLACE 条件的大表用 gh-ost / pt-online-schema-change 在低峰执行。任何 DDL 在 MGR 里会全组复制,先在一个从库演练(可直接用实验机克隆环境)。

## 排障字典(全部来自本次实测)

按"现象 → 根因 → 处置"组织,这是本文的核心资产:

| 报错/现象 | 根因 | 处置 |
| --- | --- | --- |
| `ERROR 3032 server is currently in offline mode` | 成员出错退组时 MGR 置 offline_mode,重入组后**不自动清**(root 能连、普通账号/exporter 全拒,易误判为"库挂了") | `SET GLOBAL offline_mode=OFF;` |
| `ERROR 3092 not configured properly to be an active member` | 外层泛化错误,看日志分三种:① unknown variable(初始化时插件变量没 loose-);② more executed transactions(GTD 超前);③ super_read_only 未清 | 对应:加 loose- 前缀 / RESET BINARY LOGS AND GTIDS 或走 clone / 重启清态 |
| `more executed transactions than those present in the group` | docker 首次初始化自带 5 条本地 GTID;或成员退组期间组内少了它的视图事务 | 前者:入组前 RESET;后者:由 GTID 最全的节点重建组(见第 5 篇) |
| clone: `Restart server failed (mysqld is not managed by supervisor process)` | mysqld 是容器 PID 1,clone 无法自动重启 | 预期内:`docker restart` 后再 `START GROUP_REPLICATION`(数据已克隆落盘) |
| `clone plugin is not present or active` | 节点没装 clone 插件 / donor 没授权 | 各节点 `INSTALL PLUGIN clone SONAME 'mysql_clone.so'`;donor 账号加 BACKUP_ADMIN |
| recovery: `Authentication requires secure connection` | InnoDB Cluster 收编后恢复账号要求 TLS | `SET GLOBAL group_replication_recovery_use_ssl=ON`(已固化 role-mgr.cnf) |
| `ERROR 3139 CHANGE REPLICATION SOURCE ... cannot be performed` | 对 GR 托管通道用 CHANGE REPLICATION SOURCE 改 SSL | GR 通道的 SSL 由 `group_replication_recovery_use_ssl` 插件变量管 |
| `ERROR 1290 --super-read-only` | 向 SECONDARY 发写/DDL,或插件卡态时执行管理操作 | 业务写走 6446;卡态先 `docker restart` |
| 两个 SECONDARY 同时 RECOVERING 不动 | 互相等 donor,组内无 ONLINE 成员 | 全部 STOP,由 GTID 最全者重新引导(第 5 篇 runbook) |
| exporter `mysql_up 0` 但 mysqld 活着 | 十有八九是 offline_mode(见第一行);其次查 exporter.cnf 权限(uid 65534) | 见对应条目 |
| 配置"改了没生效" | SET GLOBAL 不持久 / mysqld-auto.cnf 漂移覆盖 my.cnf | 见第 2 篇漂移纪律;`cat /var/lib/mysql/mysqld-auto.cnf` 非 `{"Version": 2}` 即有漂移 |
| `information_schema` 容量"不变化" | stats 缓存 86400s | `SET SESSION information_schema_stats_expiry=0`(第 2 篇实测 96→192) |
