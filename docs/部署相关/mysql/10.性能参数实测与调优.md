# 10. 性能参数实测与调优(sysbench)

## 实测环境与口径

第 2 篇的 22 项决策参数,大部分值靠经验定——"专机内存 50~70%"、"SSD 起步 2000"这类规则没有本机数字背书。2026-11-09 笔者搭了一台一次性台架,把主要性能参数逐个过 A/B,本文是全部数据与裁决。

台架:PVE 虚机 mysql-bench(vmid 119,4C / 8G / 40G 盘,Ubuntu 26.04 LTS,docker 29.1.3),盘落 local-lvm(原生 NVMe,非 hddvm 的 dm-cache 路径);MySQL `mysql:8.4` 镜像实测 **8.4.13**(比第 1 篇的 8.4.11 新两个小版本);压测 sysbench 1.0.20 与 mysqld 同机共置——4C 生产形态下压测客户端与数据库抢 CPU 是真实场景的一部分。

母机:Intel E5-2698B v3(16C32T,2.0GHz,Haswell),同机还有路由、开发机等在跑的 VM。这是共享宿主机的噪声地板,两种表现都实测到了:同配置背靠背复测漂移仅 0.4%(write_only 两轮),跨时段却出现过 ±17%(read_only,E1 与 E7 各跑一次 6G)。所以本文的每条裁决只采信**同窗口背靠背**的数据,跨时段差异只当线索。

方法口径,四条:

1. **数据集 24 表 × 100 万行 ≈ 6.3G**(sbtest 标准表 + k 二级索引),刻意大于所有参测 buffer pool 挡位,让命中率曲线拉得开;`--rand-type=uniform` 无热点访问——生产的热集通常远小于全量数据,这里的命中率读数偏悲观;
2. **每轮同一起点**:写 conf → `docker restart mysql`(静态参数动态参数一视同仁)→ 健康等待 → 60s 预热 → 180s(持续写组 300s)计时,`--report-interval=10`;吞吐取间隔汇报后 2/3 时段的 TPS 中位数,延迟取最终汇总 p99;
3. **每轮采集** `SHOW GLOBAL STATUS` 前后增量(buffer pool 命中率、物理读、Created_tmp_disk_tables、Threads_created)与 `iostat -x`;
4. **PVE 盘参数 aio=native**(踩坑见文末,这一项不改,下面所有数字作废——它把 4K 随机 IOPS 钉死在 7k)。

复现用的脚本与逐轮原始输出都留在台架上(`/root/bench/`),关键脚本贴在文末复现一节。

## buffer pool:修复 IO 瓶颈后,曲线才显形

读密集(read_only,8 线程)全挡位:

| buffer pool | 稳态 TPS | 命中率 | 物理读(240s) | read_write 稳态 TPS | rw p99(ms) |
| --- | --- | --- | --- | --- | --- |
| 256M | 490 | 83.6% | 229 万 | 250 | 112.7 |
| 512M | 502 | 84.7% | 215 万 | — | — |
| 1G | 523 | 86.1% | 198 万 | 270 | 94.1 |
| 2G | 565 | 89.1% | 163 万 | — | — |
| **4G(基线)** | **667** | 95.3% | 76 万 | **358** | **55.8** |
| 6G | 757 | 98.5% | 26 万 | — | — |

三个读数:

- **256M 挡的瓶颈在盘不在缓存**:83.6% 命中率,物理读 9433 次/秒——uniform 随机访问下 NVMe 的有效 IOPS 天花板顶住了吞吐,不是"InnoDB 慢";
- **命中率不是线性换吞吐的**:512M→1G 只 +4%,2G→4G +18%——命中率 89%→95% 这一段,每 1 个百分点买的吞吐最多,因为漏掉的页从 60 万/4 分钟降到 33 万/4 分钟,前台等待是乘在尾部延迟上的(rw p99 从 94ms 降到 56ms);
- **6G 挡的读收益在 E8 背靠背复测中 +12% 稳定复现**(轮内漂移 0.5%;但跨时段出现过 -3% 的噪声孤例,见终裁一节),写收益同样稳定为正。

裁决:8G 专机的 buffer pool 从 4G 提到 6G(内存占比 74%),读 +12%、写 +7~14%(终裁一节 E8 背靠背确认),内存余量约 1G,兜得住 OS + docker + mysqld 非池开销(实测连续跑 4 小时无 OOM、无 swap)。基线模板同步更新,注释里写明这条曲线;"50~70%"经验上限在这台机器上被实测收益顶破,但换机器要按公式重算:`总内存 − buffer pool ≥ OS(~500M) + docker(~200M) + mysqld 非池(~800M) + 每连接 × max_connections`。

## redo 容量:非瓶颈,1G 是保险不是性能

写密集(write_only,8 线程,双1),只动 `innodb_redo_log_capacity`:

| redo 容量 | 稳态 TPS | p99(ms) |
| --- | --- | --- |
| 100M(镜像默认) | 800 | 45.0 |
| 512M | 839 | 44.2 |
| 1G(基线) | 832 | 44.2 |
| 4G | 819 | 45.0 |

四挡挤在 ±2.4% 里,就是噪声。约 850 TPS 的写入强度远没到让 1G redo 出现 checkpoint 压力的量级(经验公式:redo 写入速率 × 撑得住的突发时长 < 容量)。基线 1G **维持**,但第 2 篇给它写"写密集 1G~4G"的理由要修正:1G 的价值是给突发写入留缓冲、把 checkpoint age 钉在安全水位,不是吞吐;性能敏感场景加 redo 在这个强度下买不到东西。

## 双1 的价格标签

`(innodb_flush_log_at_trx_commit, sync_binlog)` 四组合,write_only 8 线程:

| 组合 | 稳态 TPS | 相对双1 | 语义 |
| --- | --- | --- | --- |
| **(1,1) 双1 基线** | **840** | — | 每次提交 redo+binlog 各一次 fsync,不丢已提交事务 |
| (2,1) | 906 | +8% | redo 每 秒一次 fsync,崩溃丢最多 1 秒事务 |
| (1,0) | 986 | +17% | binlog 不主动 fsync,崩溃靠 OS 缓存,主从可能漂移 |
| (2,0) | 1314 | +56% | 两边都不管,崩溃可能丢一段已提交事务 |

这台 NVMe 上双1 的完整价格是 **36%**(1314 vs 840)。第 2 篇"别动"的判断维持,现在有定价:性能敏感场景松到 (2,1) 只换 8%,却把 RPO=0 放掉了——不值。真要吞吐,该做的是升级硬件或改架构,不是松刷盘。

## io_capacity:越激进刷脏,越慢

持续写 300s(write_only),只动 `innodb_io_capacity/_max`:

| 挡位 | 稳态 TPS | p99(ms) |
| --- | --- | --- |
| 200 / 2000(官方默认) | 864 | 41.1 |
| **2000 / 4000(基线)** | **828** | 44.2 |
| 4000 / 8000 | 790 | 47.5 |

单调反着排:io_capacity 越大,后台刷脏越激进,跟前台抢 I/O,吞吐反而越低——这个写入强度下根本不需要那么急。基线 2000/4000 **维持**(居中,突发期把脏页压下去的能力比默认 200 强),但"SSD 就该调大"的直觉在这台机器上没有数据支撑,档位间差异 -5%~-9%,属于"选哪个都不痛"的参数,不值得为此返工线上配置。

## 连接与线程:饱和点在 32~64,建连省 1ms

read_write 线程扩展曲线(基线 conf):

| 线程数 | 稳态 TPS | avg(ms) | p99(ms) |
| --- | --- | --- | --- |
| 4 | 258 | 15.5 | 46.6 |
| 8 | 345 | 22.9 | 66.8 |
| 16 | 429 | 37.3 | 110.7 |
| 32 | 476 | 66.6 | 173.6 |
| 64 | 493 | 129.8 | 297.9 |
| 128 | 498 | 256.9 | 549.5 |

4 个 vCPU 在 32 线程后吞吐封顶(493→498,2%),延迟代价却线性涨:64 线程 avg 130ms 是 8 线程的 5.7 倍。**这台机器的并发甜蜜点在 8~16 线程**,应用连接池按这个配;max_connections=500 是给连接风暴留的保险丝,不是给业务并发用的配额,维持。thread_cache_size=32 也够用(最高峰值轮次 Threads_created 增量 214,复用充足)。

`skip_name_resolve` ON→OFF 各测 500 次独立建连(容器内客户端 → 容器 eth0 IP,走真实反查路径):ON 每连接 8ms,OFF 7ms,省 1ms(12%)。连接池长连接场景无感,短连接高频场景有感。基线 ON 维持,代价是账号 host 全用 IP 段(第 3 篇纪律)。

**附带实测出一个容量规划坑**:128 线程 × 24 表直接 ERROR 1461 `Can't create more than max_prepared_stmt_count statements (current value: 16382)`。16382 ÷ 24 表 ÷ 每表 9 条 ≈ 76 个并发连接就会撞线——max_connections 定 500 的机器,如果应用是重预编译风格(ORM 池每个连接挂几十条 stmt),这个默认值比连接数先爆。巡检 M02 看连接利用率之外,Error 1461 出现率也该看一眼。

## tmp_table_size:64M 挡不住大聚合,按会话提挡

自写负载:400 万行表 `SELECT g, COUNT(*), SUM(id) ... GROUP BY g`(g 基数约 98 万,聚合临时表含哈希摊销约 60~90MB),10 次取总耗时:

| tmp_table_size / max_heap_table_size | 10 次总耗时 | Created_tmp_disk_tables |
| --- | --- | --- |
| 16M(官方默认) | 196s | 11(每查询落盘) |
| **64M(基线)** | **178s** | **11(同样落盘!)** |
| 256M | 49s | 0(全内存) |

64M 这个基线值在真实聚合面前**刚刚不够**:哈希表摊销后峰值 ~62MB 越线,照落盘。裁决:全局维持 64M(它是每会话上限,256M × 高并发会话是内存放大,反面教材那一类);分析型大查询用会话级覆盖 `SET SESSION tmp_table_size=256M; SET SESSION max_heap_table_size=256M;`——这正是第 2 篇"每连接乘数保持默认、按会话覆盖"哲学的正向应用。判据用现成的:`Created_tmp_disk_tables` 增长快 = 有查询在落盘,拿 `EXPLAIN` 找到它再决定给谁提挡。

## 终裁 A/B 与调优参数集

基线 conf(4G)与调优 conf(唯一变更:buffer pool 6G)背靠背:

| 场景(8 线程) | 基线 4G(E0) | 调优 6G(E7/E8) | 差 |
| --- | --- | --- | --- |
| read_only | 666 | 747~748(E8 两轮) | **+12%** |
| read_write | 339 | 386 | **+14%** |
| write_only | 844 | 903 | **+7%** |

read_only 的 6G 收益在 E1(+13%)与 E7(-3%)两次测量间打架,补了一轮背靠背交替复测(E8,4G/6G 各两轮,同窗口):

| 轮次 | 4G 稳态 TPS | 6G 稳态 TPS | 差 |
| --- | --- | --- | --- |
| r1 | 668 | 747 | +11.7% |
| r2 | 665 | 748 | +12.3% |

6G 的读收益 +12% 两轮复现(轮内漂移 0.5%),E7 那次 646 判定为宿主机噪声孤例。三个场景的结论合起来:**6G 对读 +12%、写 +7~14%,全部稳定为正**。

**调优参数集最终只动一个 MySQL 参数**:

```cnf
# ---------- 一、内存与 InnoDB(实测修订,2026-11-09,第 10 篇) ----------
# 8G 专机:6G(74%)实测读 +12%、写 +7~14%;换机器按文末公式重算,余量不足回 4G
innodb_buffer_pool_size = 6G
```

其余参数全部维持基线,各自拿到了定量背书:redo 1G(非瓶颈,保险)、双1(RPO=0 定价 36%)、io_capacity 2000/4000(突发兜底)、max_connections 500(风暴保险丝)、thread_cache 32、skip_name_resolve ON(1ms/连接)、tmp_table 64M(大查询会话级 256M)。

真正的大头不在 MySQL 里,在 PVE:见下一节。

## 踩坑:aio=io_uring 把 4K 随机 IOPS 钉死在 7k

E1 第一轮跑完,256M 挡只比 4G 慢 17%——命中率高就是数据集 6.3G、池只有 256M,物理读该是百万级,17% 的差距对不上。fio 五件套一测,存储层露馅:

| fio(4G 文件,O_DIRECT) | io_uring(PVE 默认) | aio=native |
| --- | --- | --- |
| 4K 随机读 qd1 | 6.9k IOPS | 7.2k IOPS |
| **4K 随机读 qd32** | **7.0k IOPS** | **74.4k IOPS(10.6 倍)** |
| 4K 随机写 qd32 | 14k IOPS | 67.9k IOPS |
| 顺序读/写 1M qd8 | 616 / 580 MB/s | — |

qd1 和 qd32 一个数,说明瓶颈在串行的提交路径而不是盘;宿主机上对同一 thin 池直测独立 LV,4K 随机写 qd32 有 103k IOPS——盘没问题,qemu 的 io_uring 引擎在这套内核 + LVM-thin + virtio-scsi 栈上出了性能罚。`qm set` 换 `aio=native` 后 MySQL 全部数字抬升:read_only +17%(571→666)、read_write +15%(294→339)、write_only +30%(648→843)。改之前跑的 E0/E1 全部作废重测,旧数据留在台架 `results_io_uring/` 里对照。

三个教训:

1. **测 IOPS 必须先让数据真的落盘**。fio 对 thin-LVM 上未分配的块读,得到的是 dm-thin 零快路径的假 IOPS——笔者第一次诊断就吃了个 88k 的假数(实为 trim 后未分配块秒回零),[PVE 第 2 篇](../pve/2.存储性能实测.md)口径一节警告过的坑换了个形态再咬一口;
2. **qd1 == qd32 就是串行瓶颈指纹**,先怀疑虚拟化 I/O 路径(qemu aio 模式、单 iothread),别急着怪盘;qemu 实际参数看进程 cmdline 的 `-blockdev` JSON(`"aio":"io_uring"`),`qm config` 里不写就是不显式、走默认;
3. [PVE 第 4 篇](../pve/4.盘参数性能实测.md)在 ZFS 时代就实测过 io_uring 性能罚并把 tankvm 全量改了 threads;2026-10 存储迁移到 LVM+dm-cache 后这条配置**没有跟过去**,新 VM 默认又落回 io_uring。现网 jm-* 系列虚机的盘全部吃这个罚,迁移账要单独算。

## 复现步骤

台架:克隆一台干净 Ubuntu 26.04 VM(4C/8G/40G)或按第 1 篇装 docker;`qm set <vmid> --scsi0 ...,aio=native` 先行。

```bash
# 依赖(阿里云源,101 克隆体的 tuna 源 403)
apt-get install -y docker.io sysbench fio
# docker 镜像加速(daocloud)后拉镜像
docker pull mysql:8.4
# 目录与基线 conf(仓库 conf/common.cnf)
mkdir -p /data/mysql/{data,conf}
# 第 1 篇的 docker run 命令启动,容器名 mysql,root 密码自定

# 建压测账号
docker exec mysql mysql -uroot -pXXX -e "CREATE DATABASE sbtest; \
  CREATE USER 'sbtest'@'%' IDENTIFIED BY 'sbtest'; GRANT ALL ON sbtest.* TO 'sbtest'@'%';"

# 灌数(24 表 × 100 万行;先 SET GLOBAL innodb_redo_log_capacity=4G 加速,完事重启回落)
sysbench oltp_common --db-driver=mysql --mysql-host=127.0.0.1 --mysql-user=sbtest \
  --mysql-password=sbtest --mysql-db=sbtest --tables=24 --table-size=1000000 --threads=8 prepare
```

单轮测试的驱动逻辑(`run_test.sh`,完整脚本在台架 `/root/bench/scripts/`):写 conf(基线 + KEY=VAL 覆盖)→ `docker restart mysql` → 等健康检查 → 60s 预热 → `--report-interval=10` 计时 → 前后抓 `SHOW GLOBAL STATUS` 与 `iostat -x`。实验组就是 run_test 的参数序列,本文九组实验共 40 余轮,单机顺序跑完约 3 小时。

分析侧注意:`information_schema` 的表统计有 86400s 缓存,核对行数/索引前先 `SET SESSION information_schema_stats_expiry=0`(第 2 篇的坑,这次在核对索引时又踩了一遍);sysbench 灌数日志里"Creating a secondary index on X"是**开始**不是完成,判断是否跑完看进程不在 + 行数核对。

## 已知坑

| 坑 | 现象 | 处置 |
| --- | --- | --- |
| PVE 盘 aio=io_uring(默认) | 4K 随机 qd32 钉死 7k IOPS,MySQL 吞吐 -15~30% | `aio=native`,现网 VM 盘全部要查一遍 |
| thin-LVM 假 IOPS | fio 读未分配块秒回零,88k"假满分" | 测前先 O_DIRECT 写满文件,别 trim |
| max_prepared_stmt_count=16382 默认 | 高并发 × 多表预编译 ERROR 1461 | 动态调大;或按"每连接 stmt 数 × 连接数"重估 |
| tmp_table_size 64M 对大聚合不够 | Created_tmp_disk_tables 增长,聚合慢 3.6 倍 | 会话级提到 256M,全局不动 |
| 跨时段噪声 ±17% | 同配置不同时段读数漂移 | 裁决只信同窗口背靠背;重要结论跑两轮 |
