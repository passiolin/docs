# 6. MySQL Router(访问层)

> **实测状态**:✅ 已实测 —— MySQL Router 8.4(镜像 `container-registry.oracle.com/mysql/community-router:8.4`),双实例部署于 mysql-1 / mysql-2,2026-09-30。读写口路由、穿 Router 的故障切换、双实例并发验证完成。报错与时间线摘自实测。

## 定位

Router 是 MGR 对应用的**稳定入口**:6446 永远指向当前主(读写),6447 自动轮询从库(只读)。主挂了应用不用改连接串,Router 根据集群元数据自动把 6446 切到新主。生产至少部署**两个实例**(本文部署在 115/116),避免访问层自身单点。

## 前置:把 MGR 收编为 InnoDB Cluster

Router 的动态路由依赖 InnoDB Cluster 元数据(裸 MGR 没有),用容器里自带的 mysqlsh 收编(adopt,不影响数据和业务):

```bash
# 注意:密码里的 @ 必须写成 %40,否则 URI 解析报 Illegal character;
# 分离参数形式(-u/-p/-h)实测会丢密码,URI 编码形式最稳
docker exec mysql mysqlsh "root:Root%402026@127.0.0.1:3306" --js -e "
var c = dba.createCluster('prod', {adoptFromGr: true});
c.status();"
# 实测输出:A new InnoDB Cluster will be created based on the existing
# replication group ... Cluster successfully created based on existing replication group.
```

**收编的副作用(实测踩坑,重要)**:收编会为每个成员创建 `mysql_innodb_cluster_<id>` 账号并**重置 distributed recovery 凭据**,这些账号要求安全连接。此后任何成员重新入组,恢复通道若没开 TLS 会报:

```
Replica I/O for channel 'group_replication_recovery': Error connecting to source
'mysql_innodb_cluster_117@10.10.12.115:3306' ... Authentication plugin
'caching_sha2_password' reported error: Authentication requires secure connection
```

修复 = 给恢复通道开 SSL(插件变量,不是 `CHANGE REPLICATION SOURCE ... SOURCE_SSL=1`——后者在 GR 托管通道上实测报 ERROR 3139):

```sql
SET GLOBAL group_replication_recovery_use_ssl = ON;   -- 即时生效
-- 持久化已写入 conf/role-mgr.cnf:loose-group_replication_recovery_use_ssl = ON
```

不开 SSL 的连锁反应很隐蔽:重入组的成员恢复失败 → 退组 → 若恰好剩下两个 RECOVERING 成员会互相等 donor 卡死。处置顺序见第 5 篇"整组冷启动"。

## 部署 Router

**镜像来源**:daocloud 加速器对 `mysql/mysql-router` 仓库 403(实测),改用 Oracle 官方仓库直拉:

```bash
docker pull container-registry.oracle.com/mysql/community-router:8.4   # 实测 354MB
```

该镜像由环境变量驱动(entrypoint 自动 bootstrap 后启动),注意 **`MYSQL_INNODB_CLUSTER_MEMBERS` 是成员数量(3),不是 IP 列表**——传列表会把它的等待脚本整出算术错误(实测):

```bash
docker run -d --name mysql-router --restart=always --net=host \
  -e MYSQL_HOST=10.10.12.115 -e MYSQL_PORT=3306 \
  -e MYSQL_USER=root -e MYSQL_PASSWORD='Root@2026' \
  -e MYSQL_INNODB_CLUSTER_MEMBERS=3 \
  -e MYSQL_CREATE_ROUTER_USER=0 \
  container-registry.oracle.com/mysql/community-router:8.4
# 第二个实例在 116 上:MYSQL_HOST 换成 10.10.12.116,其余相同
```

启动后监听 6446(RW)/ 6447(RO)/ 6448 / 6449(X 协议)。日志确认拓扑识别:

```
metadata_cache INFO ... Metadata for cluster 'prod' has 3 member(s), single-primary:
    10.10.12.117:3306 / 33060 - mode=RW
    10.10.12.115:3306 / 33060 - mode=RO
    10.10.12.116:3306 / 33060 - mode=RO
```

## 路由验证(实测输出)

```bash
docker run --rm mysql:8.4 mysql -h10.10.12.115 -P6446 -uroot -p'...' -N -e "SELECT @@report_host, @@read_only;"
# router@115 6446(RW) → 10.10.12.115  0      (指向主)
# router@115 6447(RO) → 10.10.12.116  1      (轮询到从)
# router@116 6446(RW) → 10.10.12.115  0
# router@116 6447(RO) → 10.10.12.117  1
```

注意测试客户端用 `docker run --rm mysql:8.4` 时,`-h` 必须写宿主机 IP——客户端容器里的 127.0.0.1 是它自己(实测踩坑)。

## 穿 Router 的故障切换(实测)

`docker stop` 当前主 117(14:48:08 发起,含优雅退组握手),Router 侧时间线:

```
14:48:26 metadata_cache WARNING ... could not establish a connection to cluster through 10.10.12.117:3306
14:48:26 metadata_cache INFO ... 10.10.12.115:3306 / 33060 - mode=RW   ← 拓扑已更新
```

发起停止后约 18 秒(其中大部分是优雅停机的退组握手),6446 已指向新主,客户端**重连即可写**(连接本身会断,应用侧要有重试)。选举本身是毫秒级(第 5 篇实测 10ms),Router 的元数据刷新间隔决定感知延迟。

## 应用接入建议

- 连接串带两个 Router 地址(JDBC 多 host failover 或前置 LVS/DNS),如 `jdbc:mysql://10.10.12.115:6446,10.10.12.116:6446/appdb`——单个 Router 实例挂掉时无缝;
- 写走 6446,读走 6447;**6447 读到的是从库,存在复制延迟**,强一致读(写后立读)走 6446;
- Router 是无状态转发,可以随手 `docker rm -f` 重建,不影响集群数据。

## 已知坑汇总(全部实测)

| 坑 | 现象 | 解 |
| --- | --- | --- |
| daocloud 拒绝 router 仓库 | pull 403 Forbidden | 用 Oracle 官方仓库镜像 |
| 密码带 @ | mysqlsh "Illegal character [@]" / 参数形式丢密码 | URI 里编码为 %40 |
| MEMBERS 传成 IP 列表 | entrypoint 算术错误死循环等待 | 传数量 3 |
| 客户端 -h 127.0.0.1 | 容器内 127.0.0.1 非宿主机,111 拒连 | 用宿主机 IP |
| 收编后成员重入组失败 | recovery 报 "requires secure connection" | `group_replication_recovery_use_ssl=ON`(role-mgr.cnf 已固化) |
| 误用 CHANGE REPLICATION SOURCE 改 GR 通道 | ERROR 3139 | GR 通道的 SSL 由插件变量管 |
