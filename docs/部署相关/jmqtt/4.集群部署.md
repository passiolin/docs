# 4. 集群部署

## 拓扑与共享件

```
node-1 (jmqtt-1/137) ─┐
node-2 (jmqtt-2/138) ─┤─→ Redis(137,注册表 jmqtt:admin:nodes + 持久会话 + 离线队列)
                      └─→ Kafka(128,总线 topic jmqtt-cluster,每节点独立 group.id 广播)
```

节点完全对称、无 leader,也没有 MGR 式选主或 KRaft 式多数派:元数据全在 Redis/共享件,共享件活 = 集群活,不存在脑裂窗口。

## 部署差异(相对第 1 篇单机)

1. Redis 对集群可达:bind 0.0.0.0 + requirepass(单机形态的 127.0.0.1 不再适用);
2. 每节点 `JMQTT_ID` 唯一(node-1/node-2),其余 env 一致;
3. **镜像分发**:save→scp→load(实测管道直传丢内容,见第 1 篇);
4. 共享 Redis 的 key-prefix 两侧(broker/admin)一致。

## 注册与验证(实测输出)

```bash
docker exec jmqtt-redis redis-cli SMEMBERS jmqtt:admin:nodes
# 1) "node-1"
# 2) "node-2"
```

## 跨节点路由实测(核心)

订阅者连 **node-2**,发布到 **node-1**:

```
node-1 日志:PUBLISH → Kafka producer(jmqtt-cluster topic,key=MQTT 主题保序)
node-2 日志:总线消息投递: from=node-1 topic=lab/cluster/msg 本节点投递=1
node-2 订阅者:收到 cross-node-via-kafka ✅
```

消息面语义:跨节点 pub/sub 全量经 Kafka 广播;`broadcast-filters` 可收敛范围(配合 admin 的"跨节点订阅重叠检查"功能,避免静默不到)。

## 节点宕机自治(实测)

`docker stop node-1`:node-2 独立收发正常(survivor-ok)——节点无状态依赖对等体,共享件(Redis/Kafka)在即服务在。node-1 回归后自动重新注册(admin nodes 恢复两条)。**容量规划看共享件**:Redis/Kafka 的可用性就是集群的可用性,它们分别按 [redis 哨兵](../redis/5.主从与哨兵.md)与 [kafka RF=2](../kafka/3.参数基线与配置模板.md) 的基线做。
