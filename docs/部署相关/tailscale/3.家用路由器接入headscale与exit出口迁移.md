# 家用路由器接入 headscale 与 exit 出口迁移

家用网关(移动 AX3000,kwrt 25.12)以 `kwrt-gw` 加入笔者的自建 tailnet,承担两件事:对内做 mesh 网关(`--accept-routes` 接受 PVE 103 通告的办公网段,家里网段**不对外广播**),对外把境外出口从 OpenVPN 迁到 hk-1 的 exit node。控制面全程用自建 headscale(`hs.ipuff.online`),部署与组件见[自建 headscale 与 derper 中继部署](2.自建headscale与derper中继部署.md);网关侧的分流配合与 OpenVPN 拆除见[微软边缘直连与境外出口迁移](../openwrt/3.微软边缘直连与境外出口迁移(tailscale-exit).md)。

## 一、节点与需求口径

### 1.1 tailnet 拓扑

| 节点 | 地址 | 用户 | 角色 |
| --- | --- | --- | --- |
| `hk`(VPS 容器 ts-hk) | 100.64.0.1 | passio-hp | 旧节点,离线 |
| `hk-1`(VPS) | 100.64.0.2 | passio-hp | **exit node**(境外出口) |
| `tailscale`(PVE 103) | 100.64.0.3 | pve | 办公网子网路由,通告 `10.10.10.0/24`、`10.10.12.0/24` |
| `kwrt-gw`(家用网关) | 100.64.0.6 | passio-hp | 本文主角:mesh 网关 + exit 客户端 |

### 1.2 需求口径

- 家里网段(`192.168.0.0/24`)**不对外广播**,tailnet 看不到家;
- 路由器 `--accept-routes` 接受办公网段,家里设备经路由器访问 tailnet(fw4 出方向 masq 做 SNAT,对端零配置);
- DNS 不接管(`--accept-dns=false`),路由器自有 dnsmasq + smartdns 体系不动。

## 二、接入部署与包的坑

### 2.1 安装

```sh
opkg update && opkg install tailscale luci-app-tailscale
```

占 overlay 约 14.5MB(45.4M NAND,装完剩 19.2M)。`luci-app-tailscale` 1.3.0 自带一个**写坏的默认配置**,直接装完是起不来的:

1. **section 类型不匹配**:默认 `/etc/config/tailscale` 是 `config settings 'settings'`,而 init 里 `config_foreach start_instance 'tailscale'` 只遍历 `tailscale` 类型 → procd 空实例、静默不启动。修复:`uci set tailscale.settings=tailscale`(改类型不改名);
2. 默认配置没有 `option enabled '1'`,不加服务永远不启;
3. init 实际用 `--state /tailscaled.state`(根目录),uci 里的 `state_file` 选项不被读取——无所谓,反正在 overlay 上持久;
4. 排障顺序:先看 `ubus call service list` 里 tailscale 有没有 instances,再看二进制能不能前台跑。**手动前台能跑 ≠ init 能拉起**,别被前者骗了。

### 2.2 最终 uci 配置

```sh
uci set tailscale.settings.enabled='1'
uci set tailscale.settings.accept_routes='1'
uci set tailscale.settings.accept_dns='0'
uci set tailscale.settings.hostname='kwrt-gw'
uci set tailscale.settings.login_server='https://hs.ipuff.online'
uci set tailscale.settings.exit_node='100.64.0.2'
```

`advertise_routes` 刻意留空(家里网段不广播)。注册走 headscale 0.29 的新语法:

```sh
docker exec headscale headscale nodes register --user passio-hp --key hskey-authreq-xxx
# 或客户端 --authkey 预授权密钥流程,headplane 面板(:8070/admin)同样可批
```

### 2.3 防火墙:纯 device zone

mesh 的转发与 masq 需要一个 fw4 zone。**不要给 tailscale0 建 netifd 接口**——pbr 会把它纳管为 gateway 引发路由表反复被清(见第四节),zone 直接绑设备:

```sh
uci set firewall.tsz=zone
uci set firewall.tsz.name='tsnet'
uci add_list firewall.tsz.device='tailscale0'
uci set firewall.tsz.input='ACCEPT'; uci set firewall.tsz.output='ACCEPT'; uci set firewall.tsz.forward='ACCEPT'
uci set firewall.tsz.masq='1'; uci set firewall.tsz.mtu_fix='1'
uci set firewall.tsz_fwd=forwarding
uci set firewall.tsz_fwd.src='lan'; uci set firewall.tsz_fwd.dest='tsnet'
```

luci-app 的 `stop_instance` 会固定删除 `network.tailscale`、`firewall.tszone`、`firewall.ts_fwd` 这些名字——自建配置**避开这套命名**(笔者用 `tszif`/`tsz`/`tsnet`),否则服务一重启规则就消失。

## 三、与网关分流的共存

家用网关的国内外分流是 pbr + chnroute 集合(见[微软边缘直连与境外出口迁移](../openwrt/3.微软边缘直连与境外出口迁移(tailscale-exit).md)),tailscale 加进来后 `ip rule` 的全景:

| 优先级 | 规则 | 归属 | 作用 |
| --- | --- | --- | --- |
| 5200 | `fwmark 0x80000 → pbr_wan` | 笔者加(pbr.d 钩子) | tailscale 传输强制直连,防 STUN 污染 |
| 5210~5250 | `fwmark 0x80000 → main/default/unreachable` | tailscaled | 自身的防环逻辑 |
| 5265 | `fwmark 0x10000 → pbr_wan` | 笔者加 | 国内已标记流量抢在 exit 兜底之前直连 |
| 5270 | `lookup 52` | tailscaled | 对端 /32、已接受子网、`default dev tailscale0`(exit) |
| 29997+ | pbr 的 fwmark 规则 | pbr | 旧的直连/隧道标记 |

两条关键事实:其一,LAN 到 tailnet 的流量命中 5270 → table 52 → tailscale0,优先级高于 pbr 的 29997+,与 chnroute 分流天然不冲突;其二,STUN/disco 的 UDP 若被代理,学到的公网映射是假的、打洞必败(自建组件篇 1.3 的坑),所以 5200 这条是**必须**而不是优化。

## 四、打洞与直连

### 4.1 一度退化到 DERP 的根因

家⇄PVE 都在深圳,直连应答 7~10ms,但一度常驻 DERP 中继(~110-170ms)。证据链:

- VPS→PVE 打洞秒通(PVE 端点 `14.155.232.60:35659` 活着,VPS 有公网 IP,单侧 NAT 直连必成)→ **PVE 的 UDP 没有问题**;
- STUN 学到的是真实的广东电信 CGNAT 映射(不是隧道假映射,5200 规则的功劳)→ **STUN 位置与污染无关**;
- 家里的映射端口漂移过(16672→17286),电信 CGNAT 按目标分配映射端口,近似对称 NAT——disco 广播的端点与朝办公室实际用的端口对不上时,怎么打都打不通。

首次登录后的映射"新鲜窗口"内打洞成功过(4ms 直连);端口漂移后就退化。10-31 上午 PPPoE 重拨 + 全量 resync 后直连重新建立,**7~10ms / 0 丢包**,验证了"能成,但依赖新鲜窗口"的判断。

### 4.2 要永久直连

给一端固定公网 UDP 端点即可与 NAT 类型无关:办公网路由器加 `UDP 41641 → 10.10.10.106:41641` 端口映射;或两端都有公网 IPv6(v6 无 NAT,直连必成)。退化频繁时再做,目前 DERP 兜底 + 自愈重打洞够用。

### 4.3 尝试过并放弃:hk-1 二级子网路由

曾想让流量走 家→hk-1→PVE 双段 UDP 绕开打洞:让 hk-1 通告 `10.10.10.0/24`(它自身 accept-routes 能经 PVE 到办公网)。**结构上走不通**:hk-1 一旦通告并成为该前缀的 primary,headscale 不再向它下发同前缀路由——tailscale 不允许一个节点既是某网段的服务者又通过别人学这个网段。已全部回滚(通告清空、MASQUERADE 删除)。

## 五、exit 出口

```sh
# hk-1
docker exec ts-hk tailscale set --advertise-exit-node
docker exec headscale headscale nodes approve-routes -i 7 -r "0.0.0.0/0,::/0"
# kwrt-gw
tailscale set --exit-node=100.64.0.2 --exit-node-allow-lan-access=true
```

国内分流不受影响的关键:网关上加 `ip rule priority 5265 fwmark 0x10000 → pbr_wan`,让 chnroute 已标记的流量抢在 tailscale 的全兜底路由(5270)之前直连。实测:国内 10ms 不变,google 200 OK 0.58~0.99s,出口 IP = VPS;OpenVPN 隧道拆除后境外出口完全由这条 UDP 线路承担。回滚:`tailscale set --exit-node=` 清空 + 删 5265 规则。

## 六、双层自愈与验收

tailscaled 在网络抖动(PPPoE 重拨、接口增删)后 rebind,重装 table 52 偶发半途而废——一旦 table 52 只剩 `throw` 条目,mesh 与 exit 全断。双层自愈:

| 层 | 载体 | 触发 |
| --- | --- | --- |
| 事件层 | `/etc/pbr.d/20-tailscale-direct.sh` | pbr reload;5200/5265 规则 + table 52 丢失时重启 tailscale |
| 定时层 | `/root/ts-route-watchdog.sh`,cron `*/2` | 覆盖 PPPoE 重拨这类没有 pbr 事件的抖动 |

修复动作统一为重启 tailscale 服务(toggle accept-routes 只能恢复子网路由,对端路由必须整服务重启)。10-31 上午 PPPoE 重拨实测定时层有效:下一周期内 table 52 重建,终验 mesh 办公室 9ms / PVE 节点 7.9ms 直连 0 丢包,国内 6.9ms,google 经 exit 0.58s。

## 七、遗留

- VPS 开 BBR,exit node 的 WireGuard UDP 与 derper 的 TCP 链路都受益;
- 办公网端口映射(4.2)是直连永久稳定的保险;
- `MappingVariesByDestIP` 在家用 CGNAT 上两次探测都没出结果,对称 NAT 的判断是间接证据链,有机会补一次完整 netcheck。
