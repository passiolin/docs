# 3. 高可用与扩缩容

> **实测状态**:✅ 已实测 —— Doris 2.1.7,2026-09-30。杀 BE、杀 master FE(2FE 与 3FE 两种形态)、FE 选举死锁与冷启恢复、第三节点在线扩容,全流程实录。

## BE 层:副本容灾(实测)

建表 `replication_num=2`(两副本分布在不同 BE)。**停掉一台 BE(124)**:

```
SHOW BACKENDS: 124 Alive:false / 126 Alive:true
SELECT COUNT(*) FROM demo.events;  → 100000   ← 剩余副本照常服务
```

BE 回归后 tablet 自动补齐副本(clone),无需人工干预。这是 Doris 的常态自愈——巡检看 `SHOW BACKENDS` 的 Alive 与 TabletNum 即可。

## FE 层:多数派是硬约束(实测,重要)

**2 FE 形态:杀 master = 全集群不可用**。实测停掉 2FE 集群的 master 后,剩余单 FE 永远 `Node catalog is not ready`,读写全拒——BDBJE 元数据多数派(2/3 需 2 个,3/3 需 2 个)凑不齐。**结论:FE 要么 1 个(无容错),要么 3 个起,2 个是伪高可用。**

**3 FE 形态:杀 master 依赖选举收敛**。实测停掉 master 后选举未在数分钟内自动完成(卡在 follower 互相观望),期间查询同样 `Node catalog is not ready`。 Doris 的 FE 故障切换不是秒级承诺,应用侧连接串应带多个 FE 地址 + 重试。

## FE 冷启动 Runbook(实测踩出来的核心资产)

**发现:非首节点 FE 容器的 entrypoint 会死等"向 master 注册成功"才启动 JVM**——master 不存在时,所有 follower 容器在 entrypoint 层死循环,JVM 根本不启动,选举无从谈起。整组冷启的纪律:

1. **让"日志最新的前 master"第一个启动**(它的元数据最新,能赢得选举);
2. 若前 master 已无法启动:等第二新的 follower 起来凑够多数派;
3. entrypoint 死锁绕法(应急):`--entrypoint /opt/apache-doris/fe/bin/start_fe.sh` 直接拉 JVM(实测可用,失去注册包装);
4. 逐台等 `SHOW FRONTENDS` 出现 IsMaster:true 再拉下一台。

**换元数据重建时必须同步清 BE storage**(实测):FE 元数据目录清空重导后 cluster_id 变了,BE 旧 storage 拒绝注册(心跳通但永远不 Alive),`rm -rf storage` 重建 BE 才行。

## 在线扩容(实测)

第三台(125)后到,流程:宿主前置三件套 → conf 提取挂载 → FE(FE_ID=3)+ BE 容器起 → entrypoint 自动向 master 注册。实测 `SHOW FRONTENDS` 新节点 Alive:true,BE 同步注册,系统 tablet 自动再均衡。

缩容方向(未实测,官方路径):`ALTER SYSTEM DROP BACKEND "ip:9050"`(先确认副本数足够)。

## 应用接入建议

- JDBC/连接串:多个 FE 地址 failover(如 `jdbc:mysql://10.10.12.124:9030,10.10.12.125:9030,10.10.12.126:9030/demo`);
- FE 切换窗口内 SQL 报 `Node catalog is not ready`,按可重试错误处理;
- Stream Load 永远打 FE 8030(自动重定向),别直连 BE。
