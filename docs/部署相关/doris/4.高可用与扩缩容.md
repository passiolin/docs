# 4. 高可用与扩缩容

> **实测状态**:✅ 已实测 —— Doris 2.1.7,2026-09-30。杀 BE、杀 master FE(2FE 与 3FE 两种形态)、FE 选举死锁与冷启恢复、第三节点在线扩容,全流程实录。**缩容 DECOMMISSION 全流程与冷启 Runbook 断电实战,2026-10-09**。

## BE 层:副本容灾(实测)

建表 `replication_num=2`(两副本分布在不同 BE)。**停掉一台 BE(124)**:

```
SHOW BACKENDS: 124 Alive:false / 126 Alive:true
SELECT COUNT(*) FROM demo.events;  → 100000   ← 剩余副本照常服务
```

BE 回归后 tablet 自动补齐副本(clone),无需人工干预。这是 Doris 的常态自愈——巡检看 `SHOW BACKENDS` 的 Alive 与 TabletNum 即可。

## FE 层:多数派是硬约束(实测,重要)

**2 FE 形态:杀 master = 全集群不可用**。实测停掉 2FE 集群的 master 后,剩余单 FE 永远 `Node catalog is not ready`,读写全拒——BDBJE 元数据多数派(2/3 需 2 个,3/3 需 2 个)凑不齐。**结论:FE 要么 1 个(无容错),要么 3 个起,2 个是伪高可用。**

**3 FE 形态:杀 master 依赖选举收敛**。实测停掉 master 后选举未在数分钟内自动完成(卡在 follower 互相观望),期间查询同样 `Node catalog is not ready`。 Doris 的 FE 故障切换不是秒级承诺,应用侧连接串应带多个 FE 地址 + 重试。

## FE 冷启动 Runbook(实测踩出来的核心资产)

**发现:非首节点 FE 容器的 entrypoint 会死等"向 master 注册成功"才启动 JVM**——master 不存在时,所有 follower 容器在 entrypoint 层死循环,JVM 根本不启动,选举无从谈起。整组冷启的纪律:

1. **让"日志最新的前 master"第一个启动**(它的元数据最新,能赢得选举);
2. 若前 master 已无法启动:等第二新的 follower 起来凑够多数派;
3. entrypoint 死锁绕法(应急):`--entrypoint /opt/apache-doris/fe/bin/start_fe.sh` 直接拉 JVM(实测可用,失去注册包装);
4. 逐台等 `SHOW FRONTENDS` 出现 IsMaster:true 再拉下一台。

**换元数据重建时必须同步清 BE storage**(实测):FE 元数据目录清空重导后 cluster_id 变了,BE 旧 storage 拒绝注册(心跳通但永远不 Alive),`rm -rf storage` 重建 BE 才行。

## 在线扩容(实测)

第三台(125)后到,流程:宿主前置三件套 → conf 提取挂载 → FE(FE_ID=3)+ BE 容器起 → entrypoint 自动向 master 注册。实测 `SHOW FRONTENDS` 新节点 Alive:true,BE 同步注册,系统 tablet 自动再均衡。

## 缩容实录(2026-10-09,DECOMMISSION 优雅路径)

走 `ALTER SYSTEM DECOMMISSION BACKEND "ip:9050"`(先迁副本后下线,等价官方 DROP 的安全版;DROP 直删留给"实例已死且数据可弃"的场景)。**前置检查连续拦截四次,每一次都是真问题**:

| 拦截 | 报错要点 | 处置 |
| --- | --- | --- |
| 1 | `__internal_schema.column_statistics` 副本 3 > 缩后可用 2 | ALTER 改 2 |
| 2 | `__internal_schema.histogram_statistics` 同上 | ALTER 改 2 |
| 3 | `__internal_schema.audit_log` 是**动态分区表**,要 `default.replication_num` + `MODIFY PARTITION (*)` 双改 | 双改 |
| 4 | `demo2.events`(**RESTORE 恢复出来的表**被置为 3 副本) | 演练产物直接 DROP DATABASE |

清完第 4 个拦截后 DECOMMISSION 被接受:目标 BE tablet 49 → 4 → 0,**约 40 秒迁完**,完成后 BE 自动从 `SHOW BACKENDS` 消失。两 BE 形态全部表可查;再拉回第三台:清 storage + 重启 BE 容器,自动注册 Alive:true,tablet 后台再均衡。

**缩容纪律(实测总结)**:缩容前 `SHOW TABLES FROM __internal_schema` 逐张核对副本数,**别忘用户库里从备份 RESTORE 出来的表**(恢复会带出 3 副本);副本数 > 目标台数的表一张不清理,DECOMMISSION 就一步都走不动——这是保护,不是障碍。

## 冷启 Runbook 断电实战补充(2026-10-09 全流程验证)

上表 Runbook 在真实断电(2026-10-01 内网断电,10-09 恢复)中完整走了一遍,补充三条实测结论:

1. **FE 选主需要 BDBJE 多数派:3 FE 组必须 ≥2 台 JVM 在线**——只拉起"日志最新的前 master"一台会永远 `feType:UNKNOWN` 卡死(日志每 10s 刷 `wait catalog to be ready`),必须**同时拉起两台**凑多数派;
2. follower 的 entrypoint 门禁在 master 缺席时死循环(`Verify that CURRENT_FE is registered to FE failed, retry`),JVM 不启动 → 选举凑不齐 → 死锁。解法照旧:应急节点 `--entrypoint /opt/apache-doris/fe/bin/start_fe.sh` 直启 JVM(实测生效,master 起来后其余节点正常走门禁);FE_ID 分工看 FE_SERVERS(第一台是 master 候选,后加的 FE_ID 排后);
3. **宿主前置三件套会随断电回退**:`vm.max_map_count` 实测打回 1048576(<2000000),BE 的 init_be.sh **静默死掉**(错误被 `2>/dev/null` 吞掉,容器只剩 `entry_point.sh + sleep 15`,日志无新行)——表现是 FE 心跳 BE 全部 `Connection refused`。处置:手工进容器跑 `bash init_be.sh` 看真实报错;`sysctl -w` 的值**必须写进 /etc/sysctl.conf**(本次发现此前只 -w 未落盘,重启即丢)。

## 应用接入建议

- JDBC/连接串:多个 FE 地址 failover(如 `jdbc:mysql://10.10.12.124:9030,10.10.12.125:9030,10.10.12.126:9030/demo`);
- FE 切换窗口内 SQL 报 `Node catalog is not ready`,按可重试错误处理;
- Stream Load 永远打 FE 8030(自动重定向),别直连 BE。
