# 2. 变更与故障验证

所有 MySQL 写入都走真实 binlog,没有手工在 Doris 补数据。数据集是 101 万订单 / 202 万明细,DML、DDL、主库切换都在这个库上做。

## 数据集

| 库 | 表 | 行数 | 说明 |
| --- | --- | --- | --- |
| app_db(单机) | customers / products | 1,000 / 100 | 维表 |
| app_db(单机) | orders | 1,010,000 | 10,000 条快照 + 100 万条增量 |
| app_db(单机) | order_items | 2,020,000 | 20,000 条快照 + 200 万条增量 |
| app_db(单机) | sync_heartbeat | 1 | 每秒更新,端到端延迟探针 |
| app_mgr(MGR) | customers / products | 1,000 / 100 | 维表 |
| app_mgr(MGR) | orders / order_items | 5,000(+2 切换标记) / 10,000 | 功能验证数据 |
| app_mgr(MGR) | sync_heartbeat | 1 | 外部 writer 每秒更新 |

增量数据用 `lab_meta.seq`(100 万行的序列表,放在不同库,不在 CDC 的 `app_db.\.*` 过滤范围内)分批插入:订单 10 批 × 10 万,明细 20 批 × 10 万,MySQL 侧总耗时 92s。Doris 侧追上后计数与 MySQL 一致;同步期间 Prometheus 的端到端心跳延迟峰值 0.987s,binlog 总量 110,146,254 字节。

## DML

```sql
-- MySQL 单机
INSERT INTO app_db.orders (id,customer_id,status,amount,created_at,updated_at)
VALUES (1000001,1,1,123.45,NOW(),NOW());
UPDATE app_db.orders SET amount=999.99, updated_at=NOW() WHERE id=1000001;
DELETE FROM app_db.orders WHERE id=1000001;
```

| 步骤 | Doris 查询 | 结果 |
| --- | --- | --- |
| INSERT 后 | `SELECT id,amount FROM app_db.orders WHERE id=1000001` | `1000001  123.45` |
| UPDATE 后 | 同上 | `1000001  999.99` |
| DELETE 后 | `SELECT COUNT(*) ... WHERE id=1000001` | `0` |

Doris 侧表由 sink 自动创建为 UNIQUE KEY 模型,`INSERT`/`UPDATE`/`DELETE` 都按主键合并。非主键表没有验证;没有主键时 Doris 只能建 DUPLICATE 模型,更新/删除会退化成追加,生产里要避免。

## DDL

DDL 矩阵(列级操作在单机 `app_db` 上全量验证;MGR 的 `app_mgr` 上验证了加列、建表、清空、删表):

| 操作 | MySQL 语句 | Doris 结果 | 备注 |
| --- | --- | --- | --- |
| 加列 | `ALTER TABLE orders ADD COLUMN remark VARCHAR(64) NULL` | ✅ 出现 `remark varchar(192)` | MySQL VARCHAR(64) 按 UTF-8 放大 3 倍 |
| 改列类型 | `ALTER TABLE orders MODIFY COLUMN remark VARCHAR(128) NULL` | ✅ 变为 `varchar(384)` | 100 字符值保留 |
| 重命名列 | `ALTER TABLE orders RENAME COLUMN remark TO note` | ✅ 列名变 `note`,值保留 | —— |
| 删列 | `ALTER TABLE orders DROP COLUMN note` | ✅ 列消失 | —— |
| 新建表 | `CREATE TABLE app_db.ddl_new (...)` | ✅ Doris 自动建表并接住后续 INSERT | 需 `scan.binlog.newly-added-table.enabled: true` |
| 清空表 | `TRUNCATE TABLE app_db.ddl_new` | ✅ Doris 表清空 | 需 `schema.change.behavior: evolve` |
| 删除表 | `DROP TABLE app_db.ddl_new` | ✅ Doris 表删除 | 同上 |

关键开关是 `pipeline.schema.change.behavior`。Flink CDC 的默认值是 **LENIENT**:它会把不支持的 DDL 转成兼容变更,并**刻意忽略 `TRUNCATE TABLE` / `DROP TABLE`**,避免误删下游数据。不显式写 `evolve`,前四个列级 DDL 仍能生效(会被转换成 rename+add),但清空/删表不会传导——本次一开始就踩了这个坑,Doris 侧一直留着已删除的表。

新建表还有第二个开关:`scan.binlog.newly-added-table.enabled: true`。它让 source 在 binlog 阶段解析新表的 DDL 和 DML;另一个名字相近的 `scan.newly-added-table.enabled` 只在从 savepoint/checkpoint 恢复时重新快照新表,两者语义不同。只开后者、不开前者,运行期 `CREATE TABLE` 后 Doris 不会建表。

DDL 实测片段:

```sql
-- MySQL
ALTER TABLE app_db.orders ADD COLUMN remark VARCHAR(64) NULL;
UPDATE app_db.orders SET remark='hello-ddl' WHERE id=1;

-- Doris
DESC app_db.orders;                    -- remark  varchar(192)
SELECT id,remark FROM app_db.orders WHERE id=1;   -- 1  hello-ddl

ALTER TABLE app_db.orders MODIFY COLUMN remark VARCHAR(128) NULL;
UPDATE app_db.orders SET remark=REPEAT('x',100) WHERE id=1;
-- Doris: remark varchar(384); LENGTH(remark)=100

ALTER TABLE app_db.orders RENAME COLUMN remark TO note;
-- Doris: note varchar(384),值保留

ALTER TABLE app_db.orders DROP COLUMN note;
-- Doris: 列消失
```

```sql
-- 运行期新表
CREATE TABLE app_db.ddl_new2 (id BIGINT PRIMARY KEY, v VARCHAR(32));
INSERT INTO app_db.ddl_new2 VALUES (1,'a'),(2,'b');
-- Doris: 自动出现 ddl_new2,两行都在

TRUNCATE TABLE app_db.ddl_new2;
-- Doris: COUNT(*)=0

INSERT INTO app_db.ddl_new2 VALUES (5,'e'),(6,'f');
-- Doris: 5/e、6/f

DROP TABLE app_db.ddl_new2;
-- Doris: 表消失
```

`ALTER TABLE ... ADD INDEX`、`RENAME TABLE`、分区表 DDL、JSON/空间类型没有覆盖。生产接入前按业务实际 DDL 补测;尤其 `RENAME TABLE` 会改变表标识,Flink CDC 的 schema 历史和 Doris sink 的映射都要单独验证。

## MGR 主库切换

环境:122 初始主库,123/124 从库,Router 在 125(6446 读写 / 6447 只读)。切换用 `systemctl stop mysql` 模拟主库宕机,不做优雅切换。

```text

          INSERT id=900002 → Doris 出现 900002 / 222.22
20:31:19  在 122 执行 systemctl stop mysql
20:32:56  123 上查 replication_group_members:
          124 ONLINE PRIMARY,123 ONLINE SECONDARY(122 已被驱逐)
          Router 6446 → 124,read_only=0
```

```text

  currentGtid=5f141a9f-de92-11f1-bfa9-bc24116b3096:1266,
  restartGtidSet=5f141a9f-...:1-1266,a4502673-...:1-7,
```

旧主库的 binlog 文件名/位点在新主库上不存在,但 MGR 成员共享同一组 GTID;source 重连后按 GTID 在新主库找到位置,作业没有重启,只跳过了最后 1 个事件避免重复。切换窗口内 Router 会短暂拒绝新连接,应用侧要有重试;本次写入是在切换完成后发起的,没有测“切换瞬间写入”的失败率。

心跳在切换后暴露了一个 MGR 细节:原主库上的 `app_mgr.ev_heartbeat` 复制到从库后是 `REPLICA_SIDE_DISABLED`;124 升主后 EVENT 不会自动启用,Doris 里的心跳时间停在切换前。监控改用 monitor 机上的外部 writer,每秒经 Router 6446 执行 `UPDATE app_mgr.sync_heartbeat`,不再依赖 MySQL EVENT。第 3 篇给出服务与告警。

## 百万行增量

3,030,000 行(100 万订单 + 200 万明细)在 MySQL 侧 92s 写完,分 30 个事务,每批 10 万行。Doris 侧在约 2 分钟内追平:

| 指标 | 值 |
| --- | --- |
| MySQL 写入耗时 | 92s(30 批) |
| Doris 追平时间 | 约 2 分钟(含 3s checkpoint 的批量提交) |
| 同步期间心跳延迟峰值 | 0.987s(5 分钟窗口 `max_over_time`) |
| binlog 总量 | 110,146,254 字节(约 105 MiB) |
| checkpoint 间隔 | 3s |
| 作业并发 | 每条 pipeline 2 |

Doris 的 sink 按 checkpoint 批量 flush,3s 一次;10 万行的事务不会把延迟拉到分钟级,因为 binlog 读取和 Stream Load 是流水线并行的。延迟的主要构成是 checkpoint 间隔 + Doris 提交,而不是行数。这个结论只对本次 8G/4C 的 BE 和 3 副本成立;更大数据量、更多表、单事务更大时需要重新压测。

## MySQL 与 Doris 查询对比

同一份 101 万订单 / 202 万明细,MySQL 8.4 与 Doris 4.0.8 各跑同一 SQL,取多轮最小值(客户端启动约 50ms 也算在内):

| 查询 | MySQL | Doris | 倍数 |
| --- | --- | --- | --- |
| Q1 状态聚合(全量) | 2,024ms | 250ms | 8× |
| Q2 状态聚合(近 30 天) | 2,722ms | 226ms | 12× |
| Q3 品类营收 JOIN(全量) | 29,010ms | 121ms | 241× |
| Q4 品类营收 JOIN(近 30 天) | 1,907ms | 40ms | 48× |
| Q5 Top 客户(全量) | 4,125ms | 23ms | 181× |
| Q6 日趋势(近 90 天) | 581ms | 35ms | 16× |

SQL 形态:

```sql
-- Q3:明细 JOIN 订单 JOIN 商品,按品类汇总
SELECT p.category, COUNT(*), ROUND(SUM(oi.qty*oi.price),2)
FROM app_db.order_items oi
JOIN app_db.orders o ON oi.order_id=o.id
JOIN app_db.products p ON oi.product_id=p.id
GROUP BY p.category ORDER BY 3 DESC;

-- Q5:按客户汇总,取 Top 10
SELECT customer_id, COUNT(*), ROUND(SUM(amount),2)
FROM app_db.orders
GROUP BY customer_id ORDER BY 3 DESC LIMIT 10;
```

口径与限制:

- MySQL 只把 `innodb_buffer_pool_size` 在线调到 4G,其余保持默认;Doris 是三 BE、无物化视图、无预聚合,直接扫明细。倍数用于说明**查询形态差异**,不是容量选型或厂商 benchmark;
- 实验跑在共享 PVE 上,宿主机还有其他虚机,绝对耗时波动明显;表里取的是同一窗口内的最小值;
- 客户端启动、连接建立都计入,单条 SQL 的真实执行时间会比表里略低;
- 没有并发压测。Doris 的高并发是另一条维度,本次只验证单条分析查询。

MySQL 的 JOIN 在这组数据上明显吃亏:两张明细表都要按 `order_id` 回表,`GROUP BY` 又要临时表/排序;Doris 的列存 + 哈希 JOIN + MPP 并行把 202 万行的聚合压到百毫秒级。Q6 只快 16 倍,因为它按日期分组、结果集小,MySQL 的索引还能发挥作用,差距没有 JOIN 那么夸张。

## 边界

- **库要预建**:Flink CDC 的 Doris sink 不自动建 database,`app_db`/`app_mgr` 必须先在 Doris 建好;
- **DDL 覆盖有限**:列级增删改/重命名、建表/清空/删表已验证;数据库级 DDL、`RENAME TABLE`、分区变更、JSON/空间类型未验证;
- **语义**:Doris sink 的 Stream Load 日志里 `TwoPhaseCommit=false`,本次没有启用两阶段提交;主键模型靠主键合并收敛,非主键表在作业重试时可能重复。需要严格 exactly-once 的场景要单独验证 sink 的 2PC 与 Flink checkpoint 配置;
- **切换窗口**:MGR 选举期间 Router 的新连接会失败,应用要重试;Flink 作业本身不重启,但事件处理会有秒级停顿;
- **binlog 保留**:实验设 7 天(`binlog_expire_logs_seconds=604800`)。Flink 作业停机超过保留期,只能重新做全量快照;
- **版本**:Doris 4.0.8 不在 Flink CDC Doris connector 的官方支持矩阵(1.2/2.x/3.x),本次可用不代表生产长期兼容;升级前在预发重跑本篇的 DDL 清单。
