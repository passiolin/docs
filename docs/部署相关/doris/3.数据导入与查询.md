# 3. 数据导入与查询

> **实测状态**:✅ 已实测 —— Doris 2.1.7,10 万行 Stream Load 两次(冷缓存 16s / 热缓存 3.9s),2026-09-30;**Broker Load(S3)+ routine load(Kafka)+ TVF 湖仓查询,2026-10-09**。

## 建表(实测 DDL)

```sql
CREATE DATABASE demo;
CREATE TABLE demo.events(
  id      INT NOT NULL,
  user_id INT,
  event   VARCHAR(32),
  ts      DATETIME
) DUPLICATE KEY(id)
DISTRIBUTED BY HASH(id) BUCKETS 4
PROPERTIES("replication_num" = "2");
```

建模三件套:数据模型(DUPLICATE 明细 / AGGREGATE 聚合 / UNIQUE 主键)、分桶(HASH(高频过滤列),桶数 ≈ BE 数 × 1~2 起步)、副本数(实验 2 / 生产 3)。**没有 BE Alive 时建表直接报** `System has no available disk capacity or no available BE nodes`(实测)——先查 SHOW BACKENDS 再排 DDL 问题。

## Stream Load(实测)

```bash
# 造数据
awk 'BEGIN{for(i=1;i<=100000;i++) print i","i%1000",click,2026-09-30 12:00:00"}' > /tmp/events.csv

# 导入:走 FE 8030,自动重定向到 BE 8040(--location-trusted 必须)
curl --location-trusted -u root: -H "column_separator:," \
  -T /tmp/events.csv -X PUT \
  "http://10.10.12.124:8030/api/demo/events/_stream_load"
```

实测输出:

```
"Status": "Success",
"NumberLoadedRows": 100000,
"LoadTimeMs": 3947,        ← 第二次(热)3.9s;首次冷缓存 16s
```

**实测坑:默认列分隔符是 TAB**——CSV 逗号文件不带 `column_separator:,` 时全部行报错 `actual column number ... is less than schema column number`,错误详情要看返回体里的 ErrorURL(浏览器/curl 打开即见逐行原因)。

查询验证(MySQL 协议):

```sql
SELECT COUNT(*), COUNT(DISTINCT user_id) FROM demo.events;   -- 100000 / 1000
SELECT user_id, COUNT(*) c FROM demo.events GROUP BY user_id ORDER BY c DESC LIMIT 3;
```

## 导入方式选型

| 方式 | 场景 | 备注 |
| --- | --- | --- |
| Stream Load(HTTP) | 文件/流式批量,≤10GB | 本文实测;程序侧走此路最简单 |
| INSERT INTO VALUES | 少量手造数据 | 别当批量通道 |
| Broker Load / S3 | 对象存储大规模 | ✅ 已实测(2026-10-09,见下) |
| routine load | Kafka 消费 | ✅ 已实测(2026-10-09,见下) |

## Broker Load 从对象存储导入(实测,2026-10-09)

实验 S3:单二进制 SeaweedFS(`weed server -s3 -s3.port=9000 -s3.config=s3.json`,GitHub release 直下;minio 镜像源全 403)。数据流:**SELECT INTO OUTFILE 写 S3 → Broker Load 读 S3**——不用外部 S3 客户端:

```sql
-- ① 导出(10 万行 → s3://doris-bucket/events/...,3.5MB,秒级)
SELECT * FROM demo.events INTO OUTFILE 's3://doris-bucket/events/export20261009/'
FORMAT AS CSV PROPERTIES(
  'column_separator' = ',', 's3.endpoint' = 'http://10.10.12.124:9000',
  's3.access_key' = '...', 's3.secret_key' = '...', 's3.region' = 'us-east-1');

-- ② Broker Load(异步,SHOW LOAD 看进度)
LOAD LABEL demo.broker_load_s3_2
(
  DATA INFILE('s3://doris-bucket/events/export20261009/bc99361d9f24d5e-87cfb2953002f9e7_*')
  INTO TABLE events_broker
  COLUMNS TERMINATED BY ','          -- ← 实测坑:默认也是 TAB,必须显式给
  (id, user_id, event, ts)
)
WITH S3 ('AWS_ENDPOINT'='http://10.10.12.124:9000', 'AWS_ACCESS_KEY'='...',
         'AWS_SECRET_KEY'='...', 'AWS_REGION'='us-east-1')
PROPERTIES('timeout' = '300');
```

实测:10 万行 FINISHED,`COUNT(*)=100000 / COUNT(DISTINCT user_id)=1000` 与源一致。**两个实测坑**:① Broker Load 的列分隔符默认同样是 TAB(与 Stream Load 同款坑,报错排查看 ErrorURL);② 创建仓库/仓库读桶要求**桶已存在**(S3 端不代建),先建桶再 `CREATE REPOSITORY`。

## routine load 接 Kafka(实测,2026-10-09)

```sql
CREATE ROUTINE LOAD rl_job ON events_rl    -- 表名不带库前缀(job 与表同库)
PROPERTIES ('format' = 'json', 'jsonpaths' = '["$.id","$.user_id","$.event","$.ts"]')
FROM KAFKA
(
  'kafka_broker_list' = '10.10.12.128:9092,10.10.12.129:9092',
  'kafka_topic' = 'doris-rl'
);
-- 生命周期:STOP ROUTINE LOAD FOR rl_job / PAUSE / RESUME
```

实测(Kafka 4.3.1 三分区 topic,JSON 消息):创建即 RUNNING,持续消费——三批 20 条逐批落库,`COUNT` 随生产增长,`MAX(event)` 始终是最新批次。**三个实测要点**:

1. **默认从"创建时刻的分区末尾"开始消费**——创建前已在 topic 里的消息不补(实测批次 1 被跳过、批次 2/3 落库);要回溯历史加 `'kafka_default_start_offset' = 'OFFSET_ZERO'`;
2. 这版 2.1.7 **不认 routine load 的 `column_separator` 属性**(`column_separator is invalid property`)——CSV 要指定分隔符的场景改走 jsonpath+JSON 或 S3 路线;
3. 表名写 `db.table` 前缀直接语法报错,job 与表必须同库。

## 湖仓查询(TVF 直查对象存储,实测)

```sql
SELECT COUNT(*) FROM S3(
  "URI" = "s3://doris-bucket/events/export20261009/xxx_0.csv",
  "FORMAT" = "csv",
  "s3.endpoint" = "http://10.10.12.124:9000",
  "s3.access_key" = "...", "s3.secret_key" = "...", "s3.region" = "us-east-1"
);
```

实测:`COUNT(*)=100000` 与仓内表一致。**行为细节**:无 header 的 CSV 未声明分隔符时整行作为单列(`c1`)返回——TVF 直查 CSV 记得配分隔符/列映射;参数名用 `s3.endpoint` 系(报错会逐个提示缺哪个,`AWS_REGION` 要写成 `s3.region`)。
