# 多云成本监控设计与部署

按量付费的账单以天为单位变化,等到月报出来再发现异常已经来不及。这套任务每天推日报、每月推月报,单日成本相对历史基线异常时推一张红色卡片,三个动作都落到飞书群。当前接入阿里云与 AWS,代码在 `cost-job` 仓库(文中以代称出现),运行在内网一台 Linux 机器上,只使用 Python 标准库。

## 目录与职责

```
cost-job/
├── common/cost_common.py        # HTTP、重试、月份窗口、CSV、飞书发送
├── aliyun/
│   ├── script/aliyun_cost.py    # BSS 账单取数(月/日)
│   ├── script/aliyun_report.py  # 日报/月报/突增
│   ├── conf/env.example         # 凭据模板;conf/.env 不入 git
│   └── data/                    # 原始响应、缓存、告警去重状态
├── aws/
│   ├── script/aws_cost.py       # Cost Explorer 取数
│   ├── script/aws_report.py
│   ├── conf/env.example
│   └── data/
├── cron-run.sh                  # cron-run.sh <cloud> <job>
├── cron-install.sh              # 幂等安装 crontab(双 marker 包裹)
├── tests/                       # 23 个离线单测
└── logs/                        # cron 运行日志
```

每个云一个目录,内部固定 `script/`、`conf/`、`data/` 三层。新增一朵云等于复制一个同构目录,公共层只放无云差异的能力(HTTP 与重试、金额格式、飞书发送、月份窗口)。适配器契约是 `collect(month)`,返回按服务汇总的金额与币种,打印、CSV、推送由公共层统一处理。脱敏后的配置模板与脚本快照见 [README](README.md) 的「代码与配置」一节。

## 数据源与最小权限

### 阿里云

- 接口:`QueryAccountBill`,BSS OpenAPI 版本 `2017-12-14`。
- 月粒度按 `BillingCycle` 直接查;日粒度必须同时带 `BillingDate=yyyy-mm-dd`,一次查询一天。
- 账户级账单默认不按产品分组,需要 `IsGroupByProduct=true`;按 `TotalCount` 与 `PageSize` 分页取全。
- 金额口径 `PretaxAmount`(应付,已扣优惠),币种 CNY。
- 权限:RAM 服务账号只需要 `bss:QueryAccountBill`。国际站账号把 `ALIYUN_BSS_HOST` 指向 `business-intl.aliyuncs.com`,国内站用默认的 `business.aliyuncs.com`。

### AWS

- 接口:Cost Explorer `GetCostAndUsage`。wire 格式是 JSON 1.1,`POST /`,`X-Amz-Target` 为 `AWSInsightsIndexService.GetCostAndUsage`(取值依据 botocore 的 `ce/2017-10-25` 服务定义),SigV4 签名,签名区域 `us-east-1`。
- `TimePeriod.End` 是排他日期;查询当月时截止到明天,不把月末的未来日期传给接口。
- 金额口径 `UnblendedCost`,币种 USD;分组固定 `SERVICE`。
- 权限:IAM 用户只需要 `ce:GetCostAndUsage`,并在控制台启用过 Cost Explorer。
- 计费:每次 API 请求 $0.01,这是 AWS 突增只按天检查的原因。

## 突增判定

对每个服务单独计算,基线取同星期几前 4 周的中位数:

```
B = median(A(d-7), A(d-14), A(d-21), A(d-28))
Δ = A(d) - B
```

同时满足以下两条才算突增:

```
Δ >= 绝对下限
Δ >= 2.0 × B
```

绝对下限按云区分:阿里云 100 元,AWS 20 美元。突增金额记 `Δ`,不是当日总额。近 4 周没有消费的新服务,基线按 0 计,首次出现超过下限的消费会直接告警。

当前只实现单日尖峰这一类。最初的方案里还有「近 3 日均值相对前 14 日中位数上涨」的持续爬升和「预计月末超预算」的月度偏航,这两类尚未落进代码。

## 报表与推送

| 报表 | 触发 | 时间口径 | 内容 |
| --- | --- | --- | --- |
| 日报 | 每天 09:30 | 阿里云 T-1(报昨天),AWS T-2 | 当日合计、环比昨日、当月累计、服务 Top5、近 6 月平均月成本、当日突增 |
| 月报 | 每月 1 号 10:00 | 上个完整月 | 本月合计、环比上月、近 6 月平均(含报告月)、服务明细、本月逐日突增 |
| 突增 | 阿里云每小时、AWS 每天 10:10 | 同日报 | 只报未推送过的突增:服务、当日、基线、超出金额、倍数、当月累计 |

推送走飞书群机器人的交互卡片:`msg_type=interactive`,日报蓝色、月报紫色、突增红色;金额、环比、明细在卡片里用字段块与 Markdown 列表排版。同一笔突增按「日期 + 服务」写入 `data/spike_alerted.json` 去重,保留 90 天。

AWS 的日报默认评估 T-2 的数据。Cost Explorer 的数据滞后约一天,昨天的数字还会继续调整;阿里云日报按实际要求报 T-1,最近一两天的金额同样可能被重算。

## 缓存、去重与调度

- 日账单与月账单都落本地缓存:`<云>/data/daily/<月份>.json`、`<云>/data/monthly/<月份>.json`。超过 4 天的账期视为稳定,永久复用;近 4 天的数据 6 小时内复用,避免每小时重复请求接口。
- 所有 HTTP 请求经过统一重试:5xx、429、`ServiceUnavailable`、`Throttling` 与网络异常按指数退避重试,默认 3 次、3 秒起每次翻倍。
- 阿里云日账单按天查询;日报与突增先拉所在月与上月的数据,命中缓存后只补缺失日期。
- 飞书推送校验返回码,`code != 0` 直接报错,不会静默成功。

定时任务一共六条:

```
30 9 * * *    cron-run.sh aliyun daily
0 10 1 * *    cron-run.sh aliyun monthly
5 * * * *     cron-run.sh aliyun spike
30 9 * * *    cron-run.sh aws daily
0 10 1 * *    cron-run.sh aws monthly
10 10 * * *   cron-run.sh aws spike
```

`cron-run.sh` 接受 `<cloud> <job>`,单参数形式兼容旧 crontab(按阿里云处理);每个任务用独立的 `flock` 锁,跑重叠了直接跳过。`cron-install.sh` 用一对 marker 包裹写入 crontab,重复执行只替换这一段,并把旧 crontab 备份到 `logs/`。

服务器的时区必须是 `Asia/Shanghai`。默认的 Ubuntu 镜像通常是 UTC,不调整的话 09:30 会变成北京时间 17:30。

## 部署步骤

1. 复制配置模板并填凭据:

```
cp aliyun/conf/env.example aliyun/conf/.env
cp aws/conf/env.example aws/conf/.env
chmod 600 aliyun/conf/.env aws/conf/.env
```

凭据变量只有名字进入文档:阿里云是 `ALIYUN_ACCESS_KEY_ID`/`ALIYUN_ACCESS_KEY_SECRET`/`FEISHU_WEBHOOK_URL`,AWS 是 `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`FEISHU_WEBHOOK_URL`(旧的 `FEISHU_WEBHOOK` 仍兼容)。两朵云可以指向不同群,也可以共用同一个机器人。

2. 同步代码到内网机器的 `/opt/cost-job`,不带走本地缓存与日志:

```
rsync -a --exclude='.git' --exclude='data/' --exclude='logs/' ./ root@<host>:/opt/cost-job/
scp aws/conf/.env root@<host>:/opt/cost-job/aws/conf/.env
```

3. 先验证取数,再装 cron。`--dry-run` 只打印不推送:

```
python3 aliyun/script/aliyun_report.py daily --dry-run
python3 aws/script/aws_report.py daily --dry-run
python3 aws/script/aws_report.py monthly --month 2026-10 --dry-run
```

4. 安装定时任务:

```
./cron-install.sh
crontab -l            # 应看到六条,在 marker 之间
tail -f logs/aws-daily.log
```

时间表可用环境变量覆盖:阿里云 `DAILY_SCHEDULE`/`MONTHLY_SCHEDULE`/`SPIKE_SCHEDULE`,AWS 用 `AWS_DAILY_SCHEDULE`/`AWS_MONTHLY_SCHEDULE`/`AWS_SPIKE_SCHEDULE`。

## 配置项

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `SPIKE_MIN_AMOUNT` | 100(阿里云)/20(AWS) | 突增金额下限,单位随云 |
| `SPIKE_RATIO` | 2.0 | 超出金额需达到基线的倍数 |
| `SPIKE_BASELINE_WEEKS` | 4 | 基线取前几周同星期几的中位数 |
| `REPORT_DELAY_DAYS` | 1(阿里云)/2(AWS) | 日报与突增评估今天之前第 N 天 |
| `COST_RETRY_ATTEMPTS` | 3 | 瞬时故障重试次数 |
| `COST_RETRY_DELAY` | 3 | 首次重试等待秒数,之后翻倍 |
| `AWS_REGION` | us-east-1 | CE 签名区域,中国区为 cn-northwest-1 |
| `ALIYUN_BSS_HOST` | business.aliyuncs.com | 国际站改为 business-intl.aliyuncs.com |

## 排障记录

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 阿里云返回 `InvalidVersion` | 版本号写成 2017-12-09 | BSS OpenAPI 的正确版本是 2017-12-14 |
| 阿里云返回 `InvalidParameter: Granularity should be MONTHLY or DAILY` | 参数写成 `MONTH` | 改为 `MONTHLY`;日粒度还必须带 `BillingDate` |
| HTTP 200 但结果全是 0 元 | 阿里云业务错误也能以 200 返回,`Code` 为 `InvalidParameter` | 适配器对 `Code != Success` 显式抛错 |
| 明细里 `ProductName` 为空 | 账户账单默认不分组 | 加 `IsGroupByProduct=true` |
| AWS 返回 400 或 `SignatureDoesNotMatch` | `X-Amz-Target`、Content-Type 或 canonical 头不对 | 以 botocore 服务定义核对;重试时必须重新签名,`amz_date` 过期会让签名失效 |
| 部署首跑 `HTTP 503 ServiceUnavailable` | 阿里云侧瞬时故障 | 已内置指数退避重试,重跑即恢复 |
| 飞书发送报 `can't concat str to bytes` | HTTP 工具对 dict 请求体漏了 JSON 序列化 | 统一按 bytes/str/dict 三态处理 |
| AWS 当月查询报参数错误 | `TimePeriod.End` 是排他日期,且不能指向未来 | 截止到明天 |

## 限制与后续

- 账单是全账号按服务口径。阿里云要看实例级成本需要追加 `bss:QueryInstanceBill`;AWS 若要按子账号拆,需要 Organizations 管理账号并在 `GroupBy` 里加 `LINKED_ACCOUNT`。
- 腾讯云与观测云尚未接入,目录按同一规范预留。
- 日报的环比是自然日对比,周末效应明显;是否改成对比上周同星期几尚未决定。
- AWS 突增按天检查,是为了控制 CE 的请求费用;需要更高频率时改 cron 时间,不做代码改动。
