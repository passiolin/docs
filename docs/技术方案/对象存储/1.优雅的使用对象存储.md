

对象存储（Object Storage）已成为现代应用存储海量非结构化数据（如图片、视频、文档）的事实标准。它具备高可用、高扩展、低成本等优势。然而，在Java服务中集成对象存储时，开发者常面临内存溢出（OOM）、安全漏洞、成本失控等挑战。

## 1. Java服务如何上传文件

无论你选择阿里云OSS、腾讯云COS、华为云OBS还是AWS S3，上传流程大同小异。通常有三种方式：
### 1.1 简单上传（PutObject）

适用于小于5GB的文件。直接将文件流或字节数组上传。

```java
// 初始化OSS客户端
OSS ossClient = OSSClientBuilder.create()
    .endpoint("oss-cn-hangzhou.aliyuncs.com")
    .credentialsProvider(credentialsProvider)
    .build();

// 上传文件流
ossClient.putObject("bucketName", "objectKey", new FileInputStream("localFile"));
```


### 1.2 分片上传（MultipartUpload）

适用于大文件或网络不稳定场景。将文件切分为多个部分并发上传，最后合并。

```java
// 初始化上传
InitiateMultipartUploadRequest request = new InitiateMultipartUploadRequest("bucket", "key");
InitiateMultipartUploadResult result = ossClient.initiateMultipartUpload(request);
String uploadId = result.getUploadId();

// 上传分片
List<PartETag> partETags = new ArrayList<>();
for (int i = 0; i < partCount; i++) {
    UploadPartRequest uploadPartRequest = new UploadPartRequest();
    uploadPartRequest.setBucketName("bucket");
    uploadPartRequest.setKey("key");
    uploadPartRequest.setUploadId(uploadId);
    uploadPartRequest.setInputStream(partInputStream);
    uploadPartRequest.setPartSize(partSize);
    uploadPartRequest.setPartNumber(i + 1);
    UploadPartResult uploadPartResult = ossClient.uploadPart(uploadPartRequest);
    partETags.add(uploadPartResult.getPartETag());
}

// 完成上传
CompleteMultipartUploadRequest completeRequest = new CompleteMultipartUploadRequest("bucket", "key", uploadId, partETags);
ossClient.completeMultipartUpload(completeRequest);
```



### 1.3 高级上传接口（TransferManager）

大多数云厂商提供高级封装，自动选择简单或分片上传，并支持断点续传。

```java
TransferManager transferManager = new TransferManager(ossClient);
Upload upload = transferManager.upload(new PutObjectRequest("bucket", "key", new File("localFile")));
upload.waitForUploadResult();
transferManager.shutdownNow();
```


## 2. 避免服务端内存溢出（OOM）

传统服务端上传模式中，Java服务接收客户端文件后，再转发给对象存储。这种模式容易导致OOM，尤其是大文件并发时——文件数据被加载到内存，形成瓶颈。

### 2.1 问题根源

```java
@PostMapping("/upload")
public String upload(@RequestParam("file") MultipartFile file) {
    byte[] bytes = file.getBytes(); // 大文件直接撑爆内存
    ossClient.putObject("bucket", "key", new ByteArrayInputStream(bytes));
    return "ok";
}
```


### 2.2 客户端直传 + 临时密钥（STS）

核心思想：Java服务端只负责生成一个有时效、有权限的临时凭证，客户端拿着凭证直接上传到对象存储，数据不经过服务端。这样服务端内存压力归零。

临时密钥的优势：

* 内存安全：服务端不接触文件数据。
* 权限可控：可限制上传路径、操作类型。
* 自动过期：即使凭证泄露，有效期短，风险可控。

服务端生成临时密钥（以阿里云STS为例）：

```java
AssumeRoleRequest request = new AssumeRoleRequest();
request.setRoleArn("acs:ram::123456789:role/oss-upload-role");
request.setRoleSessionName("session-name");
request.setPolicy("{...}"); // 限制上传到特定目录
request.setDurationSeconds(900L); // 15分钟有效期

AssumeRoleResponse response = stsClient.getAcsResponse(request);
Map<String, String> credential = Map.of(
    "accessKeyId", response.getCredentials().getAccessKeyId(),
    "accessKeySecret", response.getCredentials().getAccessKeySecret(),
    "securityToken", response.getCredentials().getSecurityToken(),
    "region", "oss-cn-hangzhou",
    "bucket", "example-bucket"
);
// 返回给客户端
```

客户端上传（JavaScript示例）：
```js
const client = new OSS({
    region: credential.region,
    bucket: credential.bucket,
    accessKeyId: credential.accessKeyId,
    accessKeySecret: credential.accessKeySecret,
    stsToken: credential.securityToken
});
await client.put('user-uploads/myfile.jpg', file);
```


### 3. 资源滥用与成本失控

临时密钥虽然解决了OOM，但存在一个隐患：如果攻击者获取了临时密钥，可以在有效期内无限上传文件，耗尽你的对象存储费用。因此需要更精细的控制。
3.1 预签名URL（Presigned URL）

预签名URL是更安全的替代方案。服务端为单个文件生成一个带签名的URL，客户端使用PUT方法上传。每个URL可以：

* 绑定唯一的对象路径。
* 设置有效期（例如5分钟）。
* 限制文件大小（通过Content-Length范围）。
* 限制HTTP方法（仅PUT）。

这样攻击者即使获取URL，也只能上传一个文件到指定位置，无法批量滥用。

Java生成预签名URL（阿里云OSS）：

```java
GeneratePresignedUrlRequest request = new GeneratePresignedUrlRequest("bucket", "objectKey", HttpMethod.PUT);
request.setExpiration(new Date(System.currentTimeMillis() + 300_000)); // 5分钟
request.setContentLengthRange(1L, 10 * 1024 * 1024L); // 限制1B~10MB

URL signedUrl = ossClient.generatePresignedUrl(request);
return signedUrl.toString();

```


3.2 服务端限流与配额管理

即使使用预签名URL，攻击者仍可能通过大量请求生成URL，然后并发上传。因此服务端需要：

* 限制每个用户每分钟/每天生成URL的数量（基于Redis计数器）。
* 限制每个用户上传的文件总大小（例如每天不超过1GB）。
* 结合业务逻辑：只有完成特定操作（如表单提交）后才生成URL。
