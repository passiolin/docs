# OSS 元数据索引设计 — Elasticsearch 8 方案

## 一、背景与目标

当前预签名上传流程：客户端 → 服务端生成预签名 URL → 客户端直传 S3。服务端只返回了 `objectKey`，**没有持久化任何元数据**。这导致：

- 无法按用户/时间/类型查询文件
- 无法统计存储用量
- 无法做生命周期管理（清理过期文件）

引入 Elasticsearch 8 作为文件元数据索引，**不替代 S3 存储**，只做元数据检索。

---

## 二、索引设计：`infra_oss_files`

### 2.1 Mapping 字段

| 字段 | ES 类型 | 说明 |
|---|---|---|
| `fileId` | `keyword` | 主键，独立 UUID，与 `objectKey` 解耦 |
| `objectKey` | `keyword` | S3 对象路径，如 `images/user123/2026-05-09/uuid-avatar.jpg` |
| `bucket` | `keyword` | 存储桶名称 |
| `visibility` | `keyword` | `PUBLIC` / `PRIVATE` |
| `fileType` | `keyword` | `IMAGE` / `DOCUMENT` / `VIDEO` / `AUDIO` / `GENERIC` |
| `fileName` | `text` + `keyword`（子字段） | 原始文件名，支持全文检索与精确匹配 |
| `contentType` | `keyword` | MIME 类型，如 `image/png` |
| `fileSize` | `long` | 文件大小（字节），上传成功后回调更新 |
| `userId` | `keyword` | 上传用户 ID |
| `uploadTime` | `date` | 上传完成时间 |
| `expireTime` | `date` | 预签名 URL 过期时间（仅记录，不控制 S3 对象生命周期） |
| `status` | `keyword` | `PENDING` / `COMPLETED` / `DELETED` / `EXPIRED` |

### 2.2 字段设计说明

- `fileId` 使用独立 UUID，不与 `objectKey` 绑定。若未来迁移存储路径或更换桶，业务标识不变。
- `fileName` 使用 `text` 类型支持中文/英文分词搜索，同时保留 `keyword` 子字段用于精确匹配和聚合。
- `status` 四态设计，覆盖完整生命周期。

---

## 三、数据写入时机

| 时机 | 写入内容 | 说明 |
|---|---|---|
| **生成预签名 URL 时** | 除 `fileSize`、`uploadTime` 外全部字段，`status=PENDING` | 保证"查得到"，即使客户端未最终上传 |
| **客户端上传完成回调** | 更新 `fileSize`、`uploadTime`、`status=COMPLETED` | 依赖客户端诚实上报，需防篡改校验 |
| **S3 Event Notification** | 同上 | **推荐方案**，S3 上传完成后触发 Lambda/Function，回调服务端更新 ES，不依赖客户端 |

### 3.1 PENDING 记录兜底处理

- 定时任务（如每小时）扫描 `status=PENDING` 且 `expireTime < now` 的记录
- 标记为 `EXPIRED`，可选配合 S3 Lifecycle 清理实际未上传成功的碎片对象

---

## 四、查询场景与索引优化

### 4.1 支持的查询场景

| 场景 | 查询条件 | ES 优势 |
|---|---|---|
| 用户文件列表 | `userId` + `status=COMPLETED` + 分页 | 毫秒级响应 |
| 按文件名搜索 | `fileName.text` 分词匹配 | 全文检索 |
| 按类型/时间筛选 | `fileType` + `uploadTime` range | 聚合过滤 |
| 存储用量统计 | `userId` + `sum(fileSize)` | 聚合计算 |
| 公开资源列表 | `visibility=PUBLIC` + `status=COMPLETED` | 快速筛选 |
| 管理后台审计 | `bucket` + `uploadTime` range + 排序 | 高效分页 |

### 4.2 索引配置建议

- **单索引策略**：文件元数据量增长相对可控，无需按时间滚动
- **分片数**：3~5 个主分片，1 个副本（根据集群规模调整）
- **未来扩展**：若数据量激增，可按 `uploadTime` 启用 ILM（Index Lifecycle Management）做冷热分离

## 五、与现有架构的衔接

| 现有流程 | 新增动作 |
|---|---|
| `POST /api/oss/upload` 生成预签名 URL | 同步写入 ES，`status=PENDING`，返回 `fileId` 给客户端 |
| 客户端完成 S3 上传 | 调用回调接口（或 S3 Event 触发）更新 ES，`status=COMPLETED` |
| `POST /api/oss/download` 查询下载 | 先查 ES 确认 `objectKey` 存在且权限匹配，再生成预签名 URL |
| `DELETE /api/oss/objects` 删除对象 | 删除 S3 对象后，同步或异步删除/标记 ES 记录 |

## 六、风险与兜底

| 风险 | 应对策略 |
|---|---|
| ES 写入失败，但预签名已生成 | 预签名 URL 仍可用，但查不到记录。可异步补偿写入，或允许"无记录"状态存在 |
| 客户端未回调，ES 一直 PENDING | 定时任务扫描标记 EXPIRED，S3 Lifecycle 兜底清理未确认对象 |
| ES 与 S3 状态不一致 | **以 S3 为准**，定时对账任务扫描差异，ES 作为"尽力同步"的检索层 |
| 客户端伪造回调，篡改 fileSize | 回调接口需校验预签名上传的签名或依赖 S3 Event（不可伪造） |

---

## 七、后续可扩展

- **文件内容检索**：结合 Tika 提取文档内容，写入 `content` 字段，支持全文搜索
- **图片元信息**：提取 EXIF（拍摄时间、地理位置、相机型号），丰富检索维度
- **版本管理**：`objectKey` 不变时，ES 中保留历史版本记录，S3 使用版本控制
- **访问统计**：在 ES 中增加 `downloadCount`、`lastDownloadTime` 等字段，记录访问热度
